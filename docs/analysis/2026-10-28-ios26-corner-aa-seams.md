# 圆角上的 1px 细线：三角形覆盖式抗锯齿的边（2026-10-28）

桌面小组件四角的细线被记过两轮，`bbmetal20` 与 `bbmetal21` 都还在。这里给出它的几何形状、排掉的方向，以及现在指向的机制。结论是这些线是圆角被切成三角形扇之后的内部边，成因落在「设备对 CoreAnimation 声明只支持单采样」这条链上，修法是让驱动支持多采样解析，而不是再加一层裁切。

证据帧：`docs/progress/evidence/k90auto/kernel-12377-attr-bbmetal21/run/png/shot-01034.png`（桌面，小组件与图标）、`shot-01549.png`（控制中心媒体卡展开）。原始分辨率 1156×2510，3 倍缩放，所以 1 个物理像素是 1/3 点。

## 1. 线的位置

把 `shot-01034` 里小组件那块白色区域按四个值域分层（`<8` 黑、`8..90` 暗、`90..200` 中、`200..250` 亮、`>=250` 白）逐像素打出来，白色区域是 x 63..1051、y 190..735，圆角半径约 81 像素，弧心在 (144, 270)。

在那个坐标系里，顶左角有一条 45° 的亮线，从矩形角 (63, 189) 出发，经过 (115, 242) 左右停住；把这条线延长，它正好穿过弧心 (144, 270)。弧的下切点在 y=270 附近，那里有一条水平亮线从 x=63 向右到 x≈113 停住，也就是弧心所在的水平线。

四个角都有同一种结构，只是方向按角镜像。把 190..255 的值域线性拉到 0..255 之后看整块，这些线是一簇**从角上放射出来的短斜线与虚线**，间距随角度变化，形状与弧的三角形剖分一致。这不是内容的抗锯齿，小组件那块白色区域里除了这些线没有别的东西。

## 2. 排掉的方向

控制中心展开的媒体卡在 `shot-01549` 里可以当对照：外框有 1px 浅色描边，圆角弧上只有一层干净的抗锯齿，没有放射线；卡片内部的浅灰封面矩形圆角同样干净。桌面底部的 Dock 也是圆角矩形，顶左角只有一层干净的弧，没有多余像素。

也就是说，同一套 Metal 状态、同一个进程（backboardd 与 SpringBoard 都走这条路径）、同一份着色器库下，纯颜色的圆角矩形是干净的，只有小组件那块的圆角带线。裁剪路径、scissor、viewport、混合状态这些全局性的东西因此都不在这个缺口上；`bbmetal18` 与 `bbmetal19` 分别验证过 viewport 与 scissor，与此一致。

图标（Photos、Settings）四角也干净，但图标的圆角是烘进 `Assets.car` 位图的，不经过运行时的圆角剖分，所以它只能说明采样与合成没问题。

## 3. 现在指向的机制

小组件那块白是「被圆角裁切的图层内容」，它的圆角不是烘进位图的。线正好落在扇形剖分的内部边上，说明这些边被真正光栅化成了可见像素，而不是被合并进填充。

设备对 CoreAnimation 声明只支持 1 个采样：`hackios-xnu-kernel/userland/src/redwoodmetal.m:2160` 的 `- (BOOL)supportsSampleCount:(NSUInteger)count { return count == 1; }`。文件开头第 83 行把「multisample resolve」列在未实现项里，`:2147` 到 `:2151` 写明了原因：`MTLStoreActionMultisampleResolve` 与 `resolveTexture` 都没有，contract 只存它有的、不做解析。

Adreno 本身给 2 与 4 个采样，`rwa_texture_shape.sample_count` 也已经从 `[descriptor sampleCount]` 一路传到 contract（`redwoodmetal.m:1232`、`:1630`、`:2263`、`:2601` 四处）。缺的是解析这一步，不是采样数本身。

采样式覆盖用不了，CoreAnimation 就只能用它自己的剖分式覆盖来画圆角，而剖分式覆盖要求相邻三角形在公共边上不重复着色。这条路径在我们的驱动上留下了 1px 的边，这就是看到的放射线。

## 4. 还没闭合的一环

同样的剖分式覆盖，为什么 Dock 与媒体卡没有线。现在有两个候选。

候选一：那两块走的是另一条路径。纯颜色图层可以用着色器内算圆角距离场，或者用已有的 stencil 通路（`rwa_depth_stencil` 是通的，`redwoodmetal_commandbuffer.inc:490` 起把深度模板状态、清除值与参考值都传下去了），不需要剖分。只有「裁切一个带内容的图层」才走剖分。这个候选只需要在日志里确认那两块圆角有没有单独的 draw，不需要改代码。

候选二：剖分路径对所有形状都生效，但纯色形状的边落在同色上所以看不见，而小组件的边落在黑底与白面的交界处所以显出来。这个候选可以用一张纯色背景上的大圆角矩形来试，也可以在媒体卡上把背景换成对比色再拍一次。

区分这两个候选要一次真机，或者一次带 draw 计数的抓取。在此之前，修法方向不受影响：把多采样解析做进 contract 之后，CoreAnimation 不必走剖分式覆盖，这条边自然消失。

## 5. 修法方向

真正的修法有三条，按代价排。

1. 在 contract 里加多采样解析：给 `rwa_render` 的 color attachment 带上 `resolve_target`，在 pass 结束时把多采样附件解析进单采样纹理。然后把 `supportsSampleCount:` 改成对 2 与 4 回答 yes。这一步同时解开 `AppleMetalGLRenderer` 与多采样着色器那一片。
2. 只对 CA 这一个调用方回答 yes：不做通用解析，只把 CA 的 store action 当普通写入处理。风险是 CA 会真的去读解析后的纹理，拿到的是未解析的多采样内容。
3. 不动驱动，让小组件的圆角不经过剖分：这一条要看候选一是否成立，且只解决小组件一处。

第 1 条是根因修法。第 3 条属于在症状上换一种画法，与「要的是根因」的要求相反。

## 6. 记录

`docs/progress/2026-10-27-ios26-k90.md` §44 里那句「圆角裁切没有生效：媒体卡展开后，子图层按矩形边界绘制，父图层圆角处留下深色方块」描述的是 `bbmetal20` 的布局错位，那一轮之后布局已修好，媒体卡的圆角在本轮的 `shot-01549` 里是干净的。现在剩下的问题是小组件四角的放射线，两件事不是同一个缺口。
## 7. 第一次抓取失败：上限加静默丢弃

`bbm27` 的载荷里带了第一版指纹表：一行一个（管线句柄，附件形状），上限 96 行，满了之后 `rw_pipeline_note` 直接 `return`，不打印也不计数丢弃。整轮日志里去重后正好得到 96 条，也就是每一份快照里都是同样那 96 个早期形状。小组件与 Dock 的绘制没有进表，数据不可用。

两个教训。一是**任何有上限的采集结构，满了必须打印并说明丢了多少**，否则读的人会把「上限」当成「全部」。二是**附件尺寸当不了图层身份**：96 条里 `colour` 全是 2、`samples` 全是 1，尺寸是 1125x2436、1152x2496、576x1280 这类画布与图层尺寸，没有一条能对上小组件那块白的 989x546 或者 Dock 的 1156x230。

这个判断要换一个量。视口是我们已经随 draw 传给 Gallium 的字段，早前那条 `a viewport rectangle is not implemented (asked for 96x96 at 0,0 of a 192x192 attachment)` 就是按视口描述图层的，用它区分度高于附件尺寸。

按 lead 的决定，这一条不再单独花轮次：多采样解析是 a6xx 本来就有的能力，验收本来就要求两类圆角都干净，所以直接实现，适用范围按实现后的验收结果反推。

## 8. 主因作废：斜线在 launchd 缓存补齐后不再出现

`bbm29`（启动参数补回 `rootdev=md0 launchd_unsecure_cache=1`）的同位置截图对比推翻了本文前面那条根因链。同一块小组件、左上角、同倍率、最近邻放大：

- `bbm28`（缓存缺失）：白块角外侧有发散的斜线扇面与断续白线。
- `bbm29`（缓存补齐）：干净的圆角弧，没有扇面，没有断续线。

图片在 `docs/progress/evidence/k90auto/kernel-12377-attr-bbm29/report/corner-tl-bbm28.png` 与 `corner-tl-bbm29.png`。

所以「`supportsSampleCount:` 只对 1 答 yes，导致 CA 走单采样路径、圆角边缘没有多采样平滑」这条推断不成立。缓存补齐以后 SpringBoard 拿到的图层结构与图层数量都变了（2 个图标变成 15 个、白块小组件变成有名字的两个、出现两页与页码圆点），斜线在没有开启多采样的情况下消失。本文第 2～7 节记录的事实与测量保留，从它们推出的因果判断按本节作废。

残留的形态变了一类：右下角还有一条很淡的斜向灰线，贴在弧边内侧，右上角外侧有一小段竖线（`corner-br-bbm29.png`）。数量与面积比 `bbm28` 小一个数量级，形态也是一条线而不是扇面。这一类尚未定位，下次记录时按「位置、数量、形态」三栏写，便于跨轮比较。

## 9. 新基线：观察对象换了，旧记录不能直接沿用

`bbm29` 之后桌面的内容变了，圆角的观察对象随之改变：从「一块白块小组件的四角」变成「15 个应用图标 + 2 个带名字的小组件（Weather、Calendar）+ 4 个 Dock 图标的圆角」。`corner-tl-bbm28.png` 那一类扇面记录对应的是旧对象，跨轮比较之前要先确认对象是同一类。

同一帧上仍能看到的残留有两处，只记形态与位置，不写成因：

- 小组件右下角弧边内侧，一条很淡的斜向灰线，长度约占圆角弧长的一半。
- 小组件右上角外侧，一小段竖直短线，紧贴圆角边界。

两处的数量与面积比 `bbm28` 的扇面小一个数量级。下次记录按「位置、数量、形态、所在图层」四栏写。

## 10. 方法教训：先比对载荷差异，再往里查

圆角与扩展登记两条根因链都在同一轮里作废，共同原因是 `bbm18`～`bbm28` 的载荷缺了启动参数 `rootdev=md0 launchd_unsecure_cache=1`。那段时间的排查顺序是「从现象往里推」：先看斜线像不像多采样缺失、先看失败查找像不像缺服务，然后各自做了实现或补丁。这些工作都在给一个不存在的配置问题做修复。

更省成本的顺序是先问一句「当前载荷与最后一次正常载荷差什么」。那一次对比只需要两条差异：内核命令行、根盘内容。`§39` 那轮是完整的，`bbm` 系列不完整，两边用的是同一份根盘与同一份 `system26`，所以差异只可能在载荷之外的三处——内核命令行、设备树、启动脚本。一句 `diff` 就能定位到命令行少了两项。

这条与认知无关，与顺序有关：先对齐「哪一次是好的、好在哪里」，再决定查什么。
