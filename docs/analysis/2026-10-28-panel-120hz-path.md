# 120 Hz 在当前栈里的状态：面板时序、合成器目标、每帧成本

2026-10-28，display。task-20 的产出。全部离线核出，没有构建、没有碰设备。数据侧的帧间隔统计由 perf 提供，本文引用时标明口径；代码侧的行号都在 `hackios-xnu-kernel/` 下。

## 1. 结论与先后顺序

面板物理上支持 120 Hz，而我们的栈现在跑 60 Hz，这个 60 是我们自己定的一个软件值，改它是一个启动参数。但只改它不能保证玻璃上出现 120 Hz，因为面板的扫描模式不由我们的内核决定，我们读不到它，也从来没写过它。

三层的现状与改动代价：

| 层 | 现在是什么 | 改动位置 | 代价 |
|---|---|---|---|
| 面板模式 | 由 boot loader／Android 留下的设置决定，我们的内核不碰显示硬件 | 无（我们没有这一层的代码） | 要动就得写显示控制器驱动，或从 Android 侧改 |
| 合成器目标 | 60 Hz，来自 `kFBRefreshHz`，可由启动参数 `fb_hz` 改 | 启动参数一处 | 一次打包，不重建任何产物，哈希不变 |
| 每帧成本 | 生产链 9.40 ms（中位）、驱动拷贝 1.77 ms（中位）、节拍等待 7.24 ms | 我们的 AIR／Metal 路径 | 代码改动，perf 的 task-16 指出成本几乎全在 program 准备与查找 |

先后顺序建议：**第一步只加 `fb_hz=120` 跑一轮**，理由是这一步有判别力。每帧 16.64 ms 里有 7.24 ms 是我们自己的节拍等待，这一项随 `fb_hz` 缩小；剩下 9.40 ms 的生产链里只有 2.34 ms 记在我们的 Metal 路径上，其余部分没有记账，分不清是 CoreAnimation 按 60 Hz 节拍的等待还是它自己的渲染工作。`fb_hz=120` 之后 `tl: v` 的间隔会直接分辨这两者：掉到 8.33 ms 附近说明其余是等待，停在 16.64 ms 说明渲染工作是瓶颈。第二步按第一步的结果排：若间隔掉下来，缺的就是面板侧确认（§6 的 TE 读数）；若停在 16.64 ms，就先降每帧成本，改动位置在 AIR 的 program 准备与查找。**不建议第一步就同时改面板侧与合成器侧**，两个变量会让结果没法归因。

第一步那一轮能证明什么、不能证明什么，要分开写进轮次记录。它能证明的是我们的节拍周期变了、以及 CoreAnimation 从 `:338` 读到的模式速率变了。它证明不了面板的扫描率变了：面板时序由 boot loader／Android 留下的设置决定，我们既读不到也没写过（§2）。已知风险是若面板停在 60 Hz 而我们以 120 Hz 写，约一半的帧从没被显示，并可能撕裂，而这两件事在日志里都看不出来，帧号照常递增、`tl: v` 照常打、截图照常是 home screen。所以 `shown` 间隔掉到 8.33 ms 附近只能读成「我们的节拍与 CA 的目标变成了 120 Hz」，要读成「面板跑到了 120 Hz」得由 §6 的 TE 读数或设备外部观测来支撑。这个风险可恢复（去掉启动参数即可）且不损坏任何东西。

那一轮要附带盯两个数：`present()`（SwapEnd，`:824-845`）在交换队列满时用 `IOLockSleepDeadline` 阻塞调用方、期限 `SWAP_HELD_MS` 700 ms（`:79`），队列深度 `fb_queue` 默认 2（`:154-158`）。节拍变快之后若 CA 的生产链没跟着变快，队列满的可能性上升，所以驱动统计行里 `swaps waited for the frame before` 与 `gave up` 两个数要单独看，round C 九个窗口都是 0 与 0。这是 `fb_hz=120` 可能引入的唯一一个新阻塞点。

验收阈值 55 fps（`tools/k90auto/gestures.py:26` 的 `CC_TARGET_FPS = 55`，注释记着 iOS 16.5 对照的六轮每次拉动跑 55.9 到 60.6）在 60 Hz 下已经达到，所以这一步的目标是提高上限，不是修一个不达标。

## 2. 显示路径把面板设成什么模式：不设

`iokit/Kernel/MiniIOMobileFramebuffer.cpp:5-7` 是这个驱动的自述：显示就是 boot loader 留下的那个 framebuffer（内核文本控制台画的那块内存），「There is no hardware behind it that we drive: a "swap" copies the pixels of the surfaces of its layers into that memory, and "vsync" is a timer.」

几何信息从 boot 交接来：`:36` `extern struct vc_info vinfo`，`:411-413` 把 `vinfo.v_baseaddr`、`v_width`、`v_height` 取成 `fBase`、`fPanelWidth`、`fPanelHeight`。`struct vc_info`（`osfmk/console/video_console.h:87-102`）的字段是 height、width、depth、rowbytes、baseaddr、type、name、physaddr、rows、columns、rowscanbytes、scale、rotate、reserved，**没有速率或时序字段**，所以交接本身给不出面板刷新率。

驱动自己报的几何：round C 日志里 `MiniIOMobileFramebuffer: display 1125x2436 on a panel of 1156x2510 (4624 bytes per row)`。1125×2436 是渲染尺寸（`fWidth`／`fHeight`，`:415-422`，可由启动参数 `fbwidth`／`fbheight` 覆盖），1156×2510 是面板尺寸，4624÷4=1156 说明每像素 4 字节。渲染尺寸到面板尺寸要做缩放，`fb_filter=1`（默认，`:144`）是双线性、`0` 是最近邻，`fb_threads` 决定几个处理器一起缩（`:152`，默认 3，roundb 与 round C 都用 `fb_threads=2`）。

树里没有显示控制器驱动：在 `bsd/` 与 `iokit/` 下按 dsi／dpu／sde／mdss／panel 找文件名，没有命中。`:248-249` 还写明面板的扫描位置谁都读不到，因为显示块的寄存器时钟是关的。

**面板的时序在 Android 的 DTBO 里。** `annibale-backup/20261022-2355/dtbo_a.img`（Qualcomm dtbo 头 magic `0xd7b7ab1e`、1 个条目、505,848 字节在偏移 64；用 `dtc -I dtb -O dts` 解出 20,315 行）里这块面板是：

```
qcom,mdss-dsi-panel-name = "xiaomi p11 42 0d 0a cmd mode dsc dsi panel"
qcom,mdss-dsi-panel-physical-type = "oled"       qcom,mdss-dsi-panel-type = "dsi_cmd_mode"
qcom,mdss-dsi-bpp = <0x1e>                       qcom,mdss-dsi-traffic-mode = "burst_mode"
qcom,dsi-ctrl-num = <0x00>   qcom,dsi-phy-num = <0x00>   lane 0..3 全部启用
timing@0  1156x2510  帧率 0x78=120  vfp/vbp/vpw=64/64/32  hfp/hbp/hpw=64/64/32  clockrate 0x47d2d740=1205 MHz
timing@1  1156x2510  帧率 0x5a=90   porch 与 clockrate 与 timing@0 相同
timing@2  1156x2510  帧率 0x3c=60   porch 与 clockrate 与 timing@0 相同
```

复现方式：从镜像偏移 64 读 505,848 字节写成一个 `.dtb`（前 4 字节是 `d00dfeed`），再 `dtc -I dtb -O dts -f`。

1156×2510 与驱动日志里的面板尺寸一致，所以 DTBO 里这块面板就是我们写像素的那块。三档时序的 porch 与 DSI 时钟完全相同、只有 `panel-framerate` 不同，这与命令模式面板的行为一致：面板有自己的帧内存，按自己的速率刷新，宿主只在有更新时送像素。这一块面板节点里没有找到 `qcom,mdss-dsi-pan-enable-dynamic-fps` 与 `qcom,dsi-supported-dfps-list`，DTBO 里那些属性属于别的面板变体。

所以「刷新率、时序、vsync 来源是从哪里定的」的答案分两半：**面板时序从 Android 侧继承，写死在 DTBO 的面板节点里，我们的代码既不读也不写**；**我们这一侧的 vsync 是一个软件定时器**，周期由启动参数决定（§3）。

## 3. 16.67 ms 这个下界是谁定的：我们的软件定时器

`refreshHz()`（`:178-181`）返回 `gRefreshHz`，越界回落到 `kFBRefreshHz`，接受范围 1 到 240。`gRefreshHz` 是 `:145` 的 `TUNABLE(uint32_t, gRefreshHz, "fb_hz", kFBRefreshHz)`，默认值 `kFBRefreshHz` 在 `:74` 是 60。

它有四个用处：

| 位置 | 作用 | 本轮是否生效 |
|---|---|---|
| `:916` | `show()` 里的节拍周期，`:930` `clock_delay_until(next)` 按它决定何时把画完的帧拷进面板内存 | 生效，round C 每帧实测等 6696–7138 µs |
| `:831` | `period * 5/4`，只作为「这次交换比上次晚了一个刷新以上」这个统计的阈值（`:841` `fStatSwapsLate`） | 只影响一个计数 |
| `:1205` | `armVSync()`，给注册了选择器 72 的客户端发 vsync 通知的定时器 | 从未 arm：72 两轮都没被调过（§4） |
| `:338` | `rate = refreshHz() << 16`，写进 `:355-360` 的 `SyncRate`／`PreciseSyncRate`，由 `:370-371` 作为 `TimingElements`／`ColorElements` 属性发布 | 生效，这是用户态读到的速率 |

节拍的实现（`:913-935`）：`aim = period * 3/8`（60 Hz 下 6.25 ms），`next` 从 `fBeat + period` 递推，再按早迟误差的八分之一收敛到 aim，然后 `clock_delay_until(next)` 睡到那个绝对时刻。这是内核定时器等待，不是忙等也不是 fence。帧来得比一个半周期还晚时不等，直接上屏并重置节拍（`:920-921`）。

`fb_hz` 改的是这四处，**不改面板扫描率**。若面板停在 60 Hz 而我们以 120 Hz 写，结果是约一半的帧从没被显示，并可能撕裂；日志里看不出来，帧号照常递增、`tl: v` 照常打、截图照常。

perf 核过 **73 份 `manifest.json` 全文里 `fb_hz=` 零命中、63 轮的 `commands.jsonl` 也零命中**，所以已归档的每一轮都跑默认 60，没有任何一轮请求过 8.33 ms 的周期。`tools/k90auto/summary.py:205` 的 keep 列表里本来就含 `fb_hz`，工具一侧准备着从没用过。

数据侧的判据结果（perf，口径见 §7）：63 轮、218,285 个相邻帧号间隔里，落在 8.33 ms ±0.5 ms 的是 **0 个**；按 `n = round(间隔 / 8.3333 ms)` 分档，偶数 n 占 96.07%（n=2 即 16.67 ms 单独占 78.91%），奇数 n 占 3.93% 且集中在 25.0 与 41.67 这些较大的奇数倍上；全部 63 轮里最小的单个间隔是 9.56 ms。

这个分布是代码本来就会产生的结果，因为 `tl: v` 的 `shown` 字段是节拍到来的时刻：`ready` 在 `:912` 取（GPU 等待结束之后），`began` 在 `:934` 重新赋值（节拍等待结束之后），`shown = began` 在 `:937`，`drawn`（打成 `done`）在 `:1010`。所以相邻 `shown` 之差量的是软件节拍的节奏，出现小于 16.67 ms 的间隔不需要面板跑 120 Hz。n=1 那一档的 51 个样本实际值在 9.56 到 12.4 ms，与 `:920-921` 那条「晚到的帧直接上屏并重置节拍」的分支相容；具体是哪一条路径产生的没有逐帧追。

## 4. iOS 26 用户态会不会请求 120 Hz：问了，我们的回答把它封住了

驱动对每个选择器的前若干次调用会打追踪行，开关是 `:106` 的 `TUNABLE(uint32_t, gFBTrace, "fbtrace", 3)`，打印在 `:1255-1265`，带调用方进程名、pid、标量与结构体尺寸，**已实现的选择器也打**。未实现的另有一条 `selector N not implemented`，由 `:1385-1387` 的 `gFBLogged` 位图限制成每个选择器每次启动一条。选择器枚举定义在同一个 `.cpp` 的 `:49-70`（不在头文件，20 个名字），case 表是同文件 `IOMobileFramebufferUserClient::externalMethod` 的 `:1248-1400`（20 个名字里 16 个有 case）。

口径：覆盖 round C 与 roundb 各自的 `run/*.log` 全部 24 个文件（`s000.log` 到 `s020.log`、`hung-held.log`、`hung-held-serial.log`、`system-upload.log`）。两轮的调用方都只有两个：`backboardd[38]` 调 23 个号（3 4 5 6 8 12 15 17 18 22 25 27 29 33 50 57 68 74 78 79 84 86 88），`MobileGestaltHelper[57]` 调 2 个（8 28）。两轮的号集与形状完全相同。未实现的 raw 行数是 round C 297 条、roundb 300 条，唯一号都是 15 个；raw 计数被快照重叠放大（同一条行出现在 24 个文件里的 21 个），不表示被调了 21 次。

三条决定性的：

1. **backboardd 调了 74 `kFBMethodSupportedFrameInfo`**，形状是 1 个标量入、2 个标量出、64 字节结构出。我们的实现 `:1350-1358` 把 `out[0]` 置 0、`scalarOutputCount` 改成 1、结构体 bzero，也就是**告诉窗口服务器支持的帧信息一个都没有**。这是设备日志直接来的。
2. **73 `kFBMethodChangeFrameInfo` 两轮都没被调过。** 我们的实现在 `:1333-1334`，与另外四个选择器共用一个 `return kIOReturnSuccess`，什么都不做。形状合起来是「用户态问了我们支持什么，我们答零个，于是它从来没来改过」。
3. **72 `kFBMethodNotifications` 两轮都没被调过**，把 `:247-248` 那句注释（CoreAnimation 从不请求本驱动的刷新通知，它按自己从这里读到的速率走自己的钟）从注释变成实测。这一条排除了一个候选解释：CA 不靠我们的刷新通知，它的钟来自 `:338` 发布的模式速率。

一个未实现的选择器值得单独记，但不给它命名：**78** 被调了三次，两个形状是 5 个标量 `[0x32 0x0 0x1 0x4]` 与 `[0x32 0x0 0x1 0x5]` 各带 64 字节结构入，第三个是 6 个标量 `[0x33 0x0 0x1 0xc]` 带 656 字节结构入；64 字节正好是 74 输出的结构体大小；三次调用落在 SwapBegin（选择器 4）与 SwapEnd（选择器 5）之间。78 在枚举里没有名字，我们的枚举来自 iOS 16.5 的用户态侧（`:9-10`、`:48`），而 rootfs 是 iOS 26，所以命名需要 iOS 26 的选择器表，形状吻合不构成命名依据。

15 个未实现的号里，三个对到枚举名且都与显示有关：25 `kFBMethodGetDigitalOutState`（`:58`）、29 `kFBMethodGetDisplayArea`（`:60`）、57 `kFBMethodGetColorRemapMode`（`:62`），三个都在枚举里有名字但没有 case。第四个有名字无 case 的是 82 `kFBMethodGetProtectionOptions`（`:69`），两轮都没被调过。其余 12 个号（15、17、18、22、27、33、50、68、78、84、86、88）在枚举里没有名字，原样报号。其中 50 的标量是 `[0x10000 0x0]`，0x10000 在我们自己报速率用的 16.16 定点里等于 1.0；27 与 17 是一对 3084 字节结构的出与入。这两条只是形状记录。

调用顺序（round C 的 `s001.log` 按出现序）：88 57 18 15 22 8 29 33 79(2056 出) 79(3164 出) **74(64 出)** 25 12 79(44 出) 6 27(3084 出) 17(3084 入) 84 50 4(SwapBegin) **78(656 入) 78(64 入) 78(64 入)** 68 5(SwapEnd) 3。

我们自己那几个用户态库（`userland/src/redwoodmetal.m`、`redwooddrawable.m`、`sb_metal_experiment.m` 与 `redwoodmetal_*.inc`）里 display link 与 frame rate 相关的实现是零命中：按 `DisplayLink`、`displayLink`、`FrameRate`、`frameRate`、`CAFrameRateRange`、`preferredFrameRate`、`maximumFrameRate`、`refreshRate` 搜过。CADisplayLink 与 `CAFrameRateRange` 由共享缓存里 Apple 的 QuartzCore 提供，它们要了解显示能力只能通过 IOMobileFramebuffer，也就是上面这条 74／78 的路径。

一个观测上限：`fbtrace` 默认 3，所以每个选择器只记前 3 次，**调用频次从现有日志测不出来**，78 是不是每帧一次判不了。调大 `fbtrace` 是启动参数、不重建，代价是行数（23 个号各 N 行）。

## 5. 每帧成本的账与达到 120 Hz 要动什么

用 `tl: v <id> ready <R> shown <S> done <D>` 的原始时间戳算 round C 的 `s020.log`（1861 个唯一帧号、1859 对相邻帧号）：

| 量 | 中位数 | p95 | 来源 |
|---|---|---|---|
| `shown` 间隔 | 16.64 ms | 17.13 ms | 本次计算 |
| `ready − 上一帧 shown`（生产链） | 9.40 ms | 11.04 ms | 本次计算 |
| `done − shown`（驱动的拷贝） | 1.77 ms | 3.22 ms | 本次计算 |
| 节拍等待（`shown − ready`） | 约 7.24 ms | — | 16.64 减 9.40 |

四项与驱动自己的每五秒统计行互相印证，round C 九个窗口：`298 frames in 5011 ms (59 a second), 1933 us each in the driver, after 41 us waiting for the GPU and, 297 of them, 7025 us for the next refresh`，各窗口的「in the driver」是 1924–2033 µs、「waiting for the GPU」是 41–42 µs、「for the next refresh」是 6696–7138 µs，六个窗口是 60 fps，另外三个是 23、24、13 fps（静止屏幕重绘少，统计行分不清「生产者慢」与「屏幕没变化」）。`done − shown` 的中位数 1.77 ms 与 perf 独立算出的偏移（min 0.269、median 1.766、p95 3.280、max 4.084 ms）一致；`shown` 间隔的中位数 16.64 ms 与 perf 的稳态 16.61 ms 一致。

生产链那 9.40 ms 里，perf 从插桩窗口记账到的是 2.34 ms（`submit` 1.25、`batch submit` 0.89、`driver` 0.104、`own` 0.104，`client`／`sync`／`pass` 全 0）。CoreAnimation 自己的渲染工作两边都没有记账，所以「已记账的工作约 4.1 ms（2.34 加驱动的 1.77）」是下界。

**驱动没有让 CA 等过**，三条都排除了：选择器 6 `kFBMethodSwapWait` 立即返回（`:1323-1328`，只在 `touch_lat=1` 时打一行 `tl: w`）；`present()`（SwapEnd，`:824-845`）只在交换队列满时用 `IOLockSleepDeadline` 阻塞调用方（队列深度 `fb_queue` 默认 2，`:154-158`；期限 `SWAP_HELD_MS` 700 ms，`:79`、`:833`），而 round C 的统计行是 `0 swaps waited for the frame before, 0 gave up`，队列从没满过；GPU 完成等待每帧 41–42 µs（`:906`，上限 `SWAP_GPU_MS` 500 ms 见 `:78`）。

由此，120 Hz 的槽是 8.33 ms 时：驱动的拷贝 1.77 ms（p95 3.22 ms）已经放得下；节拍等待由 `fb_hz` 决定，120 Hz 下 aim 变成 3.125 ms；未知的是生产链里除我们那 2.34 ms 之外的部分，它要么随节拍缩短（是等待），要么不缩短（是工作）。这是第一步实验要分辨的东西，也是 §1 那个顺序的依据。

## 6. 面板侧的读数缺口与 TE 那条路

我们内核运行时面板在哪一档，现在无从知道：寄存器时钟关着（`:248-249`），boot 交接不带速率（§2），DTBO 只说明支持哪些档。

命令模式的面板自己发 TE（tearing effect）信号，**TE 由面板产生，不依赖 SoC 显示块的寄存器时钟**，所以那条「读不到」的限制不构成障碍。DTBO 里：

```
qcom,platform-te-gpio = <&tlmm>, <0x56 0x00>;        → TLMM 引脚 0x56 = 86
pinctrl-2 = <&sde_dsi_suspend>, <&sde_te_suspend>, <&sde_esync0_suspend>;
面板节点内  qcom,mdss-dsi-te-using-te-pin;  te-dcs-command = <0x01>;  te-pin-select = <0x01>;
```

我们的内核已经在用 TLMM：`bsd/dev/redwood_goodix.c:509` 的 `tlmm_phys = 0x0f100000UL; tlmm_size = 0x102000UL;`（注释写着 vendor TLMM base + 0x100000，见 sm8750.dtsi）与 `:543` 的 `tlmm = ml_io_map(TLMM_PHYS, TLMM_SIZE);`。所以数 TE 脚的翻转频率在现有能力范围内，是一条纯软件的面板实际刷新率读数。

分两步，第一步只读：

1. 只读采样：按 1 kHz 左右读 86 号脚的输入状态位，数一秒内的翻转次数，60 Hz 与 120 Hz 差一倍，不改任何配置。这是内核改动（新文件或现有 `redwood_*.c` 里加一段，加一个启动参数控制），按一轮只改一个变量的规矩，不能与 `fb_hz=120` 同一轮上。
2. 若第 1 步读不到翻转，才考虑把该脚的 mux 改成 GPIO 输入。`te-pin-select = <0x01>` 表示 Android 把 TE 路由给了 DSI 控制器的硬件 TE 输入，脚当前可能不在 GPIO 功能上；改 mux 有可能干扰正在扫描我们 framebuffer 的那条显示流水线。Qualcomm TLMM 的输入状态位在脚被 mux 到非 GPIO 功能时通常仍反映 pad 电平，这一条未实测。第 2 步要单独一轮，且要先记下原配置以便恢复。

设备侧读数清单（面板模式，供下一轮带上）：从 Android 侧读这块面板的可选模式与当前模式（`/sys/class/drm/card*-DSI-*/modes`、同目录的 `status`、`dumpsys SurfaceFlinger` 里的 refresh rate），目的是确认 120 Hz 档在 Android 下确实被选用过、Android 平时跑哪一档；这一条给不出 boot loader 交接给我们时是哪一档。从设备外部观测的方案（相机长曝光拍滚动条纹，或光电二极管贴屏数闪烁）在 TE 读不到时替代 TE，代价是要人参与与一个测试图案。

## 7. 采集条件与单位口径

引这一层的数要带三个口径。

**插桩造成的不对称。** roundb 与 round C 的 AIR 库都带 draw-perf 插桩，插桩让间隔变长、不会变短。所以带插桩都能看到 8.33 ms 样本就说明面板确实跑过 120 Hz，看不到不能排除关掉插桩后能看到。本轮结果是看不到，所以数据侧只能给到「63 轮里没有这样的样本」。与之独立的一条理由不受插桩影响：vsync 周期是 `NSEC_PER_SEC / refreshHz()`，而没有一轮设过 `fb_hz`，所以没有任何一轮请求过 8.33 ms 的周期。

**插桩的单位。** 插桩打的 `us` 值与内核 `tl:` 的微秒差 625/12 = 52.0833 倍，来源是 19.2 MHz 的时基（`numer=625`、`denom=12`），所以插桩的数乘 625/12 才是微秒，`FD_PERF_SLOW_US 6000` 的真实阈值是 312.5 毫秒。perf 给本文的稳态 16.61 ms 与 2.34 ms 已经是换算后的真实时间，与本文用 `tl: v` 独立算出的 16.64 ms 对上；引 task-16 的其它绝对数值时要带这条换算，相对比例不受影响。

**帧数的三个口径。** `gestures.py` 与直接数唯一 `tl: v` 行是一个值；`summary.py --verify` 的 `frames` 是另一个（它数 `tl: v N ready X shown` 正则的匹配）；`coverage:` 行是第三个（只数落在覆盖跨度内、带 `shown` 时间戳的）。三个值不构成矛盾。本文用的是唯一帧号：round C 的 `s020.log` 里 1861 个，而全轮的帧号是 1..3611，差额是被日志缓冲挤掉的部分。

**帧间隔取的是哪个字段。** 本文取 `shown`。`tools/k90auto/gestures.py:48-50` 的正则是 `tl: v (\d+) ready (\d+) shown (\d+) done (\d+)`，而 `shown.append(int(m.group(4)))` 取的是第四组 `done`，变量名叫 `shown`。两个字段分布形状相同，逐帧 `done − shown` 的偏移实测（6 个大轮次、53,247 帧）是 min 0.269、median 1.766、p95 3.280、max 4.084 ms，所以「有没有 8.33 ms 样本」这个结论在两个字段下一样，引具体数值时要写清是哪个。

**这批帧率读数是在什么输入下采的。** `gestures.py` 对 round C 的输出是 `swipe-left 1x: no animation to measure, each window held one frame -- a desktop with one page turns nothing, the swipe springs back`，且 0 次控制中心下拉被识别。单页桌面上的滑动不产生连续动画，所以那批帧率读数采到的是系统自发的重绘，不是被驱动的动画。要论证 120 Hz 有没有意义，先要有一个能产生连续动画的输入。

**截图与帧号的时间覆盖。** 截图命名是 shot-NNNNN，NNNNN 是轮内十分之一秒（`tools/k90auto/run-auto.py:34,163,166`，`RUN_TIMING` 的 `shot_from=100` 是设计值），所以 round C 的 101 张截图只覆盖 100.1 到 419.0 s；渲染段 0 到 100.2 s 的「桌面显示出来了」由 3611 个帧号零断裂支撑，没有逐张截图。引这两段时要分开。

## 8. 未验证与下一步

未验证的部分：

1. 我们内核运行时面板实际在哪一档。补法是 §6 的 TE 只读采样，或设备侧从 Android 读模式（后者给不出交接时的档位）。
2. iOS 26 的 CoreAnimation 把速率提到 120 Hz 是否还需要 74 报出条目、以及 78 是什么。我们的枚举来自 iOS 16.5，命名需要 iOS 26 的选择器表。补法有两条：`fb_hz=120` 之后看 `tl: v` 的间隔是否掉到 8.33 ms；`fbtrace` 调大之后看 78 的调用频次与它带的结构体内容是否随速率变化。
3. 生产链 9.40 ms 里除我们那 2.34 ms 之外的部分是什么。补法同上，`fb_hz=120` 的间隔变化直接分辨「等待」与「工作」。
4. TLMM 输入状态位在脚被 mux 到硬件 TE 功能时是否仍反映 pad 电平。
5. 面板以 60 Hz 扫描而我们以 120 Hz 写时的可见后果（撕裂还是重复帧）。我们的截图取自帧缓冲内存还是面板侧没有核过，若取自内存则截图看不到这类后果。

下一步按 §1 的顺序：第一步只加 `fb_hz=120` 跑一轮，不改代码、不重建、驱动与 AIR 的哈希都不变；第二步按第一步的间隔结果排 TE 读数或降每帧成本。
