# 120 Hz 在当前栈里的状态：面板时序、合成器目标、每帧成本

2026-10-28，display。task-20 的产出。全部离线核出，没有构建、没有碰设备。数据侧的帧间隔统计由 perf 提供，本文引用时标明口径；代码侧的行号都在 `hackios-xnu-kernel/` 下。

## 1. 结论与先后顺序

面板物理上支持 120 Hz，而我们的栈现在跑 60 Hz，这个 60 是我们自己定的一个软件值，改它是一个启动参数。但只改它不能保证玻璃上出现 120 Hz，因为面板的扫描模式不由我们的内核决定，我们读不到它，也从来没写过它。

三层的现状与改动代价：

| 层 | 现在是什么 | 改动位置 | 代价 |
|---|---|---|---|
| 面板模式 | 由 boot loader／Android 留下的设置决定，我们的内核不碰显示硬件 | 无（我们没有这一层的代码） | 要动就得写显示控制器驱动，或从 Android 侧改 |
| 合成器目标 | 60 Hz，来自 `kFBRefreshHz`，可由启动参数 `fb_hz` 改 | 启动参数一处 | 一次打包，不重建任何产物，哈希不变 |
| 每帧成本 | 生产链 9.40 ms（中位）、驱动拷贝 1.77 ms（中位）、节拍等待 7.24 ms | 我们的 AIR／Metal 路径 | 代码改动，perf 的 task-16 指出成本几乎全在 program 准备与查找 |

先后顺序：**`fb_hz=120` 那一轮已经跑过（round E），它的答案是先降 CA 一侧的成本。** 那一轮证明节拍周期确实变成了 8.333 ms（69 个相邻帧号的 `shown` 间隔里有 8 个落在 7.67 到 9.21 ms，而 round C 的 3606 个间隔最小值是 14.72 ms），也证明帧周期没有变（16 个间隔均值 16.98 ms 对 round C 的健康中位数 16.640 ms，在这个样本量之内没有差别）。三组间隔的节拍倍数是 0.98、2.04、4.99，全部落在整数节拍上，所以帧周期是按节拍网格量化的一个整数量：`ceil(非节拍时间 / 周期) × 周期`。非节拍时间约 9.6 ms 超过一个 8.333 ms 的槽，每一帧错过一个节拍落到下一个上，把刷新率翻倍只把网格加密，收益是 0。读数与推导见 §5.1。

要拿到 120 fps，第一步是给 CA 一侧那 8.24 ms 加时间戳，因为它现在没有任何读数，而它是唯一超过一个槽的项；在那之前谈「降哪一块」没有依据。第二步才是把 `fb_hz` 提上去。驱动拷像素的 1.77 ms（p95 3.22 ms）在 8.33 ms 的槽里已经放得下，节拍等待由 `fb_hz` 决定，两项都不挡路。面板侧的确认（§6 的 TE 读数）与这两步独立，它回答的是玻璃上到底扫了多少次，可以排在任何位置，但它给不出帧率。

round E 证明了什么、没有证明什么，要分开写。它证明的是我们的节拍周期变了、以及 CoreAnimation 从 `:338` 读到的模式速率变了。它证明不了面板的扫描率变了：面板时序由 boot loader／Android 留下的设置决定，我们既读不到也没写过（§2），而 `shown` 这个时间戳来自我们自己的定时器（§3），所以 7.67 ms 的间隔只能读成「我们的节拍变成了 8.333 ms」。已知风险是若面板停在 60 Hz 而我们以 120 Hz 写，约一半的帧从没被显示，并可能撕裂，而这两件事在日志里都看不出来，帧号照常递增、`tl: v` 照常打、截图照常是 home screen。这个风险可恢复（去掉启动参数即可）且不损坏任何东西。

`present()`（SwapEnd，`:824-845`）在交换队列满时用 `IOLockSleepDeadline` 阻塞调用方、期限 `SWAP_HELD_MS` 700 ms（`:79`），队列深度 `fb_queue` 默认 2（`:154-158`）。节拍变快之后若 CA 的生产链没跟着变快，队列满的可能性上升，所以驱动统计行里 `swaps waited for the frame before` 与 `gave up` 两个数要单独看。**round E 的 8 个窗口这两个数全是 0**，`fb_hz=120` 没有引入这个新阻塞点；`came a refresh late themselves` 从 round C 的 4 对 3611 变成 44 对 68，与 `:918-921` 的门槛从 25 ms 缩到 12.5 ms 一致。

验收阈值 55 fps（`tools/k90auto/gestures.py:26` 的 `CC_TARGET_FPS = 55`，注释记着 iOS 16.5 对照的六轮每次拉动跑 55.9 到 60.6）在 60 Hz 下已经达到，所以这一步的目标是提高上限，不是修一个不达标。

## 2. 显示路径把面板设成什么模式：不设

`iokit/Kernel/MiniIOMobileFramebuffer.cpp:5-7` 是这个驱动的自述：显示就是 boot loader 留下的那个 framebuffer（内核文本控制台画的那块内存），原文是 There is no hardware behind it that we drive: a `swap` copies the pixels of the surfaces of its layers into that memory, and `vsync` is a timer.

几何信息从 boot 交接来：`:36` `extern struct vc_info vinfo`，`:411-413` 把 `vinfo.v_baseaddr`、`v_width`、`v_height` 取成 `fBase`、`fPanelWidth`、`fPanelHeight`。`struct vc_info`（`osfmk/console/video_console.h:87-102`）的字段是 height、width、depth、rowbytes、baseaddr、type、name、physaddr、rows、columns、rowscanbytes、scale、rotate、reserved，**没有速率或时序字段**，所以交接本身给不出面板刷新率。

驱动自己报的几何：round C 日志里 `MiniIOMobileFramebuffer: display 1125x2436 on a panel of 1156x2510 (4624 bytes per row)`。1125×2436 是渲染尺寸（`fWidth`／`fHeight`，`:415-422`，可由启动参数 `fbwidth`／`fbheight` 覆盖），1156×2510 是面板尺寸，4624÷4=1156 说明每像素 4 字节。渲染尺寸到面板尺寸要做缩放，`fb_filter=1`（默认，`:144`）是双线性、`0` 是最近邻，`fb_threads` 决定几个处理器一起缩（`:152`，默认 3，roundb 与 round C 都用 `fb_threads=2`）。

树里没有显示控制器驱动：在 `bsd/` 与 `iokit/` 下按 dsi／dpu／sde／mdss／panel 找文件名，没有命中。`:248-249` 还写明面板的扫描位置谁都读不到，因为显示块的寄存器时钟是关的。

**面板的时序在 Android 的 DTBO 里。** `annibale-backup/20261022-2355/dtbo_a.img`（Qualcomm dtbo 头 magic `0xd7b7ab1e`、1 个条目、505,848 字节在偏移 64；用 `dtc -I dtb -O dts` 解出 20,315 行）里这块面板是：

```
qcom,mdss-dsi-panel-name = "xiaomi p11 42 0d 0a cmd mode dsc dsi panel"
qcom,mdss-dsi-panel-physical-type = "oled"       qcom,mdss-dsi-panel-type = "dsi_cmd_mode"
qcom,mdss-dsi-bpp = <0x1e>                       qcom,mdss-dsi-traffic-mode = "burst_mode"
qcom,dsi-ctrl-num = <0x00>   qcom,dsi-phy-num = <0x00>   lane 0..3 全部启用
timing@0  1156x2510  帧率 0x78=120  vfp/vbp/vpw=64/64/32  hfp/hbp/hpw=64/64/32  clockrate 0x47d2d740=1205 MHz
timing@1  1156x2510  帧率 0x5a=90   porch 与 clockrate 与 timing@0 相同
timing@2  1156x2510  帧率 0x3c=60   porch 与 clockrate 与 timing@0 相同
```

复现方式：从镜像偏移 64 读 505,848 字节写成一个 `.dtb`（前 4 字节是 `d00dfeed`），再 `dtc -I dtb -O dts -f`。

1156×2510 与驱动日志里的面板尺寸一致，所以 DTBO 里这块面板就是我们写像素的那块。三档时序的 porch 与 DSI 时钟完全相同、只有 `panel-framerate` 不同，这与命令模式面板的行为一致：面板有自己的帧内存，按自己的速率刷新，宿主只在有更新时送像素。这一块面板节点里没有找到 `qcom,mdss-dsi-pan-enable-dynamic-fps` 与 `qcom,dsi-supported-dfps-list`，DTBO 里那些属性属于别的面板变体。

所以「刷新率、时序、vsync 来源是从哪里定的」的答案分两半：**面板时序从 Android 侧继承，写死在 DTBO 的面板节点里，我们的代码既不读也不写**；**我们这一侧的 vsync 是一个软件定时器**，周期由启动参数决定（§3）。

## 3. 16.67 ms 这个下界是谁定的：我们的软件定时器

`refreshHz()`（`:178-181`）返回 `gRefreshHz`，越界回落到 `kFBRefreshHz`，接受范围 1 到 240。`gRefreshHz` 是 `:145` 的 `TUNABLE(uint32_t, gRefreshHz, "fb_hz", kFBRefreshHz)`，默认值 `kFBRefreshHz` 在 `:74` 是 60。

它有四个用处：

| 位置 | 作用 | 本轮是否生效 |
|---|---|---|
| `:916` | `show()` 里的节拍周期，`:930` `clock_delay_until(next)` 按它决定何时把画完的帧拷进面板内存 | 生效，round C 每帧实测等 6696–7138 µs |
| `:831` | `period * 5/4`，只作为「这次交换比上次晚了一个刷新以上」这个统计的阈值（`:841` `fStatSwapsLate`） | 只影响一个计数 |
| `:1205` | `armVSync()`，给注册了选择器 72 的客户端发 vsync 通知的定时器 | 从未 arm：72 两轮都没被调过（§4） |
| `:338` | `rate = refreshHz() << 16`，写进 `:355-360` 的 `SyncRate`／`PreciseSyncRate`，由 `:370-371` 作为 `TimingElements`／`ColorElements` 属性发布 | 生效，这是用户态读到的速率 |

节拍的实现（`:913-935`）：`aim = period * 3/8`（60 Hz 下 6.25 ms），`next` 从 `fBeat + period` 递推，再按早迟误差的八分之一收敛到 aim，然后 `clock_delay_until(next)` 睡到那个绝对时刻。这是内核定时器等待，不是忙等也不是 fence。帧来得比一个半周期还晚时不等，直接上屏并重置节拍（`:920-921`）。

`fb_hz` 改的是这四处，**不改面板扫描率**。若面板停在 60 Hz 而我们以 120 Hz 写，结果是约一半的帧从没被显示，并可能撕裂；日志里看不出来，帧号照常递增、`tl: v` 照常打、截图照常。

perf 核过 **73 份 `manifest.json` 全文里 `fb_hz=` 零命中、63 轮的 `commands.jsonl` 也零命中**，所以已归档的每一轮都跑默认 60，没有任何一轮请求过 8.33 ms 的周期。`tools/k90auto/summary.py:205` 的 keep 列表里本来就含 `fb_hz`，工具一侧准备着从没用过。

数据侧的判据结果（perf，口径见 §8）：63 轮、218,285 个相邻帧号间隔里，落在 8.33 ms ±0.5 ms 的是 **0 个**；按 `n = round(间隔 / 8.3333 ms)` 分档，偶数 n 占 96.07%（n=2 即 16.67 ms 单独占 78.91%），奇数 n 占 3.93% 且集中在 25.0 与 41.67 这些较大的奇数倍上；全部 63 轮里最小的单个间隔是 9.56 ms。

这个分布是代码本来就会产生的结果，因为 `tl: v` 的 `shown` 字段是节拍到来的时刻：`ready` 在 `:912` 取（GPU 等待结束之后），`began` 在 `:934` 重新赋值（节拍等待结束之后），`shown = began` 在 `:937`，`drawn`（打成 `done`）在 `:1010`。所以相邻 `shown` 之差量的是软件节拍的节奏，出现小于 16.67 ms 的间隔不需要面板跑 120 Hz。n=1 那一档的 51 个样本实际值在 9.56 到 12.4 ms，与 `:920-921` 那条「晚到的帧直接上屏并重置节拍」的分支相容；具体是哪一条路径产生的没有逐帧追。

## 4. iOS 26 用户态会不会请求 120 Hz：问了，我们的回答把它封住了

驱动对每个选择器的前若干次调用会打追踪行，开关是 `:106` 的 `TUNABLE(uint32_t, gFBTrace, "fbtrace", 3)`，打印在 `:1255-1265`，带调用方进程名、pid、标量与结构体尺寸，**已实现的选择器也打**。未实现的另有一条 `selector N not implemented`，由 `:1385-1387` 的 `gFBLogged` 位图限制成每个选择器每次启动一条。选择器枚举定义在同一个 `.cpp` 的 `:49-70`（不在头文件，20 个名字），case 表是同文件 `IOMobileFramebufferUserClient::externalMethod` 的 `:1248-1400`（20 个名字里 16 个有 case）。

口径：覆盖 round C 与 roundb 各自的 `run/*.log` 全部 24 个文件（`s000.log` 到 `s020.log`、`hung-held.log`、`hung-held-serial.log`、`system-upload.log`）。两轮的调用方都只有两个：`backboardd[38]` 调 23 个号（3 4 5 6 8 12 15 17 18 22 25 27 29 33 50 57 68 74 78 79 84 86 88），`MobileGestaltHelper[57]` 调 2 个（8 28）。两轮的号集与形状完全相同。未实现的 raw 行数是 round C 297 条、roundb 300 条，唯一号都是 15 个；raw 计数被快照重叠放大（同一条行出现在 24 个文件里的 21 个），不表示被调了 21 次。

三条决定性的：

1. **backboardd 调了 74 `kFBMethodSupportedFrameInfo`**，形状是 1 个标量入、2 个标量出、64 字节结构出。我们的实现 `:1350-1358` 把 `out[0]` 置 0、`scalarOutputCount` 改成 1、结构体 bzero，也就是**告诉窗口服务器支持的帧信息一个都没有**。这是设备日志直接来的。
2. **73 `kFBMethodChangeFrameInfo` 两轮都没被调过。** 我们的实现在 `:1333-1334`，与另外四个选择器共用一个 `return kIOReturnSuccess`，什么都不做。形状合起来是「用户态问了我们支持什么，我们答零个，于是它从来没来改过」。
3. **72 `kFBMethodNotifications` 两轮都没被调过**，把 `:247-248` 那句注释（CoreAnimation 从不请求本驱动的刷新通知，它按自己从这里读到的速率走自己的钟）从注释变成实测。这一条排除了一个候选解释：CA 不靠我们的刷新通知，它的钟来自 `:338` 发布的模式速率。

一个未实现的选择器值得单独记，但不给它命名：**78** 被调了三次，两个形状是 5 个标量 `[0x32 0x0 0x1 0x4]` 与 `[0x32 0x0 0x1 0x5]` 各带 64 字节结构入，第三个是 6 个标量 `[0x33 0x0 0x1 0xc]` 带 656 字节结构入；64 字节正好是 74 输出的结构体大小；三次调用落在 SwapBegin（选择器 4）与 SwapEnd（选择器 5）之间。78 在枚举里没有名字，我们的枚举来自 iOS 16.5 的用户态侧（`:9-10`、`:48`），而 rootfs 是 iOS 26，所以命名需要 iOS 26 的选择器表，形状吻合不构成命名依据。

15 个未实现的号里，三个对到枚举名且都与显示有关：25 `kFBMethodGetDigitalOutState`（`:58`）、29 `kFBMethodGetDisplayArea`（`:60`）、57 `kFBMethodGetColorRemapMode`（`:62`），三个都在枚举里有名字但没有 case。第四个有名字无 case 的是 82 `kFBMethodGetProtectionOptions`（`:69`），两轮都没被调过。其余 12 个号（15、17、18、22、27、33、50、68、78、84、86、88）在枚举里没有名字，原样报号。其中 50 的标量是 `[0x10000 0x0]`，0x10000 在我们自己报速率用的 16.16 定点里等于 1.0；27 与 17 是一对 3084 字节结构的出与入。这两条只是形状记录。

调用顺序（round C 的 `s001.log` 按出现序）：88 57 18 15 22 8 29 33 79(2056 出) 79(3164 出) **74(64 出)** 25 12 79(44 出) 6 27(3084 出) 17(3084 入) 84 50 4(SwapBegin) **78(656 入) 78(64 入) 78(64 入)** 68 5(SwapEnd) 3。

我们自己那几个用户态库（`userland/src/redwoodmetal.m`、`redwooddrawable.m`、`sb_metal_experiment.m` 与 `redwoodmetal_*.inc`）里 display link 与 frame rate 相关的实现是零命中：按 `DisplayLink`、`displayLink`、`FrameRate`、`frameRate`、`CAFrameRateRange`、`preferredFrameRate`、`maximumFrameRate`、`refreshRate` 搜过。CADisplayLink 与 `CAFrameRateRange` 由共享缓存里 Apple 的 QuartzCore 提供，它们要了解显示能力只能通过 IOMobileFramebuffer，也就是上面这条 74／78 的路径。

一个观测上限：`fbtrace` 默认 3，所以每个选择器只记前 3 次，**调用频次从现有日志测不出来**，78 是不是每帧一次判不了。调大 `fbtrace` 是启动参数、不重建，代价是行数（23 个号各 N 行）。

## 5. 每帧成本的账与达到 120 Hz 要动什么

这一节是两份独立测量的合成表。

- 内核侧：`tl: v <id> ready <R> shown <S> done <D>` 原始时间戳（round C 的 `s020.log`，1861 个唯一帧号、1859 对相邻帧号）。
- AIR 库插桩的窗口汇总：perf，27 条稳态窗口，字段定义与口径见 [roundb 绘制阶段拆解](2026-10-28-roundb-draw-stage-breakdown.md) §8.5，合成过程见 §8.7。
- 两份的端点取在不同地方：内核那份取在驱动的节拍上，插桩那份取在 backboardd 的调用线程上（窗口是 128 次 `fd_context_flush` 进入，两个端点都是这个进入点）。
- 这里没有 Gallium worker 线程：`air_metal.c:320` 是 `context_create(device->screen, NULL, 0)`，而 `freedreno_context.c:773-774` 的 `if (!(flags & PIPE_CONTEXT_PREFER_THREADED)) return pctx;` 让 `threaded_context_create` 一次也没有被调到，所以 `pipe` 是裸 `fd_context`，全部工作在调用线程上同步执行。

| 区间 | 由谁的时间戳界定 | 值 | 哪一份测量覆盖 | 没覆盖的部分 |
|---|---|---|---|---|
| 一帧的周期 | 相邻 `shown` 之差 | 16.64 ms，p95 17.13 | 内核 `tl: v` | — |
| 同一区间，第二个基 | backboardd 驱动线程相邻两次 flush 进入 | 16.61 ms（perf 的区间是 16.61 到 17.03） | AIR 插桩 | `fd_perf_close` 在没有 draw 时提前返回、不计帧也不更新窗口起点，所以 128 帧是 128 次「至少有一次 draw 的关闭」，间隔里可以含任意多次空关闭的时间 |
| 同一区间，第三个基 | 内核窗口统计行的 ms ÷ frames | 16.60 到 16.63 ms（5002 到 5012 ms ÷ 301 到 302 帧） | 内核统计行 | 5 秒窗口的平均值 |
| 生产链 | 上一帧 `shown` 到本帧 `ready` | 9.40 ms，p95 11.04 | 内核 `tl: v` | 里面 CA 的渲染工作没有任何读数 |
| 节拍等待，相减得出 | 本帧 `ready` 到本帧 `shown` | 7.24 ms（16.64 减 9.40） | 内核 `tl: v`，1859 对相邻帧的中位数 | 与下一行是同一段的两种取样，差 0.16 到 0.24 ms |
| 节拍等待，直接读出 | 内核窗口统计行 `for the next refresh` 那一段，按等待帧数加权 | round C 7080 µs，round D 7068 µs，roundb 11133 µs（只覆盖 36 帧） | `summary.py`（perf，提交 `26c157b`）；内核逐窗口报的 round C 九个窗口是 6696 到 7138 µs，7080 落在其中 | 加权方式是 `sum(on_beat × beat_us) / sum(on_beat)`，是窗口内平均 |
| 驱动拷像素 | 本帧 `shown` 到本帧 `done` | 1.77 ms，p95 3.22 | 内核 `tl: v`；统计行的 `in the driver` 1924 到 2033 µs 是同一段 | 它在 `shown` 之后、落在下一帧的生产链区间里，与 backboardd 的工作并行，所以不进插桩窗口的和 |
| GPU 完成等待 | `MiniIOSurfaceDrawn` 那一段（`:906`） | 41 到 42 µs | 内核统计行 `waiting for the GPU` | 上限 `SWAP_GPU_MS` 500 ms（`:78`） |
| AIR 记账 `driver` | 一帧里所有 draw 从 `entry` 到 `exit` | 2 单位 = 0.104 ms | AIR 插桩 | 四个有名阶段是它的子段，所以 `own` 不能与 `driver` 相加 |
| AIR 记账 `submit` | 一次 flush 里 `fd_perf_close` 之后到 `out:`，含提交 ioctl 与等 batch 空间 | 19 到 25 单位 = 0.99 到 1.30 ms | AIR 插桩 | — |
| AIR 记账 `client`／`sync`／`pass` | 客户端 draw 排队、`tc_sync_msg`、`pipe->flush` | 无读数 | 两边都没有覆盖 | 打出 0 的原因是代码没走到：`pass` 夹住的 `pipe->flush` 就是 `fd_context_flush`，而同一个窗口里 `submit` 是 0.99 到 1.30 ms 且整个落在 `pass` 里面，`pass` 不可能比它小，所以 `tc_flush` 这条路没走到，`sync` 与 `client` 随之没走到 |
| CA 一侧（渲染加它自己的等待） | 生产链减去 GPU 等待减去 AIR 记账 | 8.24 ms（内核基）／8.01 ms（`tl: v` 基） | 无 | 全部无读数，这是 round E 要分辨的对象 |
| 无记账段合计 | 一帧周期减去 AIR 记账 | 15.26 ms（16.61 减 1.35） | AIR 插桩 | 按墙上时间它含节拍等待 6.99 ms；那一段的成本由内核辅助线程付，不阻塞 backboardd |

两个基各自闭合。内核基：15.26 对 6.99 加 8.24 = 15.23，差 0.03 ms 即 0.2%。`tl: v` 基：7.24 加 (9.40 − 0.04 − 1.35 = 8.01) = 15.25，与 15.26 差 0.01 ms。8.01 与 8.24 相差 0.23 ms，来源是取样方式不同（1859 对相邻帧的中位数对 5 秒窗口的平均值），原样记下，没有为了闭合调数。

单位与前提写在表外以免误读：插桩的一个单位是 52.08 µs（`mach_absolute_time() / 1000`，换算因子 625/12，时基 19.2 MHz），所以表里 `driver` 与 `submit` 的单位值要乘这个因子；`batch submit` 那一列用的是另一个钟（`fd_perf_clock_us()`，真微秒）而且是文件作用域的累计量、窗口的 `memset` 不清它，28 条窗口里只有第一条是该窗口的值，量级上 28 个窗口累计 19 微秒，所以它不进这张表。roundb 与 round C 的 AIR 库都带 draw-perf 插桩，插桩让间隔变长，阶段之间的相对比例可用，绝对耗时不能与无插桩轮次直接比。

驱动自己的每五秒统计行原文（round C 九个窗口之一）：`298 frames in 5011 ms (59 a second), 1933 us each in the driver, after 41 us waiting for the GPU and, 297 of them, 7025 us for the next refresh; 0 swaps waited for the frame before, 0 gave up; 1 swaps came a refresh late themselves`。九个窗口里六个是 60 fps，另外三个是 23、24、13 fps；静止屏幕重绘少，统计行分不清「生产者慢」与「屏幕没变化」，所以每帧成本只从 60 fps 那六个窗口取。`done − shown` 的中位数 1.77 ms 与 perf 独立算出的偏移（6 个大轮次、53,247 帧：min 0.269、median 1.766、p95 3.280、max 4.084 ms）一致。

**驱动没有让 CA 等过**，三条都排除了：选择器 6 `kFBMethodSwapWait` 立即返回（`:1323-1328`，只在 `touch_lat=1` 时打一行 `tl: w`）；`present()`（SwapEnd，`:824-845`）只在交换队列满时用 `IOLockSleepDeadline` 阻塞调用方（队列深度 `fb_queue` 默认 2，`:154-158`；期限 `SWAP_HELD_MS` 700 ms，`:79`、`:833`），而队列从没满过；GPU 完成等待每帧 41 到 42 µs。第二条现在有两路读数，人工核日志之外多了工具输出：`summary.py --verify` 的 `swap queue` 那行三轮都是 0（提交 `26c157b`）：

```
roundb  driver_us=0     beat_us=-     onbeat=-
        swap queue: over 13 window(s), 0 swaps waited for the frame before, 0 gave up, 47 came a refresh late themselves; 36 frames waited for the next refresh, 11133 us each
roundc  driver_us=1928  beat_us=7080  onbeat=100%
        swap queue: over 16 window(s), 0 swaps waited for the frame before, 0 gave up, 4 came a refresh late themselves; 3593 frames waited for the next refresh, 7080 us each
roundd  driver_us=1992  beat_us=7068  onbeat=100%
        swap queue: over 16 window(s), 0 swaps waited for the frame before, 0 gave up, 4 came a refresh late themselves; 3604 frames waited for the next refresh, 7068 us each
```

所以 CA 一侧那 8.24 ms 里没有等我们的成分。`came a refresh late themselves` 三轮分别是 47、4、4：roundb 高一个量级，与它 13 个窗口只有稀疏帧数一致，配合 roundb 的 11133 µs 接近一整个周期，这给了形态区分一个维度，循环形态里帧到得晚于节拍，冻结形态里帧准时到而节拍之后就没有帧了。这一维的判读归[采样覆盖那份记录](../progress/2026-10-28-kernel-badaccess-region.md) §8。

节拍等待这一段有两个启动参数可以动：`fb_hz` 改周期，`fb_beat=0`（`:146`，默认 1，总开关在 `:913`）直接不等。`aim = period * 3 / 8`（`:917`）是目标位置，60 Hz 下 6.25 ms，与实测的 6.7 到 7.1 ms 相符。`:918-921` 还有一条晚帧分支：迟到超过 1.5 个周期的帧不等节拍、立即上屏，且不计入 `fStatOnBeat`；round C 的 16 个窗口里「等节拍的帧数」与「帧数」最多差 3（一个窗口 244 帧 239 等，另一个 109 帧 106 等），所以这条分支很少走到。周期缩短到 8.33 ms 之后 `period * 3 / 2` 这个门槛也缩短，走立即上屏分支的帧会变多，判撕裂时要带上这一条。

perf 早先按「只有节拍等待随周期缩放」算过一个约 104 fps 的上限（一帧 16.61 ms 里随周期缩放的是 6.99 ms，剩下 9.63 ms 不缩放，120 Hz 的槽是 8.333 ms，超出 1.30 ms 即 15.6%）。那个算法把帧周期当成连续量，round E 之后作废，换成量化式：`:923-924` 的 `for (next = fBeat + period; next < began; next += period)` 把上屏时刻吸附到节拍网格上，所以帧周期是 `ceil(非节拍时间 / 周期) × 周期`，一个整数量（[读数规则](2026-10-28-roundc-reading-criteria.md) §14.15）。非节拍时间约 9.6 ms 时，60 Hz 与 120 Hz 的帧周期都是两个槽即 16.67 ms，把刷新率翻倍的收益是 0；要拿到收益，非节拍时间得先降到 8.33 ms 以下。

### 5.1 round E 的结果：节拍变成 8.33 ms，帧周期没有变

round E 跑了，唯一变量是 `fb_hz=120`，驱动与 AIR 的哈希与 round C、D 相同。`summary.py` 的 `args` 列第一次非空，读出 `cpus=2 gpu_log=1 cpufreq=1 fb_threads=2 fb_hz=120`，所以 `:205` 那个保留表条目按设计生效，`refreshHz()` 返回了 120。读数与判据的完整版在 [roundb 绘制阶段拆解](2026-10-28-roundb-draw-stage-breakdown.md) §8.11，本文只记结论与它对顺序的影响。

**读数边界：这一轮没有一段长的健康 120 Hz 渲染。** 帧号 1 到 91、唯一 78、8 处断裂对应 8 次重起，形态翻转进 roundb 家族（bad access raw 243、唯一 14 行，15 代 backboardd `died on signal 11`，渲染段从 rel 18.5 s 起被崩溃循环打断，96 张截图全落在黑屏档，`ff_s=150`，`crashes=29`），17.77 s 后 hung-held。下面那些间隔来自 9 个进程世代各自的开头几帧，样本小，够定节拍周期与帧周期这两件事，不够定分布。

69 个相邻帧号的 `shown` 间隔按节拍倍数分三组，全部落在整数节拍上：

| 组 | 个数 | 区间 | 均值 | 节拍倍数 |
|---|---|---|---|---|
| 一个节拍 | 8 | 7.67 到 9.21 ms | 8.16 ms | 0.98 |
| 两个节拍 | 16 | 15.01 到 21.90 ms（其中 13 个挤在 16.29 到 17.04） | 16.98 ms | 2.04 |
| 四到六个节拍 | 41 | — | 41.62 ms | 4.99 |

第一组证明节拍周期确实变成了 8.333 ms：round C 的 3606 个间隔最小值是 14.72 ms，16.67 ms 的节拍下出现不了 7.67 ms。第二组证明帧周期没有变：round C 的健康中位数是 16.640 ms，round E 的 16.98 ms 在这个样本量之内与它没有差别。

**成立的是「那 8.24 ms 是 CA 的渲染工作」这一支**：它不随刷新率缩放，超过一个 8.333 ms 的槽，每一帧错过一个节拍落到下一个上，帧周期量化成两个槽。把刷新率翻倍只把网格加密，没有把帧挪近。另一支（那 8.24 ms 里有一部分是 CA 按模式速率的等待）被这三组数排除：若有那样的成分，间隔会落到一个节拍那一组里去，而两个节拍那一组有 16 个。

`beat_us` 的预测错了，错因与量化是同一件事。§5 那条按 `aim = period * 3 / 8` 预测它降到约 3125 µs，实测 6385 到 7562 µs，与 round C 的 6696 到 7138 基本相同。`aim` 只是 `:925-929` 那个 1/8 步长逼近的目标，而 `:923-924` 先把 `next` 推到第一个不早于 `began` 的节拍上：CA 的工作约 9.6 ms 时，`began` 已经过了第一个节拍、还没到第二个，`next` 就是第二个节拍，等待是 16.67 减 9.6 约 7.07 ms。等待时间由工作什么时候做完决定，`aim` 只在连续多帧都走到这条分支时才收敛得到，而 round E 每个窗口只有 1 到 4 帧等节拍。

**task-22 的主要失败指标没有触发**：8 个窗口的 `swaps waited for the frame before` 与 `gave up` 全是 0，`fb_hz=120` 没有引入交换队列阻塞。`came a refresh late themselves` 是 44 帧对 68 帧（round C 是 4 对 3611），与 `:918-921` 的门槛从 25 ms 缩到 12.5 ms 一致，走立即上屏分支的帧变多。`onbeat` 在 summary 行是 `-`，8 个窗口里最大的一个 25 帧但只有 2 a second，都不满足 `busy` 门槛，与 roundb 同。`driver_us` 是 1256 到 1635 µs，round C 是 1827 到 2033，两轮的窗口帧数差两个量级，这个差本文不解释。

我的判据与 device 的分档并列记在这里。我用的判据是「有间隔低于 perf 那 63 轮 60 Hz 的最小值 9.56 ms」，round E 有 8 个（rel 16.2 的 7.67、8.42、9.21，rel 39.3 的 7.86，rel 70.0 的 7.85，rel 91.0 的 7.84，rel 122.0 的 7.87，rel 182.8 的 8.58）；device 用的是分档。两条给出同一个答案，我的那条更紧，因为它不依赖档宽。

由此 120 Hz 路线的顺序改了：**先量 CA 一侧那 8.24 ms 并把它降到 8.33 ms 以下，再谈刷新率。** 那 8.24 ms 现在没有任何读数，在那之前谈「降哪一块」没有依据。驱动拷像素的 1.77 ms（p95 3.22 ms）在 8.33 ms 的槽里已经放得下，节拍等待由 `fb_hz` 决定，两项都不挡路。

## 6. 面板侧的读数缺口与 TE 那条路

我们内核运行时面板在哪一档，现在无从知道：寄存器时钟关着（`:248-249`），boot 交接不带速率（§2），DTBO 只说明支持哪些档。

命令模式的面板自己发 TE（tearing effect）信号，**TE 由面板产生，不依赖 SoC 显示块的寄存器时钟**，所以那条「读不到」的限制不构成障碍。DTBO 里：

```
qcom,platform-te-gpio = <&tlmm>, <0x56 0x00>;        → TLMM 引脚 0x56 = 86
pinctrl-2 = <&sde_dsi_suspend>, <&sde_te_suspend>, <&sde_esync0_suspend>;
面板节点内  qcom,mdss-dsi-te-using-te-pin;  te-dcs-command = <0x01>;  te-pin-select = <0x01>;
```

我们的内核已经在用 TLMM：`bsd/dev/redwood_goodix.c:509` 的 `tlmm_phys = 0x0f100000UL; tlmm_size = 0x102000UL;`（注释写着 vendor TLMM base + 0x100000，见 sm8750.dtsi）与 `:543` 的 `tlmm = ml_io_map(TLMM_PHYS, TLMM_SIZE);`。所以数 TE 脚的翻转频率在现有能力范围内，是一条纯软件的面板实际刷新率读数。

分两步，第一步只读：

1. 只读采样：按 1 kHz 左右读 86 号脚的输入状态位，数一秒内的翻转次数，60 Hz 与 120 Hz 差一倍，不改任何配置。这是内核改动（新文件或现有 `redwood_*.c` 里加一段，加一个启动参数控制），按一轮只改一个变量的规矩，不能与 `fb_hz=120` 同一轮上。
2. 若第 1 步读不到翻转，才考虑把该脚的 mux 改成 GPIO 输入。`te-pin-select = <0x01>` 表示 Android 把 TE 路由给了 DSI 控制器的硬件 TE 输入，脚当前可能不在 GPIO 功能上；改 mux 有可能干扰正在扫描我们 framebuffer 的那条显示流水线。Qualcomm TLMM 的输入状态位在脚被 mux 到非 GPIO 功能时通常仍反映 pad 电平，这一条未实测。第 2 步要单独一轮，且要先记下原配置以便恢复。

设备侧读数清单（面板模式，供下一轮带上）：从 Android 侧读这块面板的可选模式与当前模式（`/sys/class/drm/card*-DSI-*/modes`、同目录的 `status`、`dumpsys SurfaceFlinger` 里的 refresh rate），目的是确认 120 Hz 档在 Android 下确实被选用过、Android 平时跑哪一档；这一条给不出 boot loader 交接给我们时是哪一档。从设备外部观测的方案（相机长曝光拍滚动条纹，或光电二极管贴屏数闪烁）在 TE 读不到时替代 TE，代价是要人参与与一个测试图案。

## 7. TE 只读采样器的实现方案（方案，未动手）

这一节是 §6 那条第一步的方案，lead 已批范围：只读，不改引脚配置。方案先给，动手前再报一次。

**落点。** 新文件 `bsd/dev/redwood_te.c`，在 `bsd/conf/files` 的 redwood 那一段（`:111-122`）里加一行。不放进 `iokit/Kernel/MiniIOMobileFramebuffer.cpp`：那个文件已经 1616 行，而 AGENTS.md §2 对新落地文件与大改文件的上限是 1200 行。

**寄存器访问。** 四条事实复制到新文件里，注释写明出处，不去包含那个私有头：

- TLMM 物理基址 `0x0f100000`、窗口 `0x102000`（`bsd/dev/redwood_goodix.c:509`，annibale 那一支），用 `ml_io_map` 映射（同文件 `:543`）。
- `GPIO_CFG(n) = tlmm + 0x1000 * n`，位段是 [1:0] pull、[5:2] function、[8:6] drive、[9] output。
- `GPIO_IO(n) = tlmm + 0x1000 * n + 4`，bit 0 是输入、bit 1 是输出（两条都在 `bsd/dev/redwood_touch_bus_private.h:48-49`）；读法是 `rd(GPIO_IO(pin)) & 1`（同文件 `:78-82`）。
- 不包含 `redwood_touch_bus_private.h` 的理由：它 616 行，当前只有 `redwood_goodix.c` 包含，里面还有 RPMh 与 SPI 的一批 static，这个文件用不到。
- TE 脚是 86（`0x56`），`GPIO_IO(86)` 落在 tlmm + 0x56004，在 0x102000 窗口内。

**采样在哪个上下文跑。** 一个专用内核线程，只在 boot-arg 存在时用 `kernel_thread_start` 起（沿用 `redwood_goodix.c:622` 与 `redwood_buttons.c:560` 的做法），睡到指定的那一秒，跑一次有界的突发采样，打一行，然后 `thread_terminate(current_thread())`（退出形状同 `redwood_goodix.c:551-559`）。线程的总寿命是「指定的秒 + 突发长度」，其中绝大部分在睡，所以不会占住一个内核线程一秒。

**突发而不是轮询。** 命令模式下 TE 是每个刷新一次脉冲，脉冲宽度在 DTBO 里没有记。按固定间隔轮询（例如每 500 µs 读一次）会漏掉大部分脉冲，读数会低到无法解释。所以采样是连着读：在一段有界的墙上时间里反复 `rd(GPIO_IO(86)) & 1`，只在电平发生翻转时取一次 `mach_absolute_time()`，所以取时间戳的开销付十几次，不是每个样本一次。默认窗口 20 ms，占一个核 20 ms，一轮一次。

**结果怎么报。** 一行汇总，不逐秒打。格式串（落地后按惯例原文报给 lead、device、perf，供读数规则文档引用）：

```
redwood: te pin %u cfg %#x level %u, %u samples in %llu us, %u edges, shortest gap %llu us, longest %llu us
```

各字段的用途：`cfg` 是突发之前读一次的 `GPIO_CFG(86)`，用来判断这个脚当前在不在 GPIO 功能上（function 位段是 [5:2]），读不到翻转时靠它区分原因；`level` 是突发前的电平；`samples` 与 `in ... us` 给出实际采样密度，用来核对有没有漏脉冲；`edges` 除窗口长度得频率，但要先定 TE 是每个周期一个脉冲还是两次翻转，`shortest gap` 就是判据：几 µs 量级说明是窄脉冲，约 4.2 ms 说明是 120 Hz 的半周期翻转，约 8.3 ms 说明是 60 Hz。

**启动参数名。** `te_probe=<第几秒>`，缺省或 0 表示不启用；`te_probe_ms=<窗口毫秒>`，默认 20，夹在 1 到 200。命名沿用现有的 `fb_hz`、`fb_beat`、`fb_threads`、`touch_poll_us`、`touch_lat` 那一路。脚号不做成参数：86 来自 DTBO，是这台机器的事实，写在注释里。

**对日志环的压力。** 启用时一轮一行，约 100 字节；不启用时零行。按 §6 与环的实测模型（约 256 KB 固定头加约 1 MB 滚动环，环的内容速率 2.88 KB/s），100 字节约合 0.03 秒日志，与 dump 块（一个名字 1,436 字节）比可以忽略。

**构建与记录。** 宿主机 `cd hackios-xnu-kernel && XNU26_SRC=out/xnu12377 xnu26/build-macos.sh -j10 BUILD_DSYM=0`；产出更新 `docs/progress/evidence/k90auto/kernel-12377-attr26/kernel.json` 的 `record` 与 `new_prints` 两段；报新内核的字节数与 sha256，以及格式串原文。

**读不到翻转怎么读。** `edges` 为 0 而 `cfg` 有值时，这一行区分不了「面板没在发 TE」与「脚被 mux 到别的功能上所以 pad 电平在输入状态位里看不见」，两种都要报，不要选一种写成结论。第二种才触发 §6 的第二步（改 mux），那一步单独一轮，先记下原配置再改，并且要有画面没了之后的恢复手段。

**第一步明确不做的事。** 不写 `GPIO_CFG(86)`，不改 mux，不改面板时序，不动 `fb_hz`。按一轮只改一个变量，这一轮不能与 `fb_hz=120` 同轮。

**落地步骤（lead 定的四条）。** 新文件要写两处：先写 `xnu/files/bsd/dev/redwood_te.c`，再手工拷到 `out/xnu12377/bsd/dev/redwood_te.c`，因为 `xnu26/apply.sh:19` 的守卫不会重铺一棵已存在的树。注册行也要写两处：构建树的 `bsd/conf/files:111-122`，以及 `xnu26/patches/04-bsd%conf%files.patch`（在那两行 redwood 注册附近）。构建之前对每个动过的文件跑一次 `cmp`，确认两侧逐位相同。两个仓库在同一阶段各提交一笔。手工拷这一步改的是构建树，所以这一轮排在 round F 之后。

## 8. 采集条件与单位口径

引这一层的数要带三个口径。

**插桩造成的不对称。** roundb 与 round C 的 AIR 库都带 draw-perf 插桩，插桩让间隔变长、不会变短。在 round E 之前，数据侧能给到的只是「63 轮里没有 8.33 ms 样本」，而看不到不能排除关掉插桩后能看到。round E 之后这一条要改两处：一是它有了 8 个低于 9.56 ms 的间隔，二是**这样的间隔证明的是我们的节拍，与面板扫了多少次无关**，因为 `shown` 这个时间戳由 `:913-937` 的软件节拍产生（§3），面板侧没有任何读数进这一行。所以「有没有 8.33 ms 样本」这个问题只能答合成器一侧，答不了面板一侧，要答面板得用 §6 的 TE 读数或设备外部观测。与之独立的一条理由仍然成立：round E 之前没有任何一轮设过 `fb_hz`，vsync 周期是 `NSEC_PER_SEC / refreshHz()`，所以那些轮里没有任何一轮请求过 8.33 ms 的周期。

**插桩的单位。** 插桩打的 `us` 值与内核 `tl:` 的微秒差 625/12 = 52.0833 倍，来源是 19.2 MHz 的时基（`numer=625`、`denom=12`），所以插桩的数乘 625/12 才是微秒，`FD_PERF_SLOW_US 6000` 的真实阈值是 312.5 毫秒。perf 给本文的稳态 16.61 ms 与 2.34 ms 已经是换算后的真实时间，与本文用 `tl: v` 独立算出的 16.64 ms 对上；引 task-16 的其它绝对数值时要带这条换算，相对比例不受影响。

**帧数的三个口径。** `gestures.py` 与直接数唯一 `tl: v` 行是一个值；`summary.py --verify` 的 `frames` 是另一个（它数 `tl: v N ready X shown` 正则的匹配）；`coverage:` 行是第三个（只数落在覆盖跨度内、带 `shown` 时间戳的）。三个值不构成矛盾。本文用的是唯一帧号：round C 的 `s020.log` 里 1861 个，而全轮的帧号是 1..3611，差额是被日志缓冲挤掉的部分。

**帧间隔取的是哪个字段。** 本文取 `shown`。`tools/k90auto/gestures.py:48-50` 的正则是 `tl: v (\d+) ready (\d+) shown (\d+) done (\d+)`，而 `shown.append(int(m.group(4)))` 取的是第四组 `done`，变量名叫 `shown`。两个字段分布形状相同，逐帧 `done − shown` 的偏移实测（6 个大轮次、53,247 帧）是 min 0.269、median 1.766、p95 3.280、max 4.084 ms，所以「有没有 8.33 ms 样本」这个结论在两个字段下一样，引具体数值时要写清是哪个。

**这批帧率读数是在什么输入下采的。** `gestures.py` 对 round C 的输出是 `swipe-left 1x: no animation to measure, each window held one frame -- a desktop with one page turns nothing, the swipe springs back`，且 0 次控制中心下拉被识别。单页桌面上的滑动不产生连续动画，所以那批帧率读数采到的是系统自发的重绘，不是被驱动的动画。要论证 120 Hz 有没有意义，先要有一个能产生连续动画的输入。

**截图与帧号的时间覆盖。** 截图命名是 shot-NNNNN，NNNNN 是轮内十分之一秒（`tools/k90auto/run-auto.py:34,163,166`，`RUN_TIMING` 的 `shot_from=100` 是设计值），所以 round C 的 101 张截图只覆盖 100.1 到 419.0 s；渲染段 0 到 100.2 s 的「桌面显示出来了」由 3611 个帧号零断裂支撑，没有逐张截图。引这两段时要分开。

## 9. 未验证与下一步

未验证的部分：

1. 我们内核运行时面板实际在哪一档。补法是 §6 的 TE 只读采样，或设备侧从 Android 读模式（后者给不出交接时的档位）。
2. iOS 26 的 CoreAnimation 把速率提到 120 Hz 是否还需要 74 报出条目。round E 给了半个答案：`fb_hz=120` 之后 `tl: v` 的间隔没有掉到 8.33 ms，所以「CA 被 74 的零条目封顶」与「CA 的渲染工作超过一个槽」这两件事在帧率上分不开，两者都成立时读数相同。74 那一侧有一个已查明的机制缺口：我们的实现只写 1 个 scalar 而 26.6 的 framework 请求 2 个，第二个槽位保持 framework 自己栈上的初值 `0xAAAAAAAAAAAAAAAA`，调用方拿到 `0xAAAAAAAA` 当 selected index，count 是 0 时正常路径不用这个值所以目前没出问题（[选择器名字对照](2026-10-28-iomfb-selector-names.md) §5）。这一处与本文 §4 是同一层，两边互引。
3. 选择器 78 是什么。项目 enum 里没有它，而 backboardd 每次 swap 在 SwapBegin(4) 与 SwapEnd(5) 之间调它三次（blockType `0x32`、`0x32`、`0x33`，payload 64、64、656 字节，chunk offset 都是 0，extra u32 是 `{1,4}`、`{1,5}`、`{1,0xc}`），三次都落到 `:1385-1387` 的 not implemented 路径上，而那条打印由 `gFBLogged` 每启动只记一次，所以日志里看不见它每次 swap 都在发生（[选择器名字对照](2026-10-28-iomfb-selector-names.md) §6）。它对 120 Hz 路径有没有用还没有判据，补法是 `fbtrace` 调大之后看它的调用频次与它带的结构体内容是否随速率变化。
4. TLMM 输入状态位在脚被 mux 到硬件 TE 功能时是否仍反映 pad 电平。
5. 面板以 60 Hz 扫描而我们以 120 Hz 写时的可见后果（撕裂还是重复帧）。我们的截图取自帧缓冲内存还是面板侧没有核过，若取自内存则截图看不到这类后果。
6. CA 一侧那 8.24 ms 的内部构成。round E 已经定了它不随刷新率缩放（§5.1），所以它是工作而不是按模式速率的等待，但它里面各段是什么没有任何读数，而它是唯一超过一个 8.333 ms 槽的项。

生产链 9.40 ms 里除 AIR 记账那约 1.35 ms（`driver` 0.104 加 `submit` 0.99 到 1.30）之外的部分，round E 判了它是 CA 的渲染工作。

下一步按 §1 的顺序：第一步给 CA 一侧那 8.24 ms 加时间戳，第二步按第一步的读数决定降哪一块，`fb_hz` 排在这两步之后。§6 的 TE 读数与这两步独立，它回答面板侧的扫描率。
