# annibale 调试案例与方法验证

记录日期：2026-10-23。本文根据 dsh 与 Codex 的本次调试记录整理，保留有助于后续思考的案例和结论边界；通用方法见[项目排查与协作手册](../plan/debugging-and-collaboration.md)，当前命令见[真机调试手册](../plan/device-test-playbook.md)。

本次整理核对到 `handoff-platform.bin`、检查点 68／69、真机 `ios-first/089.log` 中 23:17 的首屏初始化结果，以及用户确认桌面正常后补充的壁纸、半透明和触摸反馈。主会话仍在调试；具体设备状态重新读取。本文按运行目录和文件名定位本地日志，部分已复制到 `docs/progress/evidence/2026-10-23-handoff/`，均按本地产物保存。

## 2. 已解决问题提供的方法

### 按新栈继续定位，验收持续行为

用户反馈通知栏、手势条和动画消失。第一次重建 SystemUI 编译缓存后，窗口短暂出现，随后再次崩溃；新栈指向 MIUIAod 插件，处理该包后界面才持续恢复。一次工具成功或窗口出现只能确认当次动作，验收还需进程持续运行、新崩溃停止和用户实际反馈。完整修复记录见[专门文档](2026-10-23-android-systemui-recovery.md)。

userdata 尾部写入与缓存异常先后发生，但尚未取得具体文件的物理区段对应关系，原因保持未确认。备份晚于首次写入，也限制了可恢复的时间范围。

### 调试工具也受初始化顺序约束

检查点 10 的返回路径曾在 `PE_state.bootArgs` 设置之前调用参数解析。增加前提检查，并在 `bootcpu=1` 条件下复测后，取得检查点返回和后续异常日志。该轮同时改变了启动 CPU，结果只确认修改后的组合可用。

可复用的判断是：检查点失败应同时检查被测功能和诊断返回路径。早期代码使用的锁、CPU 状态、参数和映射都有各自的初始化时机。

### 验证错误之后还能继续

旧 loader 的空上传发送零长度数据，主机拒收后不再读取最终状态，loader 等待未结束。v2 改为直接拒绝空数据。真机验收包含空请求按预期失败、下一条 `getvar product` 成功，以及后续系统盘上传成功。

这一案例要求检查协议错误后的状态，而不能在看到错误码后就结束测试。后续内核运行仍可能出现独立故障，空上传通过后继续分别定位。

### 追踪参数实际经过的路径

GIC 修复涉及 loader 输出的 redistributor 范围、stride，以及内核的校验和扫描；显示修复涉及板级配置、GOP、loader 和内核。沿实际消费关系检查，才能确定哪项配置进入本轮产物。

当前 loader 的屏幕读数已更新，用户随后确认桌面显示正常。内存中的图像、固件上报参数和实际扫描分别提供信息，不能仅凭某一个读数完成显示验收；壁纸和半透明效果继续单独检查。

### 用原始缺陷检验测试是否有效

滚屏函数把已经按字节计算的区间长度再次乘以 4，向下滚动还将高端目标地址直接作为复制起点。主会话提取实际函数，使用保护页、相邻字节比较和重叠复制测试；旧实现异常退出，修复版通过。候选回归脚本为 kernel 工作树中的 `tools/test-video-scroll.py`。

这个测试确认了复制边界修复，后续真机仍有独立退出异常。局部缺陷已经复现并修复后，继续按新的观测范围调查，避免为了维持原假设而反复修改同一段代码。

### 硬件常量需要分别核实来源

检查点 66 已通过根 vnode 初始化，随后默认外设入口调用 `redwood_soc_is_sm8750()`，旧实现读取 `0x01fc0000` 的低 16 位。已有[独立评审 F02](2026-10-23-independent-review.md)指出：SoC ID 618 有来源，寄存器地址与字段解释尚未核实。机型识别发生在部分外设开关检查之前，所以默认启动也会访问该地址。

主会话改用 loader 输出的 GIC 范围识别当前支持的 annibale：distributor 为 `0x16000000`／`0x10000`，redistributor 为 `0x16080000`／`0x200000`。更改后真机通过外设入口后的检查点 68、用户态准备前的检查点 69，随后进入 SpringBoard。

目前确认的是未经验证的访问已被移除，修复后的输入组合通过了此前阶段。未取得该次寄存器访问的底层异常状态，其他历史退出也不能全部归因于这一处。GIC 组合识别受当前平台集合约束，未知身份及新增平台需要另行验收。

## 3. 调查过程中的方法与限制

### 补全观测，再修改启动行为

早期 USB 日志为空。检查发现 `kprintf` 只在 UART 输出分支写入 loader 缓冲，K90 实际选择另一分支。修复后，`trace` 取得 BSD 初始化和 `cpu_start()`；继续覆盖 console 后，`trace3` 才出现更多 IOKit 输出。日志缺失需要按消息产生、console 选择、缓冲与主机读取逐段检查。

`trace2` 已记录 CPU 初始化完成、CoreSight 初始化完成，以及一次定时器 IRQ 的进入和退出。`trace3` 又记录：

```text
MiniIOMobileFramebuffer: display 1125x2436 on a panel of 1156x2510 (4624 bytes per row)
```

`trace3` 之后 USB 请求仍超时。继续增加必要标记和错误入口记录，`trace4`、`trace5` 已能返回 loader，后者还取得 APFS 卷信息和 panic 正文。最后一行只能说明该输出已执行，后续定位继续使用成对标记和对应调用关系。

### 错误报告可能引出另一处故障

`trace5` 记录 `Ticket lock ... is unexpectedly owned by thread ...`。主会话使用本轮 `handoff-mach-trace5` 的符号表，将锁地址定位到 `_vcputc_lock`，随后检查异常打印再次进入持锁 video console 的路径，保留独立缓冲中的 panic 正文和 fault 寄存器。错误报告自身的失败会限制原始信息，不能只根据最外层 panic 推定最初故障。

这个案例也要求地址分析与测试产物对应。锁地址、调用地址和异常寄存器要使用该轮二进制及加载信息解释，不能直接沿用旧构建的符号位置。

### 分开控制时间与执行阶段

单 CPU 交接也出现了退出，双 CPU 并行这一条件未能独立解释故障。接着在已通过的检查点 21 停留 5 秒，期间 USB 连续应答，约 5.3 秒读到正常返回；在该状态下，单纯经过这段时间没有复现失败。后续将检查点移到 framebuffer 初始化、根设备查找、挂载和 vnode 获取之后，逐段缩小范围。

61 与 63 定位 framebuffer 初始化和 `setconf()` 之后；64、65 位于 `IOSecureBSDRoot()` 前后；66 位于根 vnode 初始化之后。这些检查点均返回，再继续查看下一段默认调用。等待实验只覆盖该阶段的资源状态与持续时间，后移检查点的结果则覆盖新执行过的调用。

### 每轮重新确认输入及状态

首轮桌面参数未启用 `touchscreen`，用户观察到无触摸响应；日志同时记录软件 renderer。缺少触摸输入先核对驱动开关和初始化结果，视觉效果则检查资源与合成路径。软件 renderer 的日志只是已确认的运行状态，壁纸和半透明缺失的具体原因仍待验证。

完整启动日志 `full-v2-00.log` 记录 resident system image 作为 `md0`，小镜像作为 `md1`。中间的 `trace` 系列只包含小镜像，`trace5` 识别的卷为 redwood；后续重新上传完整系统盘，`platform/68.log` 和 `ios-first/089.log` 才取得 System 卷结果。RAM 镜像随 loader 生命周期管理，重启后重新确认；各轮结论按各自输入划定范围。

容器编辑还出现过遗漏 `docker exec -i` 的情况：退出码为 0，预期内容没有进入文件。确认文件与 diff 后才继续构建。同样，fastboot 曾退出 0 却输出 `FAILED`。两种情况都要求核对动作的实际后置条件。

容器中保留了多个临时诊断改动。主会话选择性导出长期修复，并将六个补丁应用到明确的上游基线，逐文件比较应用结果与编译树，全部一致。临时提前返回和等待逻辑清理后再做正常流程回归，防止测试成功依赖诊断专用行为。

### 把恢复成本计入实验设计

用户已明确要求减少手动介入。旧 loader 停滞时重插 USB 未恢复，后来回到 Android 桌面但主机无枚举，重插后 ADB 恢复，主机完成 Android → fastboot → loader 的切换。相同动作在不同设备状态下会有不同结果；先核对用户画面与主机状态，再选择恢复方式。固件直接进入 FASTBOOT 的能力仍需单独实测。

日志、临时标记、容器修改与已导出补丁分别记录，防止定位过程中的输入混淆。更多实现与操作细节由源码、当前调试手册和原始会话保存，后续只补充会改变判断方法或操作边界的新结论。
