# roundb 绘制阶段耗时拆解（2026-10-28）

roundb 装车的 AIR 库带逐帧计时插桩，日志里有三帧按阶段拆开的绘制耗时。本文把这三帧与六次最慢 draw 解析出来，回答各阶段的占比，并核出一处单位错误：插桩打的 `us` 值不是微秒，与内核 `tl:` 行的微秒差 52 倍。所有换算过的数都标了换算系数与它的推导。

数据范围限 roundb（`docs/progress/evidence/k90auto/kernel-12377-attr26-roundb/run/`）。round C 也有一份 `perf driver` 汇总，本轮冻结、帧数 3611，与 roundb 不可直接比，不在本文范围内。

## 1. 数据来源、计数口径与覆盖边界

插桩实现在 26 线已提交的 `hackios-xnu-kernel/tools/mesa/draw-perf.patch`（700 行）。它默认开启，`FD_PERF_DRAW=0` 才关；第一次 draw 会打一行说明当前状态。roundb 装车那份 AIR 库（`d7b9ced5a115c08c…`、13,983,936 字节）带这份插桩，`hackios-xnu-kernel/out/ios26-resume/mesa-arm64e/air-build-record.json` 的 `library_sha256` 与 `holds` 块记录了这一点，roundb 的日志证实它在运行时打印过。

计数按协议 §5 分文件组给，raw 是跨快照求和，唯一行是按整行去重：

| 行族 | `run/s[0-9]*.log` raw（21 份） | 唯一 | `run/hung-held.log` raw | 唯一 | 并集唯一 |
|---|---|---|---|---|---|
| `perf draw: timing on…` | 814 | 1 | 52 | 1 | 1 |
| `perf driver <N> us: <M> draws…` | 42 | 3 | 2 | 2 | **3** |
| `perf driver worst:` | 84 | 6 | 4 | 4 | **6** |
| `perf client ` | 0 | 0 | 0 | 0 | 0 |
| `perf flush totals:` | 0 | 0 | 0 | 0 | 0 |
| `perf flush <N>:` | 0 | 0 | 0 | 0 | 0 |

`run/hung-held-serial.log` 里这六族全部零命中。`hung-held.log` 的 2 条汇总与 4 条 worst 都在 `s[0-9]*.log` 那 3 条与 6 条之内，并集没有增加新行。

**本文的全部信息量是 3 帧加 6 次 draw。** raw 44 条汇总是 3 条唯一行在 21 份重叠快照里的重复计数（日志环约 20 秒，快照每 20 秒拉一次，同一条行会出现在多份快照里）。引用这批数据时给唯一行数，raw 只用来与量级对照。

三行族零命中的原因在 patch 的打印条件里，都能读出来，与「打印失败」是两回事：

- `perf flush <N>:` 要求 `w->frames >= FD_PERF_WINDOW`，`FD_PERF_WINDOW` 是 128。`w->frames` 是库里的静态变量，随进程重启归零。roundb 的 `tl: v` 唯一帧号是 99 个（1..113，每个帧号只有 1 条唯一行，帧号在内核侧全局递增），分散在 15 代 backboardd 上，单进程远不到 128 帧，所以窗口汇总一次也没打。
- `perf flush totals:` 要求 `total_flushes % 1024 == 0`，`total_flushes` 同样是按进程的静态变量，同一理由没到 1024。
- `perf client ` 来自 client 线程那条路径，roundb 里没有触发。

`holds` 与打印要分开读，两个方向都核。`air-build-record.json` 的 `holds` 记的是「库里有这个格式串」，`"perf flush totals"` 在其中是 true 而日志里是 0 条，这一部分编进去了而条件没满足。反方向：日志里出现一条打印就证明它生效，格式串在库里存在不证明任何一轮打过它。所以报插桩状态给两个数，构建记录的 `holds` 项与本轮日志里该族的 raw 与唯一行条数。读数规则文档 §9.4 记了这条规则。

覆盖边界一条：`FD_PERF_SLOW_US` 是 6000，`fd_perf_close()` 只在该帧累计超过它时才打这一帧的行。按第 2 节的换算，阈值是 312.5 毫秒真实时间。所以累计耗时在 33 毫秒（roundb 呈现间隔的中位数）到 312.5 毫秒之间的帧在这批数据里没有行，零行读不成零成本。

## 2. 插桩打的 `us` 值与内核 `tl:` 的微秒差 625/12 倍

两侧读的是同一个 tick 计数，换算不同：

- 内核 `hackios-xnu-kernel/out/xnu12377/iokit/Kernel/MiniIOMobileFramebuffer.cpp:169-175` 的 `micros()` 是 `absolutetime_to_nanoseconds(absolute, &ns); return ns / 1000;`，返回值是微秒。`tl: s`（`:838`）与 `tl: v`（`:1017`）都经它。
- 插桩 `draw-perf.patch` 的 `fd_perf_us()` 是 `return mach_absolute_time() / 1000;`，返回值是 tick 数除以 1000，没有过 `absolutetime_to_nanoseconds`。

所以两侧之比等于每 tick 的纳秒数，也就是 `mach_timebase_info` 的 `numer / denom`。patch 的注释写着「The clock is mach_absolute_time over 1000, the one the kernel's "tl:" lines use, so a line here lines up with tl: s, tl: Q and tl: v in the same log」，前半句对：钟确实是同一个。后半句错在单位：`ticks / 1000` 只有在时基是 1 GHz 时才等于微秒。

### 2.1 从时钟换算推出来

`numer`／`denom` 在本移植里的取值可以顺着源码定下来，不需要测：

```c
/* pexpert/arm/pe_init.c:598-599 */
timebase_freq.timebase_num = gPEClockFrequencyInfo.timebase_frequency_hz;
timebase_freq.timebase_den = 1;

/* osfmk/arm/rtclock.c:112-133，timebase_callback() */
if (freq->timebase_den < 1 || freq->timebase_den > 4 ||
    freq->timebase_num < freq->timebase_den) { panic(...); }
denom = freq->timebase_num;                  /* = timebase_frequency_hz */
numer = freq->timebase_den * NSEC_PER_SEC;   /* = 1 * 1e9 */
/* 然后按最大公约数约分，存进 rtclock_timebase_const */
```

`osfmk/arm/rtclock.c:314-317` 的 `clock_timebase_info()` 直接返回 `rtclock_timebase_const`，它就是用户态 `mach_timebase_info` 拿到的那一对。于是

    k = numer / denom = 1e9 / f        f = timebase_frequency_hz

`f` 的来源：`pexpert/arm/pe_identify_machine.c:53` 的默认值是 `24000000`，`:70-78` 用设备树里 `/cpus` 下处于 `running` 的那个节点的 `timebase-frequency` 属性覆盖它。本移植的设备树不在这个仓库里，所以 `f` 读不到字面值。

`f = 19.2 MHz` 由本移植自己的驱动在四处记下：`bsd/dev/redwood_mic.c:246` 的 `#define CLOCK_HZ 19200000`、`bsd/dev/redwood_touch_bus_private.h:265` 的 `#define XO_HZ 19200000`、`bsd/dev/adreno8_clock.c:82` 用 `19200000ULL` 作参考频率、`bsd/dev/redwood_adreno.c:820` 打印 `the crystal: 19200000`。代入：

```
k = 1e9 / 19200000，gcd(1e9, 19200000) = 1600000
  => numer = 625, denom = 12, k = 625/12 = 52.083333...
```

lead 提的 41.667 是 `125/3`，对应 `f = 24 MHz`，即 `pe_identify_machine.c:53` 那个默认值。本机是 19.2 MHz 的晶振，所以下面把 41.667 排除掉。

### 2.2 用日志验证，只用一个方向

「一帧的绘制在它被呈现之前结束」给出 `k` 的上界。三帧里两次最慢 draw 的结束时刻是 `(最后一次 entry + 它的 total) × k`，与呈现流里紧随其后的那一帧的 `shown` 比：

| 帧 | 最后一次 draw 结束（插桩单位） | 紧随的呈现 | 该帧 `shown`（µs） | `k` 上界 |
|---|---|---|---|---|
| A | 18641377 + 809 = 18642186 | 帧 1 | 970952056 | 52.083594 |
| B | 18974017 + 892 = 18974909 | 帧 18 | 988355996 | 52.087522 |
| C | 21015241 + 5512 = 21020753 | 帧 102 | 1094835200 | 52.083539 |

`625/12 = 52.083333` 满足三条，最紧的那条（帧 C）余量 0.0004%，帧 A 余量 0.0005%，帧 B 余量 0.008%。帧 A 与帧 C 的绘制分别在呈现前 4.9 毫秒与 4.3 毫秒结束，帧 B 早 79.5 毫秒。这个顺序有代码依据：`shown` 是节拍到来的时刻，`MiniIOMobileFramebuffer.cpp:912` 取 `ready`（GPU 等待结束）、`:930` 的 `clock_delay_until(next)` 等节拍、`:934` 重新赋值 `began`、`:937` 的 `shown = began`、`:1010` 取 `drawn`（打成 `done`）。AIR 的绘制在 swap 到达之前做完，swap 到达之后先等 GPU 再等节拍，`shown` 才落下，所以「绘制结束 ≤ `shown`」是这条链必然的顺序。

`k = 125/3 = 41.6667` 排除：帧 A 的两次 draw 会在 776.76 秒结束，而帧 1 在 970.95 秒呈现，绘制比它产出的呈现早 194.2 秒。这个差与日志本身的形态冲突：帧 A 的两条 worst 行在同一份快照里夹在相隔 0.57 秒的两条 `tl:` 行之间，日志按时间顺序写入，worst 行又是在该帧关闭时才打，所以这一帧的绘制结束时刻就在那 0.57 秒里，也就是 970.9 秒上下；194.2 秒的偏移放进一个按时间排序的流里不成立。`k = 1`（把插桩值当微秒）差 52 倍，同样排除。

第三条确认来自 round C，与前两条独立。`perf flush 128:` 那 27 条稳态窗口汇总的 `us/flush` 是相邻两次 flush 关闭之间的墙上时间平均值，27 条的取值只有 319、320、327 三种；按 `625/12` 换算是 16.61、16.67、17.03 毫秒。display 从 round C 的 `tl: v` 原始时间戳独立量到的 `shown` 间隔中位是 16.64 毫秒、p95 是 17.13 毫秒。两条路径的取值范围重合，偏差在 0.6% 以内。按 `125/3` 换算这三种取值是 13.29、13.33、13.63 毫秒，比实测的帧周期低 20%。

| `us/flush` | 按 `625/12` | 按 `125/3` | `tl: v` 侧的对照值 |
|---|---|---|---|
| 319 | 16.61 ms | 13.29 ms | 中位 16.64 ms |
| 320 | 16.67 ms | 13.33 ms | 中位 16.64 ms |
| 327 | 17.03 ms | 13.63 ms | p95 17.13 ms |

### 2.3 先前那版 bracket 测量的更正

本文先前用「同快照里 worst 行前后两条 `tl:` 行」给每条 worst 行定了一个 `k` 区间，六条落在 52.055 到 52.103、交集为空，当时按 bracket 松紧解释并取了 `k = 52.09`。那个下界不成立：`entry` 是绘制**开始**的时刻，而 worst 行是在该帧关闭之后才打，所以 `entry × k` 可以合法地早于前一条 `tl:` 行的事件时刻，`k ≥ 前一条微秒 / entry` 这个约束没有依据。有效的只有上界，也就是 2.2 那三条。按 2.2 重算，六个 entry 里有两个（帧 B 的 18971134 与 18974017）落在前一条 `tl:` 行的时刻之前 83 毫秒与 233 毫秒，与这个解释一致。取值从 `52.09` 改成 `625/12`，下游数字的变化都在 0.1 毫秒以内，第 3 到 5 节已按 `625/12` 重算。

有一处自洽检查不依赖 `k`：`entry` 与 `total` 同单位，所以同一帧里两次 draw 的 `entry` 之差应当等于前一次的 `total`。三帧都对上，误差 0 到 3 个单位：`18641377 − 18635230 = 6147` 对 `total 6146`；`18974017 − 18971134 = 2883` 对 `total 2880`；`21015241 − 21014391 = 850` 对 `total 850`。三帧的两次最慢 draw 都是首尾相接，中间没有空档。

单位错误的两个后果：

- `FD_PERF_SLOW_US 6000` 的真实阈值是 6000 × 625/12 = 312500 微秒，正好 **312.5 毫秒**。patch 里那条注释「A frame whose own accumulated CPU is beyond this no longer fits a 60 Hz budget (16667 us)」把 6000 当微秒读，与 16667 微秒比；实际是 312500 微秒对 16667 微秒，阈值是它自己点名的那个预算的 18.75 倍。
- 所有打印出来的 `us` 数值都小 625/12 倍。读这批数据时要么按 `k` 换算，要么只读同一行内部的占比（占比与单位无关）。本文两种都给。

## 3. 三帧的阶段拆解

三帧按时间排列。原始单位是插桩值，毫秒列按 `k = 625/12` 换算，开机后时刻取该帧第一次最慢 draw 的 `entry`。

| 帧 | 开机后时刻 | span | draws | driver | tracking | prog | emit | draw | max | program calls | cache lookups |
|---|---|---|---|---|---|---|---|---|---|---|---|
| A | 970.585 s | 6956（362.3 ms） | 2 | 6955（362.2 ms） | 0（0.00 ms） | 6950（362.0 ms） | 4（0.21 ms） | 0（0.00 ms） | 6146（320.1 ms） | 2 | 2 |
| B | 988.080 s | 12828（668.1 ms） | 55 | 8928（465.0 ms） | 76（3.96 ms） | 8817（459.2 ms） | 35（1.82 ms） | 0（0.00 ms） | 2880（150.0 ms） | 130 | 130 |
| C | 1094.500 s | 6363（331.4 ms） | 2 | 6362（331.4 ms） | 0（0.00 ms） | 6357（331.1 ms） | 4（0.21 ms） | 0（0.00 ms） | 5512（287.1 ms） | 2 | 2 |

占比按四个阶段之和算，三帧一致：

| 帧 | tracking | prog | emit | draw | driver / span |
|---|---|---|---|---|---|
| A | 0.00% | **99.94%** | 0.06% | 0.00% | 100.0% |
| B | 0.85% | **98.76%** | 0.39% | 0.00% | 69.6% |
| C | 0.00% | **99.94%** | 0.06% | 0.00% | 100.0% |

四条读数：

- `prog` 在三帧里都是 98.76% 到 99.94%，占比稳定。`prog` 覆盖 `d->prog - d->track`，即 program 准备与查找那一段。
- `draw` 三帧都是 0，`emit` 是 0.06% 到 0.39%。命令流的生成与提交在这三帧里读不出耗时。
- 四个阶段之和与 `driver` 相等或差 1 个单位（A：0+6950+4+0 = 6954 对 6955；B：76+8817+35+0 = 8928 对 8928；C：0+6357+4+0 = 6361 对 6362），差值是取整。所以 `driver` 这段时间被四个阶段完整覆盖，没有落在阶段之外的部分。
- 帧 B 的 `driver / span` 是 69.6%，剩下 30.4% 的 span 在 driver 阶段之外；A 与 C 都是 100.0%，整段 span 都在 driver 里。

`program calls` 与 `cache lookups` 在三帧里都相等（2/2、130/130、2/2），而按时间排列是 2、130、2，不单调。两个计数器是库里的全局变量，随进程重启归零，所以三帧分属三代 backboardd。A 与 C 都是 2 次 draw 配 2 次 program call，形态是一个新进程最早的帧；B 是 55 次 draw 配累计 130 次 program call，形态是进程跑了一阵之后的帧。每次 program call 都伴随一次 cache lookup，两个计数器同步递增，本文没有从 patch 里读出它们在什么条件下会分开，所以只报相等这一条。

单次 program 准备的耗时在两帧里相差约 51 倍：A 的 2 次共 362.0 毫秒，每次约 181 毫秒；B 这一帧的 459.2 毫秒对累计 130 次，每次约 3.5 毫秒。B 的 130 是累计值而 459.2 毫秒是这一帧的值，两个数不同源，所以这个 51 倍只是量级对照，读不成「冷启动比热路径慢 51 倍」。要那个数需要每帧的 program call 增量，patch 里 `fd_perf_progs` 是累计量，日志里没有增量。

## 5. 与呈现流的对齐

对齐只能在单份快照的有序流里做，本节的时间全部来自 `tl: v` 的唯一行（99 个帧号，`shown` 字段），插桩侧的时间按第 2 节的 `k` 换算到同一个真实微秒轴上。

呈现间隔有两个口径，差得很远，本文两个都给。日志里在的帧号是 99 个、范围 1..113，缺 14 个（21、22、33、42、50、54、62、66、82、85、101、103、106、112），每缺一个就有一对被「只取相邻帧号」这个过滤条件丢掉，而被丢掉的往往正是跨空洞的那一对。

| 口径 | 对数 | 中位数 | p90 | 最大 | 超过 100 ms |
|---|---|---|---|---|---|
| 只取相邻帧号连续的对 | 85 | 33.25 ms | 50.05 ms | 16411.2 ms | 3 |
| 在日志里的帧号依次配对 | 98 | 33.32 ms | 10368.58 ms | 80329.3 ms | 16 |

「依次配对」那一列才是本轮呈现时间轴的实际形状：16 对超过 100 毫秒，其中 **13 对落在 10.3 到 10.7 秒这一档**，另有 80.3 秒（111 → 113）、40.3 秒（105 → 107）、20.3 秒（102 → 104）、16.4 秒（2 → 3）、753.5 毫秒（17 → 18）、126.3 毫秒（19 → 20）。10.4 秒这一档是 15 代 backboardd 崩溃循环的周期。「只取相邻帧号」那一列量的是帧连续流动时的节奏，用它报本轮的呈现问题会把 p90 从 10.4 秒读成 50 毫秒。

三帧慢帧与呈现流的对照：

| 慢帧 | 两次最慢 draw 的窗口（开机后） | 窗口内呈现的帧号 | 前一次呈现 | 后一次呈现 |
|---|---|---|---|---|
| A | 970.585 .. 970.947 s | 无 | 无，帧 1 是本轮第一次呈现 | 帧 1 于 970.952 s，窗口结束后 4.9 ms |
| B | 988.080 .. 988.277 s | 无 | 帧 17 于 987.603 s，窗口开始前 477.4 ms | 帧 18 于 988.356 s，窗口结束后 79.5 ms |
| C | 1094.500 .. 1094.831 s | 无 | 帧 100 于 1084.202 s，窗口开始前 10297.2 ms | 帧 102 于 1094.835 s，窗口结束后 4.3 ms |

**三帧与呈现流的关系是同一种。** 窗口整个落在两次呈现之间，窗口内没有任何呈现，窗口结束后 4.3 到 79.5 毫秒就是紧随的那次呈现。第 2.2 节那三条 `k` 的上界就来自这个关系。

这里的「呈现」是 `tl: v` 的 `shown`，它记的是软件节拍到来的时刻（`MiniIOMobileFramebuffer.cpp:930` 的 `clock_delay_until(next)` 等到节拍、`:934` 重新赋值 `began`、`:937` 的 `shown = began`），与面板扫描无关，节拍周期是 `NSEC_PER_SEC / refreshHz()`。所以本节对齐的是绘制与软件节拍，不是绘制与上屏。

三帧所在的那个呈现间隔长度差很多：

- A 之前没有呈现，帧 1 是本轮第一次，所以它前面那个间隔量不出来；它后面是 2 → 3 的 16411.2 毫秒空洞。
- B 落在 17 → 18 的 753.5 毫秒里。它的 driver span 是 668.1 毫秒，占这个间隔 88.7%；两次最慢 draw 只占 196.6 毫秒，其余由另外 53 次 draw 分摊。
- C 落在 100 → 102 的 10632.9 毫秒里（帧 101 不在日志里，这个间隔跨两个帧号），它自己的 driver span 是 331.4 毫秒，占 3.1%。剩下那 10.3 秒里没有绘制，插桩量不到它。

A 之后那个 16411.2 毫秒与 C 所在那个 10632.9 毫秒的量级与 15 代 backboardd 的崩溃循环对得上，roundb 的 15 起 `signal 11 code 11` 事件见[归属复核](2026-10-28-roundb-memmove-attribution.md) §7。

所以「慢帧是不是就发生在这些 worst draw 上」的答案分两层。绘制与呈现这一层三帧都对上了：最慢 draw 都在它们产出的那次呈现之前几毫秒到几十毫秒完成。间隔本身只有 B 对上，它的间隔 88.7% 被绘制占满；A 前面没有可量的间隔，C 的间隔里只有 3.1% 是绘制，剩下的 10.3 秒由这批数据之外的原因造成。

## 6. 结论与它的边界

在插桩打出来的这三帧里，绘制耗时集中在 `prog`，即 program 准备与查找，占比 98.76% 到 99.94%，三帧一致；`draw` 阶段三帧都是 0，`emit` 最高 0.39%，`tracking` 最高 0.85%。单次 draw 最长 320.1 毫秒，其中 319.9 毫秒在 `prog`。

四条边界，引用这个结论时一起带上：

- **样本是 3 帧。** 唯一行只有 3 条汇总与 6 条 worst，raw 44 与 88 是快照重叠的重复计数。3 帧里 2 帧是新进程最早的帧（2 次 draw、2 次 program call），第 3 帧是跑了 55 次 draw 的帧。占比在三种形态下一致这一点让结论比样本量看起来稳一些，样本量本身仍然小。
- **阈值以下的帧没有数据。** 打印条件是累计超过 6000 个插桩单位，即 312.5 毫秒真实时间。roundb 呈现间隔的中位数是 33.25 毫秒、p90 是 50.05 毫秒，都远低于阈值。所以这批数据描述的是超过 312.5 毫秒的那些帧，对占多数的 33 到 312 毫秒这一段没有任何读数，零行读不成零成本。
- **绝对耗时不能与无插桩的轮次比。** 插桩每次 draw 取 8 次钟并做每帧簿记，每 128 帧一次打印。相对占比可用，绝对值带着插桩自身的开销。可作性能验收的绝对耗时要等关掉插桩重编之后的轮次。
- **这批数据解释不了 roundb 的呈现时间轴。** 依次配对的 98 对里有 16 对超过 100 毫秒，其中 13 对在 10.3 到 10.7 秒这一档，最大 80.3 秒；三帧慢帧的 driver span 最多 668.1 毫秒。只有 B 占满了它所在的那个间隔（88.7%），而那个间隔只有 753.5 毫秒；C 占它那个 10632.9 毫秒间隔的 3.1%。把 roundb 的呈现问题归到 program 准备上，与这些空洞的量级不符。

### 6.1 验收的形状：每帧成本已经够，缺的是渲染段长度

round C 与 round D 的稳态每帧成本是 16.60 到 16.64 毫秒（8.7 那张表的三条路径），用户定的验收阈值 55 fps 对应一帧 18.18 毫秒，稳态在它之内。三轮 summary 行的 `under18` 都是 100%，`long_count` 是 4、3、0。

验收没有通过，原因是渲染段的长度。`round-stats.py` 的 `swap holes` 段报 round C 的末次交换在开机后 12939.2 秒，而该轮 `tl:` 覆盖从 12841.5 秒起，即渲染段约 97.7 秒；round D 的末次交换在 rel 96.4 秒。在那之后系统不再提交帧，而轮次还要跑约 320 秒。

round C 那 8 个低于 60 a second 的窗口（59、48、30、24、24、23、13）的节拍等待与驱动时间与 60 a second 的窗口相同。插桩一侧那 4 条 `770`／`772`／`775 us/flush` 窗口给同一个结论：每条的 `max` 在 57919 到 58566 单位之间，即 3.017 到 3.050 秒，对应 `swap holes` 报的「15 秒周期、3 秒上下」那族空洞；扣掉那一个间隔，其余 127 个间隔平均 317 单位、16.5 毫秒，与稳态相同。帧数少是提交少了，每帧本身没有变慢。

所以性能这条线的阻塞点在渲染段为什么只有约 96 到 98 秒，也就是 15 秒周期序列与终末段那条线。每帧成本这一侧已经给出结论。

`summary.py --verify` 现在直接读窗口统计行里的三个交换队列计数与节拍等待，三轮的基线：

## 7. 对后续的意义

P6 要的「每帧成本拆解」在这批数据覆盖的范围内有了答案：成本在 program 准备与查找，命令流生成与提交读不出耗时。这个答案的适用范围是第 6 节那四条边界之内。

要把范围扩大，需要动插桩本身，两处：把 `FD_PERF_SLOW_US` 降到能覆盖 33 到 312 毫秒这一段，以及让 128 帧的窗口汇总能触发（要求单进程关闭 128 帧以上，roundb 的崩溃循环下拿不到）。round C 的形态是 3611 次交换、帧号 1..3611 零断裂、两个进程全轮存活，单进程帧数够触发窗口汇总，第 8 节是它真的打出来之后的读数。降低阈值那一处要重编 AIR 库，与关掉插桩出验收数的要求相反，所以是两份产物：一份带插桩、阈值降低、用于定位；一份不带插桩、用于验收。重编的前置见 task-17 与 `hackios-xnu-kernel/tools/mk-mesa.sh`。

单位这一处建议在下次动这个 patch 时一起改，两种改法都可以：`fd_perf_us()` 里过 `mach_timebase_info` 的 numer／denom 换算成真实微秒，或者保留现在的取法而把字段名与 `FD_PERF_SLOW_US` 的注释按 tick/1000 写清。lead 定的时序是现在不改：这份 patch 在 26 线已提交，改注释会让链戳变化、触发 `hackios-xnu-kernel/tools/mk-mesa.sh:106-117` 重解包重打整棵树，所以等 task-17 关掉插桩重编时一起做，那时链戳本来就要变。本文只记 `k = 625/12` 的推导与它的三条验证。

task-17 的待合并清单因此有三处，都在同一个 patch 上，与 `framewatch.m` 的 `arg_base` 那一行放在一起：

1. `fd_perf_us()` 的单位（上面那一段）。
2. `draw-perf.patch:241-244` 那段自检注释：它把 `off by` 写成一个缺陷指标，而实际报的是它自己 `first_now` 取值位置造成的一次性偏差（8.6）。
3. **`fd_perf_checks_sum` 与 `fd_perf_checks_worst` 漏清**：两者是文件作用域全局（`:87`、`:190`），`:285` 的 `memset(w, 0, sizeof(*w))` 只清窗口结构，`:271` 拿累计量除以本窗口的 `w->frames`，所以除第一个窗口之外每一条窗口汇总的 `batch submit` 都是「从进程启动到现在的平均」，`max` 是进程生命周期的最坏值。28 条按文件顺序单调上升（0、1、2、2、3、4、4、5、6、6、7、8、8、10、10、11、12、12、13、14、14、15、16、17、17、18、19、19）就是这个缺陷的形状。改法是把这两个全局移进 `struct fd_perf_win`，或者在 `memset` 之后一并清零。

`prog` 那一段对应 AIR 库里的哪些调用点，本文没有做。要定位需要一个带故障的轮次给出的 `lr` 读数，配[归属复核](2026-10-28-roundb-memmove-attribution.md) §6.4 的页对齐反解，候选是 §6.3 那 9 处源码调用点与 stub 地址 `0x4316f0`。round C 全轮零故障，没有 `lr` 读数。

### 8.5 窗口汇总各字段的定义、单位与两处口径缺陷

字段名与它量的区间，全部从 `draw-perf.patch` 的计时点读出来：

| 字段 | 计时点 | 量的区间 |
|---|---|---|
| `us/flush` | `:233` 的 `took = now - w->last_close`，`:268` 除以 `w->frames` | 调用线程上相邻两次 `fd_context_flush` 进入之间的墙上时间。一个窗口是 128 次这样的进入。这一层没有 Gallium worker 线程（8.5），所以调用线程与驱动侧是同一个线程 |
| `draws`、`calls` | `:270`、`:281` | 一帧的 draw 次数与到达驱动入口的调用次数 |
| `driver` | `w->driver += f->driver`（`:224`），`f->driver` 来自 `:637` 的 `driver = c.exit - c.entry` | 一帧里所有 draw 从进入到退出的总时间 |
| `own` | `:227` 的 `f->drawn + f->emit + f->prog + f->track` | 四个有名阶段之和，是 `driver` 的子集 |
| `submit` | `fd_perf_window_submit`（`:318-327`），在 `fd_context_flush` 里从 `fd_perf_close` 之后计到 `out:` | 一次 flush 的剩余部分，注释写明含提交 ioctl 与等 batch 空间 |
| `batch submit` | `fd_perf_clock_us` 夹住 `fd_batch_check_size`（`:165-167`） | batch 满时提交被接受所花的时间 |
| `client` | `:206` 的 `w->client += f->wait` | 客户端一侧 `tc_draw_vbo` 的排队等待 |
| `sync` | `fd_perf_window_sync`（`:296-305`）夹住 `tc_flush` 里的 `tc_sync_msg` | 客户端线程的同步消息 |
| `pass` | `fd_perf_window_pass`（`:307-316`）夹住 `tc_flush` 里的 `pipe->flush` | 打点位置在 `tc_flush` 里，而这一层的 `pipe` 是裸 `fd_context`、`tc_flush` 不在路径上（8.5），所以被夹住的那次调用没有发生，字段恒为 0，读不成 0 µs |

两处口径缺陷，读数时要绕开：

- **两种钟混在同一行。** 除 `batch submit` 外所有字段用 `fd_perf_us()`，即 `mach_absolute_time() / 1000`，一个单位是 52.08 微秒；`batch submit` 用 `fd_perf_clock_us()`（`:90-93`），即 `os_time_get_nano() / 1000`，一个单位是 1 微秒。同一行里两个单位，行内相加之前要先分开换算。
- **`batch submit` 是进程累计量除以本窗口帧数。** `fd_perf_checks_sum` 与 `fd_perf_checks_worst` 是文件作用域的全局（`:87`、`:190`），`:285` 的 `memset(w, 0, sizeof(*w))` 不清它们，而 `:271` 拿它除以 `w->frames`。28 条按文件顺序的取值是 0、1、2、2、3、4、4、5、6、6、7、8、8、10、10、11、12、12、13、14、14、15、16、17、17、18、19、19，单调上升，`max` 同样单调。所以这一列只有第一个窗口是该窗口的值，后面的窗口读成「从进程启动到现在的平均」，跨窗口不可比。它的量级本身也说明 `fd_batch_check_size` 几乎没有成本：28 个窗口累计 19 微秒。

**分辨率与「0 意味着什么」。** 一个单位是 52.08 微秒，所以任何字段打出 0 表示这一段低于 52.08 微秒，不表示代码没走到。`client`、`sync`、`pass` 三项在 28 条里全是 0，其中 `pass` 的 0 可以排除「走到了但低于分辨率」：`pass` 夹住的 `pipe->flush` 就是 `fd_context_flush`，而同一窗口里 `submit` 是 19 到 25 个单位、0.99 到 1.30 毫秒，`submit` 的区间整个在 `pass` 里面，`pass` 不可能比它小。所以 `tc_flush` 这条路径没有走到，随之 `tc_sync_msg`（`sync`）与客户端 draw 路径（`client`）也没有走到。

这个推断有源码支撑，而且是故意设计成这样的：`hackios-xnu-kernel/tools/mesa/air/air_metal.c:320` 是 `device->pipe = device->screen->context_create(device->screen, NULL, 0)`，`:314-319` 的注释写明「Flags zero on purpose -- not PIPE_CONTEXT_PREFER_THREADED, so there is no Gallium worker thread between this library and the driver. A map held across a dispatch (rwa_buffer_map) is a direct mapping of the kernel's buffer only while that is true.」`freedreno_context.c` 在 flags 不带 `PIPE_CONTEXT_PREFER_THREADED` 时直接返回原 context，所以 `pipe` 就是裸的 `fd_context`。**客户端那一侧的插桩在这个配置下是死的，而且是为了让 `rwa_buffer_map` 能直接映射内核 buffer 才必须如此。** [差距分析](2026-10-28-ios26-perf-gap.md) §2.6 从代码独立读到同一条，两处可以互引。

**`client 0` 读不成「客户端从没等过」**，`perf client ` 那个家族两轮 0 条也是同一个原因：`fd_perf_close(&fd_perf_client)` 在 `:659-661` 遇到 `!f->draws` 就提前返回，客户端一侧没有 draw 计数就永远不会打那一行。要把客户端一侧读出来需要另一处计时点，现有 patch 里没有；而那处计时点不能加在线程化上下文里，因为这个配置下它不在路径上。

**窗口的边界。** `fd_perf_close`（`:655-698`）在 `!f->draws` 时提前返回，既不加 `w->frames` 也不更新 `w->last_close`（`:258`、`:288`）。所以 128 帧是 128 次「至少有一次 draw 的关闭」，两次之间的间隔可以跨过任意多次空关闭，`us/flush` 因此是这一段墙上时间的平均，含空关闭的时间。

### 8.6 `perf flush totals:` 那三个百分比来自自检自己的取值位置

三条唯一行：

```
perf flush totals: 1024 flushes, gaps 698680 us of 403876 us span, off by 72%
perf flush totals: 2048 flushes, gaps 1085239 us of 790435 us span, off by 37%
perf flush totals: 3072 flushes, gaps 1528433 us of 1233629 us span, off by 23%
```

三条的 `gaps − span` 都正好等于 294804 单位，也就是 8.4 那条慢窗口的 `max`。原因在 `draw-perf.patch:245-256`：`first_now` 是在**已经把这一段 gap 加进 `sum_gap` 之后**才赋值的，所以 `sum_gap` 比 `span` 多出进程生命周期里第一个 gap，而这个进程的第一个 gap 正是那 15.354 秒。`off by` 的算式是 `:252` 的 `(sum_gap * 100 / span) - 100`，三个百分比从 72 降到 23 只是因为 `span` 在长而那个固定的差值不变。

patch 在 `:241-244` 的注释把这个自检写成「gap 加起来要与进程花在 flush 上的时间相等，若差开，窗口就没在数它声称的东西，从这一行导出的每个速率都是错的」。按上面的定位，这三行报的是它自己 `first_now` 取值位置造成的一次性偏差，扣掉那一个 gap 之后 `sum_gap` 与 `span` 逐单位相等。**「一个自检报了偏差」与「计数不一致」是两件事**，看到这三个百分比要去查的是一个不存在的缺陷。

### 8.7 稳态那 15.26 毫秒是什么

三段测量拼起来能定到毫秒级。内核 `MiniIOMobileFramebuffer.cpp:1041-1046` 的窗口统计行每 5 秒打一条，round C 有 16 条，它给的三个字段互不重叠：`us each in the driver` 是 `:1029` 的 `fStatDrawing`，从节拍之后累到交换结束；`waiting for the GPU` 是 `:911` 的 `fStatWaiting`；`us for the next refresh` 是 `:933` 的 `fStatBeatWait`，即 `:930` 那次 `clock_delay_until` 的时长。60 a second 那 8 个窗口的实测：

|---|---|---|---|---|---|---|
| 3 | 301 | 5002 ms | 1827 µs | 41 µs | 301 | 6988 µs |
| 5 | 301 | 5006 ms | 1843 µs | 41 µs | 301 | 6849 µs |
| 6 | 301 | 5003 ms | 1890 µs | 41 µs | 301 | 7002 µs |
| 9 | 302 | 5012 ms | 1924 µs | 41 µs | 302 | 7138 µs |
| 11 | 301 | 5003 ms | 2014 µs | 42 µs | 301 | 6935 µs |
| 12 | 301 | 5001 ms | 2021 µs | 41 µs | 301 | 6998 µs |
| 14 | 301 | 5003 ms | 2026 µs | 41 µs | 301 | 6950 µs |
| 15 | 301 | 5002 ms | 2005 µs | 41 µs | 301 | 6999 µs |

帧周期是 5002 到 5012 毫秒除以 301 到 302，即 16.60 到 16.63 毫秒。三个字段加起来是 8.86 到 9.07 毫秒，剩下 7.5 到 7.8 毫秒内核没有测。这剩下的部分在 swap 到达之前，属于客户端一侧；插桩在这一侧记账到 1.35 毫秒（`driver` 0.104 加 `submit` 1.25，`batch submit` 是累计量、量级在微秒上，见 8.5），所以还有约 6.2 到 6.4 毫秒两边都没有记账。

`fStatDrawing` 与插桩无关，它给的 1827 到 2033 微秒与 `tl: v` 的 `done − shown` 中位 1.766 毫秒是两个独立测量，差 3%。

稳态一帧 16.61 毫秒的分层，按区间界定写：

| 区间 | 由哪两个时间点界定 | 谁量的 | 值 |

| 一帧的周期 | 相邻两次 `shown` | display 从 `tl: v` 原始时间戳，1859 对相邻 | 中位 16.64 ms，p95 17.13 ms |
| 同一个周期，另一条路径 | 调用线程上相邻两次 `fd_context_flush` 进入（这一层没有 worker 线程，见 8.5） | 插桩 `perf flush 128:` 的 `us/flush`，27 条稳态 | 16.61 到 17.03 ms |
| 同一个周期，第三条路径 | 内核统计行的帧数除跨度 | `MiniIOMobileFramebuffer.cpp:1041-1046`，8 个 60 a second 窗口 | 16.60 到 16.63 ms |
| 生产链 | 上一帧 `shown` 到本帧 `ready` | display | 中位 9.40 ms，p95 11.04 ms |
| 节拍等待 | 本帧 `ready` 到本帧 `shown` | display 用减法得 7.24 ms；内核 `fStatBeatWait` 直接量 | 6849 到 7138 µs |
| GPU 等待 | swap 到达后等 GPU 完成 | 内核 `fStatWaiting`（`:911`），`:906` 的 `MiniIOSurfaceDrawn` 上限 500 ms | 41 到 42 µs |

三条路径量到的周期是 16.64、16.61 到 17.03、16.60 到 16.63 毫秒，互相差在 0.6% 以内。插桩那一条同时是 `k = 625/12` 的第三条验证（2.2）。

15.26 毫秒（16.61 减 AIR 记账的 1.35）分成两段：

- **6.99 毫秒是节拍等待。** `:930` 的 `clock_delay_until(next)`，由 `fb_beat` 控制（`:146` 的 TUNABLE，默认 1），目标位置是 `:917` 的 `aim = period * 3 / 8`，60 Hz 下是 6.25 毫秒。它跑在内核的辅助线程上，不阻塞 backboardd，但按墙上时间落在两次 flush 进入之间，所以它在这 15.26 毫秒里面。这一段随刷新周期缩放，120 Hz 下按同一比例是约 3.50 毫秒。
- **8.24 毫秒是 CA 一侧的工作，两边都没有记账。** 它是生产链 9.63 毫秒（16.62 减 6.99）扣掉 GPU 等待 0.04 与 AIR 记账的 1.35 之后的余量。用 display 那一组数算同一个余量是 9.40 减 0.04 减 1.35 等于 8.01 毫秒。两个值差 0.23 毫秒，来源是取样不同：display 的是 s020 里 1859 对相邻帧的中位数，内核的是 5 秒窗口的平均值。这一段的拆分需要在 CA 一侧加时间戳，现有日志里没有，本文拆不动。

两段相加 6.99 加 8.24 等于 15.23 毫秒，与插桩一侧的 15.26 差 0.03 毫秒，即 0.2%。用 display 那一组算是 7.24 加 8.01 等于 15.25，差 0.01 毫秒。两条独立路径在这里闭合。

驱动拷像素的 1.77 毫秒在 `shown` 之后，落在下一帧的生产链区间里，与 backboardd 的工作并行，所以它不进上面那两段的和。

**这 15.26 毫秒里没有一段是在等我们的驱动入口。** display 核过四处：选择器 6 `kFBMethodSwapWait` 立即返回（`:1323-1328`）；`present()` 只在交换队列满时阻塞调用方（`:843-847`，深度 `fb_queue` 默认 2，期限 `SWAP_HELD_MS` 700 毫秒），而 16 条统计行全是 `0 swaps waited for the frame before, 0 gave up`，队列从没满过；GPU 等待实测 41 到 42 微秒；节拍等待跑在辅助线程上，不阻塞调用方。插桩一侧能给的支持是 `pass 0` 排除了线程化上下文的 flush 路径（8.5），所以 `client 0` 与 `sync 0` 读不成「客户端从没等过」，它们只是没有读数。

### 8.8 对 120 Hz 的含义

一帧 16.61 毫秒里，随刷新周期缩放的只有节拍等待那 6.99 毫秒。剩下 9.63 毫秒（生产链：GPU 等待 0.04、AIR 记账 1.35、CA 一侧 8.24）会不会跟着缩放，现在没有读数能回答。

**在「9.63 毫秒的非节拍时间不随刷新率缩放」这个前提下**，120 Hz 的槽是 8.333 毫秒，9.63 毫秒超出 1.30 毫秒即 15.6%。本文早先据此写了一个约 104 fps 的上限，那个算法是错的：它把帧周期当成「非节拍时间加节拍等待」这样一个连续量，而 `MiniIOMobileFramebuffer.cpp:923-924` 的 `for (next = fBeat + period; next < began; next += period)` 把上屏时刻吸附到节拍网格上，帧周期是 `ceil(非节拍时间 / 周期) × 周期` 这样一个整数量。9.63 毫秒装不进一个 8.333 毫秒的槽，就落到第二个槽上，周期是 16.67 毫秒，**`fb_hz=120` 单独改这一处帧率不变**。要拿到收益，非节拍时间必须先降到 8.33 毫秒以下；降到 8.33 以下之后周期才是 8.33 毫秒。round E 实测确认了这个量化行为，见 8.11。

前提可能不成立，因为那 9.63 毫秒里 8.24 是 CA 一侧的工作，而 CA 从 `MiniIOMobileFramebuffer.cpp:338` 读模式刷新率、按它走自己的钟（`:245-256` 的注释与 `refreshHz() << 16`）。两种可能：

- 那 8.24 毫秒里有一部分是 CA 按 60 Hz 节拍的等待。它会随 `fb_hz=120` 缩小，非节拍时间落进一个 8.333 毫秒的槽，帧周期跟着变成 8.333 毫秒。
- 那 8.24 毫秒全部是 CA 的渲染工作。它不缩放，非节拍时间仍是 9.63 毫秒，帧周期仍是两个槽即 16.67 毫秒。

### 8.9 round E 的判据

round E 的唯一变量是启动参数 `fb_hz=120`，驱动与 AIR 的哈希与 round C／D 相同，不重编。判据按能不能分开上面两种可能来定：

| 读数 | 60 Hz 基线（round C／D） | 若 CA 那一段随刷新率缩放 | 若 CA 那一段是渲染工作 |
|---|---|---|---|
| `shown` 间隔中位数 | 16.64 ms | 掉到 8.33 ms 附近 | 停在 16.6 ms 附近，帧落到隔一个节拍上 |
| `beat_us`（`summary.py` 新列） | 7,080／7,068 µs | 约 3,125 µs，即 `aim = period * 3 / 8` 在 8.333 ms 周期下的值 | 同左，这一项只由 `fb_hz` 决定，两种结果下都该降 |
| `onbeat` | 100% | 可能下降，见下 | 同左 |
| 8.33 ms 整数倍分档 | 63 轮里 8.33 ms ±0.5 ms 零命中 | 出现 n=1 档 | 仍是 n=2 档为主 |

`beat_us` 降到约 3,125 µs 是两种结果下都该发生的，所以它验的是「节拍等待完全由 `fb_hz` 决定」这一条，不验 CA 那一段。分开两种可能要靠 `shown` 间隔中位数：掉到 8.33 ms 附近说明 CA 跟着模式刷新率走、那 8.24 毫秒里有等待的成分；停在 16.6 ms 而帧落到隔一个节拍上，说明 CA 每帧的工作本身就要约 9.63 毫秒，8.333 毫秒的槽装不下，它隔一个节拍提交一次。

`onbeat` 可能下降的原因在 `:920-921`：迟到超过 1.5 个周期的帧不等节拍、立即上屏，并且不计入 `fStatOnBeat`。60 Hz 下这个门槛是 25 毫秒，120 Hz 下缩到 12.5 毫秒，走立即上屏分支的帧会变多。这一项下降要读成门槛缩小的后果，与「帧变慢了」分开。

**主要失败指标是那两个交换队列计数。** roundb、round C、round D 三轮的「swaps waited for the frame before」与「gave up」都是 0，这是「驱动没有让 CA 等过」的工具输出。round E 若这两个数变成非零，那就是 `fb_hz=120` 引入的新阻塞：`present()` 只在交换队列满时用 `IOLockSleepDeadline` 阻塞调用方（`:843-847`，深度 `fb_queue` 默认 2，期限 `SWAP_HELD_MS` 700 毫秒），周期缩短之后生产链若还是 9.63 毫秒，队列被填满的机会比 60 Hz 下大。

### 8.10 CA 一侧的时间戳排在 round E 之后

round E 判的是那 8.24 毫秒里有多少随刷新率缩放。缩放的那部分把 `fb_hz` 设成 120 就处理掉了，不需要额外读数；不缩放的那部分才需要 CA 一侧的时间戳去分解。所以加时间戳这个改动排在 round E 之后，round E 出结果之前不动。

round E 已经跑完，结果是第二种：那 8.24 毫秒不缩放（8.11）。CA 一侧的时间戳因此从「排在 round E 之后」变成下一步，它要分解的是这 8.24 毫秒里哪些能降到 8.33 毫秒以下。

用户定的验收阈值是 55 fps、一帧 18.18 毫秒，稳态的 16.62 毫秒已经在它之内，这一条与 `fb_hz` 无关（6.1）。round C 的 16 个窗口里有 8 个是 60 a second，另外 8 个是 59、48、30、24、24、23、13 a second；那几个低值窗口的节拍等待与驱动时间与 60 a second 的窗口相同，低的原因是提交的帧数少，8.4 那一段给了插桩一侧的同一个结论。

### 8.11 round E 的结果：节拍变成 8.33 毫秒，帧周期没有变

round E 的唯一变量是 `fb_hz=120`，`summary.py` 的 `args` 列第一次非空，读出 `cpus=2 gpu_log=1 cpufreq=1 fb_threads=2 fb_hz=120`；驱动与 AIR 的哈希与 round C／D 相同，不重编。8 个窗口、78 次交换、`tl:` 跨度 266 秒、最大空洞 79.9 秒。形态翻转进 roundb 家族：bad access raw 243／唯一 14 行，15 代 backboardd `died on signal 11`，渲染段从 rel 18.5 秒起被崩溃循环打断，96 张截图全落在黑屏档，`ff_s=150`，`crashes=29`。

**读数边界：本轮没有一段长的健康 120 Hz 渲染。** 帧号 1 到 91、唯一 78、8 处断裂对应 8 次重起，下面那些间隔来自 9 个进程世代各自的开头几帧，样本小，只够定节拍周期与帧周期这两件事，不够定分布。

8.9 那张表的四项判据，三项给了明确答案，一项的预测错了。

**一、节拍周期确实变成了 8.333 毫秒。** 69 个相邻 id 的 `shown` 间隔里有 8 个落在 7.67 到 9.21 毫秒，均值 8.16 毫秒即 0.98 个节拍。round C 的 3606 个间隔最小值是 14.72 毫秒，16.67 毫秒的节拍下出现不了 7.67 毫秒。这一项直接证明 `refreshHz()` 返回了 120。

**二、帧周期没有变。** 16 个间隔落在 15.01 到 21.90 毫秒、均值 16.98 即 2.04 个节拍，其中 13 个挤在 16.29 到 17.04 之间、均值 16.85，另外 3 个是 15.01、15.70、21.90；round C 的健康中位数是 16.640 毫秒。剩下 41 个间隔均值 41.62 毫秒，是 4 个与 6 个节拍的混合，分布与 roundb 的退化形态相同（roundb 是 n=2 占 43.5%、n=4 占 29.4%、n=6 占 20.0%）。三组的节拍倍数是 0.98、2.04、4.99，全部落在整数节拍上。

8.9 那两种可能里成立的是第二种：那 8.24 毫秒的 CA 一侧工作不随刷新率缩放，它超过一个 8.333 毫秒的槽，每一帧都错过一个节拍、落到下一个上，帧周期量化成两个槽。把刷新率翻倍只把网格加密，没有把帧挪近。

**三、`beat_us` 的预测错了，错因与量化是同一件事。** 8.9 预测它降到约 3,125 微秒即 `aim = period * 3 / 8`，实测是 6,385 到 7,562 微秒，与 round C 的 6,696 到 7,138 基本相同。`aim` 只是 `:925-929` 那个 1/8 步长逼近的目标，而 `:923-924` 的网格推进先把 `next` 放到第一个不早于 `began` 的节拍上：CA 的工作约 9.6 毫秒时，`began` 已经过了第一个节拍、还没到第二个，`next` 就是第二个节拍，等待是 16.67 减 9.6 约 7.07 毫秒。等待时间由工作什么时候做完决定，`aim` 只在连续多帧都走到这条分支时才收敛得到，而 round E 每个窗口只有 1 到 4 帧等节拍，收敛不了。

**四、主要失败指标是干净的。** 8 个窗口的「swaps waited for the frame before」与「gave up」全是 0，`fb_hz=120` 没有引入交换队列阻塞。「came a refresh late themselves」是 44 帧对 68 帧（round C 是 4 对 3611），与 8.9 预测的方向一致：`:920` 的门槛从 25 毫秒缩到 12.5 毫秒，走立即上屏分支的帧变多。`onbeat` 在 summary 行是 `-`，8 个窗口里最大的一个 25 帧但只有 2 a second，都不满足 `busy` 门槛，与 roundb 同。`driver_us` 是 1,256 到 1,635 微秒，round C 是 1,827 到 2,033；两轮的窗口帧数差两个量级，这个差本文不解释。

**对 120 Hz 路线的结论因此改了。** 8.8 那个约 104 fps 的上限算法是错的：帧周期按节拍网格量化，量化之后 `fb_hz=120` 在非节拍时间降到 8.33 毫秒以下之前帧率不变，round E 的实测帧周期 16.98 毫秒与 round C 的 16.640 毫秒在样本量之内没有差别。要往 120 走，顺序是先量那 8.24 毫秒的 CA 一侧、把它降到 8.33 毫秒以下，再谈刷新率。

**本轮还给出一个与 120 Hz 无关的结果**：bad access 第一次带 `lr`，12 个唯一值、无 PAC 位、全部小于 `0x180000000`，故障 pc 与 roundb 逐位同为 `_platform_memmove+0x9c0`，故障 dst 与驱动拷贝缓冲的交集是 9/10。归属解法见[读数规则](2026-10-28-roundc-reading-criteria.md) §3.7 的页对齐反解，候选见[归属复核](2026-10-28-roundb-memmove-attribution.md) §6.3；这一部分归 display 的归属包，本文只记它出现了。
