# GPU 桌面、性能与外设验证经验（2026-10-26）

本文整理 Claude Code 接手 GPU 后的完整调试时间线，重点记录哪些检查改变了判断。CP 启动的后续结果见 [A830 专题](2026-10-24-a830-command-startup.md#9-测试构建与服务生命周期)，通用方法见[排查与协作手册](../plan/debugging-and-collaboration.md)。具体启动与恢复命令继续以[真机调试手册](../plan/device-test-playbook.md)为准。

## 1. 对照成立前，先检查输入与触发场景

桌面加速初次运行后，用户看到标签附近闪烁、控制中心背景异常。早期调查从条带尺寸推断 CPU 缓存或 UBWC，又尝试关闭纹理预取。这些检查尚未分离原因，部分轮次还改变了症状类别。用户补充「异常内容里出现电池图标」，后续按分块位置与 framebuffer fetch 的数据依赖核对，才找到读取了其他分块旧内容的路径。

源码确认，已有 framebuffer fetch 补丁在首次读取前处理 CCU 与 UCHE，A8xx 还需处理 CCHE。userland `94e4c97` 在该位置增加 CCHE 失效；修复前后各约 95 张自动截图，已知色块由部分截图出现变为零张，用户也确认闪烁消失、控制中心正常。结果覆盖已测场景和库版本；颜色检测只覆盖已知异常区域，其他显示问题仍需截图检查与用户反馈。

两次失败对照值得保留：首次关闭 UBWC 的一轮未通过 GPU 阶段 22，随后使用软件绘制，且没有出现壁纸；后续多核对照又误选了未含 CCHE 修复的旧根盘。前者不能用于排除硬件壁纸问题，后者不能用于评价修复后的显示正确性。用户提供的视频也属于较早的触摸启用轮次。先核对运行、renderer、镜像内的库和场景，再解释「有没有闪烁」，可以减少围绕错误输入继续调整。

## 2. 沿每帧处理过程寻找耗时，并重新评估旧结论

最初显示驱动的软件缩放耗时较长，向量化与 CPU 档位控制缩短了这部分时间。后续控制中心仍有长帧，调查继续分解绘制、提交、缓冲分配和页表发布，发现串行提交等待、IOVA 查找及全量页表清理的成本。增加有界提交排队、按空闲位置查找并只发布改动页表项后，主动画帧率继续改善。只释放队列等待期间的锁，实测收益有限；该结果没有支持早期的主要锁竞争假设。

继续计时还发现，缓冲接口频繁执行 GPU／GMU／SMMU 健康检查，读取 MMIO 本身占用提交时间。`00259e5` 允许短时间复用成功结果，同时保留失败状态和到期重查。该配置的控制中心主动画约 58.7 帧/秒，帧间隔 p95 约 17.5 ms；这是所测动画窗口的结果。整轮含有静止期，复制到 framebuffer 完成后的面板扫描也未测量，不能据此报告完整的物理显示延迟。

GPU 整轮忙碌比例较低后，会话一度判断 GPU 频率无需调整；后续帧内提交和等待计时又显示频率实验值得比较。相同内核和根盘下，请求较高 GPU 档位的一轮绘制耗时缩短，较低档位对照也已结束。截止本次阅读，日志尚未给出独立实际时钟读数；准备增加的档位统计来自软件最后请求值。性能改善支持继续验证频率影响，调频归属、实际工作频率与 GPU 温控执行仍需单独确认。

温度记录也有修正。早期每隔一段时间读取的温度较低，报告据此称提频轮未触发温控；后续完整日志与峰值记录确认启动阶段曾超过 70 °C，温控已触发。用户要求不主动触发九十多度后，尚未运行的高温实验已撤下。自然出现的低阈值转换提供了一部分实测，传感器失效、持续过热与恢复仍需分别验证。调频状态可观察，整机功耗尚未完成测量。

上述检查顺序适用于多段异步处理：先用同一帧的时间点区分计算和等待，再对耗时较大的部分做小范围修改；每次修改后重新测量。提高核心数、排队深度或固定高频的收益取决于剩余耗时，单次总体均值不足以决定默认配置。

## 3. 外设验证要检查实际状态和中途退出

手电与震动的 SPMI 写入先经历两种映射失败：窗口不足造成访问越界，扩大为整个窗口又在启动早期分配失败。最终根据已发现的通道分别映射所需页面。该过程说明映射范围应从实际访问计算，整个硬件窗口的大小还受执行阶段的映射资源限制。

传输完成后寄存器未变化，驱动保留停止写入。核对厂商调用后，将 Extended Register Write 改为 Extended Register Write Long，手电与震动的配置写入开始生效。原操作码为何未生效仍未确认。震动的 `FAULT_CLR` 则是另一种情况：该命令写入后自清，应检查故障状态。此前配置中途失败，退出又仅检查「配置完成」，导致模块保持使能；`5847dd3` 从首次写入记录清理责任，退出时停止并关闭模块。实现见[震动驱动](../../hackios-xnu-kernel/xnu/files/bsd/dev/annibale_haptic.c)和[手电驱动](../../hackios-xnu-kernel/xnu/files/bsd/dev/annibale_torch.c)。

无人值守结果覆盖手电写入、读回、限时熄灭及 iOS 控制中心命令；震动覆盖配置、短时驱动及故障状态。界面按钮改变、协议完成与实际光亮或震感分别验收，后两项仍需人在设备旁确认。关闭请求也要核对是否真正发出：新建的 AVFlashlight 对象曾读到自身档位为零而没有发送关闭，随后由内核时长上限熄灭。保护不应仅依赖用户态对象保存的状态。

设备树 panic 提供了软件侧的类似经验。新增并发查询后，源码确认 `find_entry()` 使用共享游标。启动时缓存平台身份减少了热路径访问，`940e513` 再改为每次查询自己的游标，处理其他调用方的并发问题，见[设备树补丁](../../hackios-xnu-kernel/xnu/patches/69a-pexpert%25gen%25device_tree.c.patch)。缓存与可重入修订作用不同；后续多轮未复现支持已测负载下的结果。

## 4. 兼容性判断逐层验证实际入口

系统升级调查最初从部分 iPhone 镜像推断较新系统只剩 arm64e，后续检查同版本 iPad 构建，确认 iPadOS 18.7.10 仍有 arm64 缓存。应按设备、构建与镜像检查架构，版本号不足以替代这个步骤。QuartzCore 链接 OpenGLES 并保留 GLSL 文本，可以支持继续检查 OGL 路径；系统能否启动并采用该路径仍未实测。

Turnip 探针依次经历构建成功、实例创建成功但设备数为零、后续枚举被 SIGILL 终止。零设备与缺少 `HAVE_LIBDRM` 导致的枚举分支有关；源码还发现未知 `SET_PARAM` 一律成功，会使客户端启用尚未实现的 VM_BIND，`811abcb` 已限制可接受的参数。SIGILL 后提出了用户态读取 `CTR_EL0` 的假设，并准备改用 Darwin 接口获取缓存行大小；修订后的探针仍在运行，尚无填充、计算或三角形读回的成功结果。

最小探针应逐层验证实际入口：加载、枚举、创建对象、提交与结果读回。能力查询的返回值和空结果要单独解释，接口名与编译产物只覆盖前面的阶段。完整 Metal 路线与系统升级继续保留为待验证，现有 GLES 桌面作为可恢复的对照配置。

## 5. 自动化配置需要覆盖已有功能

用户在会话末段反馈音量键、电源键、电量百分比和充电显示消失。源码确认按键与电量驱动分别受 `buttons`、`battery` 控制，本轮载荷遗漏了 `buttons=1 battery=1`。生成器已补上两项，随后载荷等待验证。截止本次阅读，新的有效电量读数、状态栏及物理按压结果还未取得；充电状态原本依据电流方向推断，充电器在线状态仍有 ADSP 依赖。

这个问题应先比较上一份成功配置与本轮实际输入，再检查驱动退化。自动触摸能够完成翻页，仍未覆盖真实按键；GPU 性能报告需要同时列出已有功能的回归范围。长期运行脚本也需固定版本：会话末段队列完成处出现 Shell 语法错误，随后读取的脚本已正常，且共享目录存在同期修改。现有记录支持检查运行版本及修改归属，尚未完整复现语法错误的形成过程。
