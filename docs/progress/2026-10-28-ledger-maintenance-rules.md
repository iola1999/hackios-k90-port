# 2026-10-28 总账维护与快照文档更正决定

desktop 的维护产出记录。规则来自 lead 2026-10-28 的裁决与当天的落位实例，供后续维护者与接手会话直接沿用，同类判断不再问 lead。

## 1. 快照文档的事实错误更正

交接文档这类时点快照默认不改写、不加状态批注，完成状态由总账行承载（lead 2026-10-28 定）。区分标准看改动的性质：错误常量、错误哈希、错误格式串属事实错误，按下面的判别规则更正（inline 或更正清单），更正处附来源说明（正确值、源码位置、承载更正的分析文档）；把「待做」改成「已做」或加状态批注属状态改写，归快照规则管，不做。

实例（2026-10-28，lead 批准）：[模型切换交接文档](../plan/2026-10-28-team-handoff-model-switch.md) §2 与 §4 的「16 KiB」拷贝阈值更正为 65536 字节（源码常量 `redwoodmetal.m:2408` 的 `NOCOPY_LIMIT = 0x10000`，原错数来自 `:2405` 注释），更正的实测与推理在[读数规则 §3.6](../analysis/2026-10-28-roundc-reading-criteria.md)。这条错常量已造成实际损害：按「≤16 KiB 才拷贝」比对 roundb 的 32768 字节尺寸分布，开出「超过阈值仍被拷贝」的错误怀疑，display 与 perf 各花时间排除。lead 批准例外的理由：仍在被接手的文档里留着错常量，下一个接手的人会重复同一误判。

源码注释（`redwoodmetal.m:2405`）的同一错数已由 display 改掉并提交（`.userland.git` `e0b7b62`，仅注释、行号未变）；这类更正赶在打包之前提交，这一轮跑了什么就由提交记录说明。工作树状态检查覆盖 userland 源码，未提交时打包照常进行，改动清单进 `manifest.json` 的 `worktree_status`（2026-10-28 起这一项只记录、不拦打包）。更正的权威口径在[读数规则 §3.6](../analysis/2026-10-28-roundc-reading-criteria.md)。

判别规则（lead 2026-10-28 定，取代 desktop 早先「错误常量 vs 读数细化」的区分，desktop 的判法被否）：看更正能不能在原句内改一个值、且该段的论证结构不因它作废。能，正文 inline 更正；不能（更正会让该段论证整体作废，或要改多处互相依赖的数），正文不动，写进快照文档末尾新增的更正清单一节。更正清单加在末尾、不插开头，避免全节重编号断掉页内链接；开头的介绍文字加一句指向它。实例一（inline）：「16 KiB」→65536 字节，单值错误，同一句里就是操作值。实例二（更正清单）：SpringBoard 死亡代数——它同时错在两个方向（漏了确实死了的 91 与 166，多了没死的 267），属事实错误，但 §2 同一句里 pid 列表、「各有 15 条 `exited code -1`」「每对间隔约 10 秒」三个数互相依赖，改一个要连着改另两个，故进交接文档 §11，与 slide、共享缓存区间、pc 距离、归属作废、P1 对数、周期方向共七条。

## 2. 总账行的处理规则

- 行里会过期的计数直接去掉数字，计数以被链接文档为准：「待确认项 9 条列在 §12」写成「待回填与已定的项列在该文档 §12，条数以文档为准」（lead 批准，同类不用再问）。实例：perf 读数规则行的 §12 条数一天内 9→17→18。
- 同一事实只在一行承载：两处要落同一结论时，后到的行写「随某行承载，本行不展开」。两行要不要合成一行，按承载文档是否相同判——承载文档相同的合并，不同的分列（lead 2026-10-28 定）。实例：task-1 与 task-14 的两版内核承载文档相同（内核镜像名记录）、又是同一件事的两个阶段，由标完成的 P1 一行承载；GPU_SPEED 更正在协议与 README、更正清单行承载交接文档 §11，承载不同所以分列。被引用的文档章节正在修正中时，总账行先不写该节号，修正确认并核对后再引。实例：roundb ASCII 故障地址来源由 device 的 task-2 对齐结论行承载，perf 的补充行不展开。
- 落位前核对三项：链接的文档存在、章节号有效、行内关键常量对过源码或原始产物。实例：`NOCOPY_LIMIT = 0x10000` 对过 `redwoodmetal.m:2408` 才落「阈值 65536」的行；device task-2 行的 15 物理事件、91/166、13/15 紧邻拷贝逐项对过对齐文档。
- 成员消息引用了不存在的位置时，先三步检索确认确实不存在（当前文档、`git log --all -S` 全历史、相关规划文档），再找出处的真实构成并回报，总账不按错误引用改动。实例：「总账第 16 行性能验收判据（≥55／35 ms）」不存在，引文实际由三处合成——总账「性能验收口径」行（引用旧口径是为了声明作废）、`docs/analysis/2026-10-28-ios26-perf-gap.md` §4.1 的判据模板表、`tools/k90auto/gestures.py:26` 的 `CC_TARGET_FPS = 55`。
- 核对用的检索自身要限定范围：对 `docs/` 递归必须带 `--include` 或排除 `docs/progress/evidence/`，优先 `rg`，规则与事故记录在[运行协议 §5](../plan/k90auto-run-protocol.md) 的检索纪律条。
- 行的 commit 前缀记该行内容首次落地的提交，被链接文档后续的修订不回写前缀，增量由专门文档承载（lead 2026-10-28 定）。实例：perf 读数规则两行按 `8131f5d` 记，task-13 等后续改动提交后不更新这两个前缀。
- 同一轮里一部分新代码验证成立、另一部分零读数时，两者分开写、各带原因，不混在一句里（lead 2026-10-28 定为样板）。实例：round C 的 exec 行验证成立，bad access 四字段零读数的原因是零故障而不是打印失败，骨架 §7 把两句分开并互相引用；混写会让下一个人读成打印整体失效。
- 改数分两种对象（lead 2026-10-28 裁定）：作为结论陈述的值，改数写新口径值并加缺陷说明；快照／归档里工具输出的原样引用，不改数、行尾加注记——改它等于篡改历史记录。实例：骨架 §7 summary 表行 `crashes=7` 原文保留、加注记（7 全部来自 `ReportCrash` 名字出现次数、真实退出 0、新口径本轮 0、roundb 旧值 6 新值 30）；总账的结论陈述值零命中、无需改。
- pack 段自述字段不作配置权威（lead 2026-10-28 定）：`manifest.json` 的 pack 段整体由 `make-payload.py:97` 的 `pack = dict(pack_record)` 从上一期 pack 记录逐字复制，段里的自述字段（`round_notes`、`expected_*` 等）描述的是那条记录写下时的状态，不必等于本轮实际配置；引用时带来源限定、只作旁证，本轮配置的成立依据是 jobs 文件、日志与本轮实测写入的字段（如 `driver_sha256`）。实例两个：round C `round_notes` 第三条「多一个 framewatch 实例」，成立依据是 `rc.jobs.freeze:19` 与日志启动行，round_notes 只作旁证；`expected_driver_sha256` `31f2d6b7…` 是 roundb 期旧基线值、本轮实际 `9d66dd36…`，断言配显式更新路径的修复归 task-10。同类情况照此区分。
- 提交频率的操作性约束（用户 2026-10-28 定、lead 10-28 细化，AGENTS.md §4 现行文本为准；取代我此前记的两版）：①一次汇报对应至多一笔提交——做完一批工作、向 lead 汇报的时候提交，汇报之前不提交，提交频率由汇报频率决定，而汇报频率天然是粗的；②判据是「这批改动是不是同一次工作的产出」——同一次工作里定稿的几份文档加一处修复加它的验证是一笔，跨文件跨待办项都算一笔；③同一时刻或相邻几分钟内连续产出多笔提交就是拆得过细，自查信号：提交前先看 `git log -3 --format='%h %ci %s'`，若自己上一笔就在几分钟前且属于同一次工作，说明上一笔提交早了；④只有两段工作在不同时间完成、彼此能独立回退时才分开，唯一例外是别人正被挡住等这一处改动，那时它可以单独立即提交；⑤提交说明可以长——这一段工作做了什么、验证到什么程度、每一项的结论都写进去；压缩历史会连说明一起丢掉，阶段结论只能靠说明承载，宁可说明长也不拆笔。四个形状样例（lead 10-28 指定）：`a51a085`（device，打包闸拦下之后提交——例外条款「别人正被挡住等这一处改动」的正确用法）、`26c157b`（perf，同文件同工具同目的的两处修改一笔）、`ad1d1cd`（8 个文件、说明分五条——一段工作里定稿的几份文档合成一笔）、`62b0a5a`（round E 落账一笔）。反例：`3195eb6`／`cf2b0ef`／`dec0631`／`cf03f88` 四笔时间戳完全相同（17:02:58），是 lead「至少拆成四笔」指令的直接后果——该指令已撤销，round C／D 的总账更新应当是一笔。§4 当天改过三版（「攒到阶段结束合成一笔」→「一个阶段性结果、跨不相关待办拆多笔」→「一段一起完成的工作、同一时刻连续多笔即拆得过细」），前两版只作演变记录、以现行文本为准。因果记录：「拆笔」方向的指令当天造成两次事故——perf 的 `git reset --mixed HEAD~1` 历史改写（见下下条）与 desktop 的 17:02:58 四笔；**lead 派活时给的拆分指令要按 §4 现行文本核一遍再发**。更早的 `28ddbfd`／`83140fc`／`44fc575` 三笔按任何口径都应是一笔，不回退。
- 提交上限收紧到每个成员每个设备轮周期一笔（lead 10-28 晚定；配套的 AGENTS.md §4 与 §1 新文本当晚在工作区出现过又回退、尚未提交，仓库当前是 `6a53d9c` 版——规则内容以 lead 消息与本记录为准）：设备轮周期指从上一轮收尾到本轮收尾；代码改动与它的验证都完成时可以单独一笔；措辞清理、待更正标记、注记、指针占位不单独立提交——工作区编辑对全体成员即时可见，「让别人看到」不构成提交的理由，提交的理由只有两个：一段工作完成，或别人正被挡住等这一处改动。推论来自 lead 收回 `b1cb924`（四处 🔵 待更正标记单独一笔，正是用户抱怨的「改个进度文件就提交一次」的形状；按只加提交的原则留在历史里不改写，教训记在这里）。`c95b587`（perf-gap 措辞清理单独一笔）提交于 §4 新文本生效前，同样不回退。例外仍是两条：别人正被挡住；判据的事前登记与它要判的读数必须分属两笔提交（第五个形状样例 `8caeaa4`，perf——读数规则文档新增 round F 判据一节写在证据目录可读之前，与读数同一笔提交会让「事前」这个性质只存在于提交说明里、git 上分不出哪些判据是事前定的；它是五条规则里唯一要求拆的，拆本身就是证据；配套：该节开头明写「本节的提交时刻就是登记时刻」，读者可用 `git log` 核它早于证据目录可读的时刻）。提交说明规范（lead 同批定，AGENTS.md 文本待落）：第一句写改了哪个文件或工具、它的行为变成什么，读者只看 `git log` 就能判断要不要展开；不用只有团队内部知道的词（落账、对平、核销、判读口径、常设闸、起跑、批次、口径差写成实际动作：更新总账、核对、结案、读数规则、固定检查、开始一轮、排期、两边说法不一致），不写只存在于聊天里的编号。补记（lead 10-28 晚）：这两段约定不进 `AGENTS.md`——用户要求不改该文件，lead 已用 `git checkout HEAD -- AGENTS.md` 还原成 52 行原版；规则改写在 goal 里，维护文档时以 goal 为准。同批定的总账更新频率：`docs/plan/2026-10-23-tracking.md` 一个设备轮周期最多改一次，一项一行、只写状态变化，细节写进各条目链接的专门文档（用户点名）；round F 这一批账目等修复轮结果出来后一次改完、一笔提交，用词清理（68 处命中，lead 给了替换写法）并入同一笔。
- 历史操作前先收半成品（lead 2026-10-28 定）：任何历史操作（压缩、rebase、force push）之前先问一遍各成员手里有没有半成品文档——「攒到阶段结束」挡不住历史操作把工作区里的半成品当成定稿一起收进仓库。实例：2026-10-28 的压缩把当时的工作区收进 `297ca93`，其中 `docs/analysis/2026-10-28-panel-120hz-path.md` §5 的每帧成本表还是 perf 更正前的口径（2.34 ms 与 14.3 ms，两个值都已作废，更正后约 1.35 ms 与 15.26 ms），由 display 改。更新（10-28 晚）：display 已改出工作区新版——§5 的 2.34 ms 换成记账的约 1.35 ms（`driver` 0.104 加 `submit` 0.99..1.30）、§5.1 从两个结果分支改成 round E 的结果（填分支二、删分支一，含三组间隔的节拍倍数 0.98／2.04／4.99 表与读数边界：91 帧、8 处断裂、没有稳态）、§1 顺序改成先量 CA 8.24 ms 降到 8.33 以下再谈刷新率、TE 只读采样器方案插入 §7（采集条件与未验证顺延 §8／§9）、selector 74 与 78 改成与 task-24 文档 §5／§6 互引；待提交。**它落地前，引每帧成本用 perf 的 `docs/analysis/2026-10-28-roundb-draw-stage-breakdown.md` §8.5 与 §8.7，HEAD 里那份（`297ca93` 扫进去的半成品）不要用**。
