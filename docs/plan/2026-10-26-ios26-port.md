# iOS 26 移植计划（2026-10-26）

目标：K90 运行 iOS 26.6.2（`23G90`）用户态，身份为 iPhone 17（`iPhone18,3`，`V57AP`），内核基于 `xnu-12377.121.6`。用户决定见[路线图](2026-10-26-roadmap.md)第 3 节，接口差异见[内核接口差异分析](../analysis/2026-10-26-ios26-27-kernel-abi.md)。第一个里程碑是软件渲染进入 SpringBoard；GPU 路线（`AccelServer` 替换 `renderer` 后用 GLES，或 Metal 驱动）等真机结果再定。iOS 16.5 配置保持可启动，作为对照。

当前实测（10-27）：K90 已进入 iOS 26 软件桌面，全面屏上滑、翻页和控制中心通过自动检查；Metal 在 A830 通过计算、绘制与内容读回，IOSurface 共享内容、属性及提前释放通过，原生 CARenderer 在软件与 A830 后端均通过两帧像素检查，同步和桌面接入继续验证。原生 screen class 36、402×874 点和顶部 62 点安全区已在 K90 通过四项自动手势检查；独立 SpringBoard Metal 注册后仍有 MPS 与 Siri sampler 缺项，完整 GPU 桌面尚待验证。版本、参数、性能与剩余范围见[真机后续记录](../progress/2026-10-27-ios26-k90.md)。

## 1. 可能调整的决策

| 决策 | 当前选择 | 理由 | 何时重新评估 |
|---|---|---|---|
| 内核基线 | `xnu-12377.121.6`（macOS 26.5 发布版本），内核报告 Darwin `25.6.0` | 已公开源码中最新；iOS 26.6.2 需要的系统调用、trap、MIG 全部覆盖 | 苹果公开 27 系列内核源码后 |
| 构建环境 | macOS 本机 Xcode（Apple clang 21），脚本在内核仓库 `xnu26/` | Apple clang 带 XNU 类型 builtin 与 arm64e 支持；本机 arm64 构建，不经 Rosetta | 需要在 Linux 容器复现时 |
| arm64e 用户态 | 内核仍为 arm64，不启用 PAC 密钥；`cpu_subtype` 报告 arm64e 以接受 arm64e 程序 | 关闭密钥后 PAC／AUT 指令不改变指针，共享缓存的认证指针由内核按普通指针重定位 | 真机出现指针认证相关崩溃时 |
| 小核调度 | 12377 移植中去掉 `small_cores`／`sched_slow_secondaries` 配对，所有核心同等调度 | 12377 的 arm64 配置不带 SMT 调度器，原实现依赖它；K90 的 8 个核心都是 Oryon | 调度或功耗结果需要区分核心时 |
| persona 与身份版本 | 沿用 16.5 移植的放宽：不检查 persona 授权和存在性、不检查非 root 调用方请求 uid／gid 0；xpcproxy 变为服务时保留身份版本 | 与 16.5 上 Sileo、RunningBoard 的修复保持一致 | iOS 26 上出现相关问题时 |
| BCM2837 板级保护 | 恢复 8796 中被 12377 删除的两处：跳过 trust cache 初始化、跳过 IORTC 等待 | 本移植没有 trust cache，也没有 RTC 驱动 | 实现 trust cache 后 |
| 内核堆虚拟地址 | zone map 虚拟地址从 24 GB 减到 16 GB；未设置 `vm_compression_limit` 时压缩池上限 4 GB | 没有 KTRR 时内核堆位于物理内存映射和 CPU 窗口之间，约为 43 GB 减去内存窗口大小；11 GB 窗口下原配置超出 7 GB，`kmem_range_init` panic | 内存窗口超过 13 GB，或压缩池耗尽触发 jetsam 时 |
| 写合并映射 | `VM_WIMG_WCOMB` 与早期块映射在 DRAM 之外也使用 Normal non-cacheable，与 8796 相同 | 12377 对 DRAM 之外的写合并映射改用 Device-GRE；panic 区与帧缓冲在内核内存窗口之外，非对齐访问在 Device 内存上产生对齐异常 | 帧缓冲或 GPU 内存移入内核窗口后 |
| 启动模式与任务来源 | 根设备用 `rootdev=md0` 指定；launchd 的任务来自 `/System/Library/xpc/launchd.plist`，由 `userland/mkcache.py` 用我们的任务表生成，不签名，boot-arg `launchd_unsecure_cache=1` 让 `launchd_cache_loader` 跳过签名校验 | kern.bootargs 含 `rd=md0` 时 iOS 26 的 launchd 按恢复环境启动，跳过 usermanagerd 等启动任务；正常启动时只读这份缓存，不扫描 LaunchDaemons 目录 | 需要 Apple 签名的缓存，或该 boot-arg 失效时 |
| 设备身份 | loader 的 payload 条目 `identity`（`mkpayload.py --identity v57`）选择 iPhone 17：设备树属性取自 IPSW 的 `DeviceTree.v57ap`，chip-id 0x8150、board-id 0x08 取自 BuildManifest；`platform-name` 按芯片写成 `t8150` | 固件的设备树里 `platform-name` 为空，推断由 iBoot 填写；`t8150` 是按 chip-id 推定的名字 | 出现按平台名查找资源失败时 |

## 2. 源码组织

- `xnu26/apply.sh` 取 `xnu-12377.121.6`，应用 `xnu26/patches/series`，再复制 `xnu/files/`（与 8796 共用，`xnu26/files.skip` 列出的除外）和 `xnu26/files/`（12377 专用版本）。
- `xnu26/export.sh` 把工作树导出回这三处：修改的苹果文件按文件导出补丁；新文件与 `xnu/files/` 相同则不重复保存。
- `xnu26/deps-macos.sh` 准备依赖：AvailabilityVersions-157.2、libdispatch-1542.100.32、libpthread-539.100.4（macOS 26.5 的组件版本），带 `usr/local` 的 iPhoneOS SDK 副本，`libfirehose_kernel.a` 与 `libpthread_kext.a`。产物在 Git 忽略的 `xnu-deps/26/`。
- `xnu26/build-macos.sh` 构建内核；`xnu26/xcrun` 让 make 能按路径使用上面的 SDK 副本。

## 3. 补丁迁移结果

8796 的 78 个补丁在 12377 上三方合并：42 个直接应用，32 个文件共 72 处冲突，3 个补丁的目标文件已删除。处理方式：

- 13 个补丁只把 `uio` 栈缓冲区改为 8 字节对齐，12377 已用 `UIO_STACKBUF` 实现同样的修改，丢弃。
- 3 个补丁（61～63）只服务于小核配对，按第 1 节丢弃；`machine_routines.c` 中对应代码同时去掉。
- `bsd/conf/files`、`osfmk/conf/files.arm64`、`makedefs/MakeInc.def`、`board_config.h` 按 12377 的新结构重写；`dk_memdev_info_t` 已移到 `disk_private.h`，`mi_base` 的修改随之移动。
- `MASTER.arm64.bcm2837` 与 `BCM2837.h` 在 12377 中已删除，改为 `xnu26/files/` 中的新版本。配置以 12377 的 `MASTER.arm64.iPhoneOS` 为基础，去掉需要苹果私有库或硬件的选项（签名强制、img4、PGO、rosetta、CPU 计数器、`sched_hygiene_debug`、内核转储加密），加入 `nos_arm_pmap`、`nos_arm_asm`、`mockfs`、`ramfs`、`apfs`、`no_kextd`。
- 12377 把 VMAPPLE 的串口改名为 `PL011_UART`，`BCM2837.h` 同步改名。
- `kern_exec.c` 的 persona 与身份版本、`kern_memorystatus` 的内存阈值按 12377 的新函数结构重写，行为与 16.5 移植相同。
- lldbmacros 的补丁目标已删除，丢弃。

## 4. 后续步骤

1. 编译通过：修正共用驱动在 12377 内核接口上的编译错误，链接通过。
2. QEMU 冒烟测试：12377 内核加 iOS 16.5 用户态，确认内核基本功能，再换 iOS 26 用户态。
3. iOS 26 系统镜像：从已解密的 SystemOS 生成根文件系统；arm64e 程序、dyld 共享缓存、launchd 任务表（`userland/mkjobs.py`）、iPhone 17 的 MobileGestalt。
4. 用户态替代驱动（`MiniIOSurface`、`MiniIOMobileFramebuffer`、`MiniAppleKeyStore`、MiniAMFI 等）按 iOS 26 的调用方式核对和修改。
5. 真机启动到 SpringBoard（软件渲染），记录帧率与内存。
6. 评估 GPU 路线与 iOS 27 差异。

## 5. 进度

- 2026-10-26：补丁迁移完成，`exporthdrs`、`installhdrs` 与依赖库构建通过；完整内核构建进行中。
- 2026-10-26：内核链接通过，在 QEMU 中挂载根文件系统并启动 iOS 16.5 的 launchd。launchd 报告 `could not set up inheritance port` 后退出；iOS 16.5 用户态在 12377 内核上只作冒烟测试，不继续处理。
- 2026-10-26：loader 的 payload 增加 `memsize` 条目（`mkpayload.py --memsize`），内存窗口可以超过 6 GB。11 GB 窗口先在 `kmem_range_init` panic，按第 1 节调整内核堆虚拟地址后通过：data／ptr 区各 3.4 GB，压缩池 4.6 GB。panic 时 `SavePanicInfo` 写 panic 区出现对齐异常并连续嵌套 panic，按第 1 节恢复写合并映射后只剩一次 panic。
- 2026-10-26：`ios26/fetch.sh` 在 macOS 上从 IPSW 的三个磁盘镜像取出系统文件，沿用 iOS 16.5 的选择规则：根文件系统 60871 个文件 5.7 GB，dyld 共享缓存（arm64e，不含 `.symbols`）4.9 GB。`userland/build.sh` 用 `IOS=../ios26` 生成 `root26.apfs` 与 `system26.apfs`，与 16.5 的镜像分开存放。
- 2026-10-26：iOS 26 的 arm64e 用户态在 QEMU 中运行。QEMU CPU 改用 `neoverse-n2`（`max` 带 LVA，内核在 `vm_sanitize` 的地址范围断言处 panic）。
  - 内核侧修改：
    - 共享缓存 slide 信息 v3／v5 的认证指针在没有指针认证的内核上按普通指针写回。
    - dyld pager 在 BCM2837 上启用 arm64e 修正格式，跳过签名。
    - 控制台输出在 `disableConsoleOutput` 判断之前写入 loader 日志。
    - devfs 创建 `/dev/console` 时权限为 0666（12377 拒绝对它 chmod，logd 与 distnoted 打开失败）。
    - 用户态 `brk #0xB000`～`#0xBFFF` 引起的异常也记录调用栈。
    - `systrace=1` 时 exec 失败路径打印原因。
  - 用户态侧：iOS 26 的 launchd 只信任路径在 `/System/Library` 下的任务，系统镜像的 `/System/Library/LaunchDaemons` 改为空目录，由 stage0 把 `/redwood/LaunchDaemons` 绑定上去。
  - 结果：launchd 与各守护进程启动，恢复环境下 backboardd 在 `user/501` 域中启动后停在 persona 查找。
- 2026-10-26：改为正常启动。
  - 根设备：loader、`bsd_init.c` 与 `IOKitBSDInit.cpp` 接受 `rootdev=md0` 作为根设备参数。
  - 缓存：`launchd_cache_loader` 要校验 `launchd.plist` 的签名，改用第 1 节的无签名缓存。
  - 签名：launchd 正常启动时遇到非平台二进制会 panic，`build.sh` 给小镜像里没有签名的程序加 ad hoc 签名（内核把 ad hoc 签名的程序当作平台二进制）。
  - persona：usermanagerd 缺少 `/private/var/keybags/persona.kb` 时以 `Daemon failed to load persona manifest.` 退出，`build.sh` 写入一份没有用户的第 1 版清单。
  - loader 用 iPhone 17 身份。
  - QEMU 180 秒结果：keybag、usermanagerd、`launchd_cache_loader` 等启动任务全部执行，usermanagerd 不再退出；lsd 反复中止（18 次，调用栈见交接文档）；日志中没有 backboardd 与 SpringBoard 的记录，屏幕全黑。
  - 正常启动时 launchd 自身的日志没有输出到控制台，这两个进程是否启动待确认。

- 2026-10-26 接续：确认 user/501、SpringBoard 与 backboardd 已启动；修复 AMFI 开发日志权限及无 Sandbox 标签服务的 XPC check-in；POSIX 用户容器身份使 lsd 查询通过，关闭 Medina 后开始提交帧。swap 与 IOSurface 新布局已适配；AMFI `0x66` 适配后显示启动标志和进度条，后续桌面待验；详见[QEMU 记录](../progress/2026-10-26-ios26-qemu.md)。

- 2026-10-26 后续：ramfs 支持 `RENAME_SWAP` 后，原生 UserManagement 清单及容器身份查询通过，临时 POSIX 身份替换已移除；SystemStatus 加入默认任务，23G90 本地启动状态适配与独立输入服务使 QEMU 经 Home 按键进入 SpringBoard。图标、组件、标签和壁纸显示仍需修复，交互继续验证，见[QEMU 记录](../progress/2026-10-26-ios26-qemu.md)。
