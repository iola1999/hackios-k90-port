# fixguard7 预登记：载荷重跑与计数分母（2026-10-29）

## 1. 这次要回答什么

fixguard5 与 fixguard6 的差异只有 AIR 库，结果从 103 次 bad access、42 张全黑、14 个 backboardd 世代翻成 0 次、43 张 home screen、一次没死。读数无法区分「那条 UAF 与分配状态相关」与「插桩改变了时序」。同时 `rwa shadow:` 零行让「守卫是否被执行到」悬空。

两件事按顺序答：先答崩溃是否可复现（改代码前的单次重跑），再答计数分母（插桩第二版，重跑之后再动）。结论范围在数据到手前写下，见第 3 节。

## 2. fixguard7：同一载荷重跑一次

同一载荷重跑不改库、不改包，代价最小的一次判别。

不重打包、不重建、不改任何二进制。重放 fixguard6 的 handoff 载荷（AIR `cbf1689c…`、守卫＋计数），`epoch` 与命令行都与 fixguard6 一致，唯一变量是时间与进程内的分配状态。截图默认关掉，日志采集优先。

| 结果 | 结论 | 下一步 |
| --- | --- | --- |
| 复现 `…9c0`／`x2 = 0xc0` 形态，backboardd 至少死一次 | 崩溃在带插桩的库上也可达，fixguard6 的健康是偶发；单轮结果不可判 | 提密度后按多轮估计发生率 |
| 仍健康、bad access 0 | 崩溃不是该载荷的稳定性质；fixguard5 的 103 次不是这条载荷的固定行为 | 重放守卫版载荷（`1be6ebf7…`）看崩溃是否复发，再决定归因方向 |

「同一形态」的判据沿用 fixguard5：`redwood: backboardd bad access` 行的 `pc` 仍是 `…9c0`、`x2` 仍是 `0xc0`、故障地址仍是反向域名字符串字节。

这一步只能分「稳定／不稳定」，给不出发生率。守卫版载荷 `1be6ebf7…` 的重放留到下一步，它回答「崩溃是否与两份 AIR 产物相关」。

## 3. 结论范围

- 单次重跑只能分「稳定复现／不稳定」，不能给发生率。要给发生率，每份载荷至少 5 轮，且轮次之间清空日志环。
- 重跑健康不能推出「守卫有效」：守卫在两份产物里都在，fixguard5 带着守卫仍然 103 次。
- 重跑复发不能推出「插桩导致崩溃」：只说明该载荷的崩溃可达。
- 本计划得到的任何结论都只覆盖 `x2 = 0xc0` 这一形态与 `backboardd`／`SpringBoard` 这两个进程。

## 4. 插桩第二版改动（fixguard7 跑完再动）

改三处，库只多一个版本，守卫条件与返回值不动：

| 位置 | 改动 | 目的 |
| --- | --- | --- |
| `fd_try_shadow_resource` 入口 | 首次调用打一行（含 `pid`），之后每 1024 次调用打一行 | 进程不退出也能拿到 `calls`／`is_shared` 分母 |
| 守卫拒绝处 | 保留首次拒绝行，改成带 `pid` | 区分进程 |
| `util_copy_rect` | 门槛从 `width == 0xc0` 改成「前 8 次任意 width」，带 `pid`、src、dst、len 与四个计数 | 覆盖 355／38 两种行宽 |

`atexit` 收尾行保留，它只在正常退出时出现，不承担分母。

健康轮次是这一版的判读前提：上一版三个打印点全挂在退出与首次拒绝／首次交换上，fixguard6 恰好两个 GPU 进程都没退出，于是零行。这一版的首调行与每 1024 次汇总行都在进程存活期间输出，健康轮次也有分母。

## 5. 打点密度与环容量

单进程上界 24 行，算法如下：

| 打点 | 条数 | 说明 |
| --- | --- | --- |
| 首调行 | 1 | 每次进程启动一次 |
| 每 1024 次调用汇总行 | `min(15, calls // 1024)` | 封顶 15 行，`calls` 上万也不再增长 |
| 行拷贝行 | 8 | 前 8 次任意 width |
| `atexit` 收尾行 | 1 | 只在正常退出时出现 |

按 3 个 GPU 进程（backboardd、SpringBoard、一个扩展）计，全轮上界 72 行，占 7,347 行日志环的 1%。即使 3 个进程各自跑到 15 行汇总上限，也只占 3%。

日志环覆盖是判读前提：截图改为按需后，环里主要装内核行与 `rwa` 行。72 行的插桩预算按每轮清理一次环来算，若一轮里进程世代数超过 20（fixguard5 的 backboardd 就有 14 个世代），预算按世代数线性放大到 480 行，仍占 6.5%。

## 6. 预登记读数表

第一问，`fd_try_shadow_resource` 是否被调用：

| 读数 | 结论 | 下一步 |
| --- | --- | --- |
| 无首调行 | 该进程里从未调用 | roundb 的交换归因作废，转 AIR 侧 buffer 生命周期 |
| 有首调行、`is_shared = 0` | 进入过但没有导入资源 | 守卫与这条 UAF 无关 |
| `is_shared > 0` 且 `refused = is_shared` | 每次导入都被拒 | 守卫在跑；崩溃若仍在，说明交换不是唯一来源 |

第二问，行拷贝实参：

| 读数 | 结论 |
| --- | --- |
| 有 `rwa row:` 行、同进程有 bad access、`src` 与 bad access 的 `x1` 相同 | 命中故障行，可读 src／dst／len 与当时计数 |
| 有 `rwa row:` 行、同进程无 bad access | 打印的不是故障行，只作背景 |
| 无 `rwa row:` 行而有 bad access | 行宽之外还有第三种写法，下一轮按 `pc` 反查调用者 |

## 7. 未做与风险

首次调用行只能证明入口被执行，不能证明守卫前后的行为；`is_shared` 的取值依赖 `rsc->b.is_shared`，导入路径若在 26 用户态不走 `fd_resource_from_handle`，该计数会一直是 0。

G1／G2 重放沿用原载荷，`epoch` 与命令行不变，因此两轮之间唯一的差异是时间与分配状态。若 device 重放时重新打包，`epoch` 会变，载荷哈希随之变化，判别力下降。
