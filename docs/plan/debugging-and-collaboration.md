# HackiOS 项目排查与协作手册

本文记录 REDMI K90（SM8750，`annibale`）移植中可复用的思考方法、系统原理和协作约束。更新日期：2026-10-26。当前命令见[真机调试手册](device-test-playbook.md)，阶段安排见[总账](2026-10-23-tracking.md)，方法的实际来源见[启动案例](../analysis/2026-10-23-boot-debugging-sop.md)、[桌面交互案例](../analysis/2026-10-24-interactive-runtime.md)、[A830 命令执行案例](../analysis/2026-10-24-a830-command-startup.md)和[GPU 桌面验证案例](../analysis/2026-10-26-gpu-validation-lessons.md)。本次完整会话阅读范围见 GPU 桌面验证案例第 6 节。

已在代码或工具链中修复的问题只保留必要背景。本文重点回答：下一步检查什么、这个检查能区分哪些原因、结果支持多大范围的结论。

## 1. 先定义问题和完成条件

接手先读用户最近的完整反馈，确认目标、已授权操作、数据保护要求和已经尝试过的恢复动作。摘要用于定位内容；重要判断要回到实际命令、输出和对应源码。多个会话共享目录，设备状态、构建输出和未提交修改都可能已经变化。

把用户看到的现象转换成可检查的状态。例如「没有通知栏」对应 SystemUI 进程、窗口和崩溃记录；「手机没反应」需要区分 USB 枚举、协议响应、内核运行和面板显示。现象相似的故障可能发生在不同层，先确定哪层失去预期行为。

完成条件应直接对应目标。编译成功验证构建；检查点返回验证该段执行与返回；系统盘上传验证传输；挂载日志验证文件系统阶段；SpringBoard 进程、framebuffer 与用户实际操作共同验证界面。QEMU 与真机分别记录，某一层通过后继续验收依赖它的下一层。

阶段通过后继续按功能验收，分别记录显示、合成、输入和响应时间。画面停住先查系统是否仍在执行，再看该功能是否更新；确认有延迟响应后，调查转向耗时，并保留已经通过的输入结果。用户反馈修正了观察范围，就更新同一条结论。

用户的视频、截图和口头反馈先关联具体运行，确认是否为最新一轮、是否加载壁纸、采用哪个 renderer。自动操作覆盖的功能也写清楚：合成触摸可以验证界面流程，物理按键还需驱动初始化与真实按压检查。改变启动配置后，把此前已可用的按键、电量和触摸列入回归项；单项性能通过仍可能伴随其他功能退化。

## 2. 用能区分原因的实验推进

每轮先写出竞争解释，并为每项写出可检查的预测。选择检查的依据是不同原因能否产生不同结果。例如「没有内核日志」可能来自内核尚未执行、输出分支未被采集、缓冲被替换或主机读取失败；直接重启后，这几种情况都可能再次出现，检查日志写入点与缓冲状态能区分其中一部分。某项检查无论得到什么结果都不会改变下一步，就先重新明确要回答的问题。

多项检查都能区分同一组解释，就优先选择副作用较少、观察范围较明确且失败后可恢复的一项。搜索、构建和真机试验都有成本，范围由当前问题决定；定向读取已有状态能回答的问题，先读取状态。需要修改硬件配置才能区分原因，就先明确实际会改变哪个条件及如何恢复。

新结果改变了已知执行阶段，就重新排列假设。本次故障已定位为特权取指权限错误后，调查先验证页权限，暂缓缺少对应现象的时钟调整。结果与所有预期都不符，就检查实验条件和原来的解释是否有遗漏；继续逐项修改已知差异，可能始终没有检验真正的原因。

缓冲创建调查可以说明如何选择检查。控制中心卡顿，新建 GPU 缓冲较慢，最初怀疑等待 GPU 锁。释放队列等待期间的锁后，新建耗时仍未明显下降；接下来记录总耗时，并单独计时内存分配与等锁。这两项若占大部分时间，就继续查对应调用；若只占少部分，就沿剩余代码检查 GPU 映射。该轮记录可以写成：

```text
现象：释放队列等待期间的锁后，创建缓冲仍慢。
待区分：分配内存慢、等待锁久、建立 GPU 映射慢。
检查：把创建总耗时与内存分配、等锁耗时并列记录，先保留现有分配和同步行为。
判断依据：分配和等锁只占少部分，尚不足以解释创建总耗时；剩余代码还需建立 GPU 映射。
下一步：检查映射函数内部的地址查找和页表发布，再分别计时、修改和复测。
后续结果：查找空闲地址和发布页表的处理范围缩小后，缓冲创建耗时下降。
边界：时间缩短后，还需检查映射正确性、显示异常及失败后的资源保留。
```

类似调查适用于「某个函数很慢，但函数里既分配资源又等待其他任务」的问题。总耗时只能确定要继续拆查哪个函数；分段计时才能决定先改分配、锁还是映射。该轮数字及剩余限制见[桌面验证案例](../analysis/2026-10-26-gpu-validation-lessons.md#2-沿每帧处理过程寻找耗时并重新评估旧结论)。

优先改变一个影响执行的条件。修改多个条件后取得成功，只确认该组合可用；各项修改的因果关系需要另做对照。冷重启与复用继承状态也是实验条件，和代码、固件及参数一起记录。

修正了一个有来源的实现差异后，分别记录「差异已修正」和「原故障是否改变」。结果没有变化，先确认修改已进入运行产物并改变了预期状态，再评价原因判断。实际状态未改变，就重新检查实验输入；状态已改变而现象仍在，则该项修订尚不足以消除故障，需要重新评估其余解释。实现修订是否必要，继续按接口、调用关系和资源约束判断。

蓝色色块调查最初根据条带尺寸怀疑 CPU 缓存或纹理压缩，这些解释都能符合形状。用户看到色块中出现电池图标后，检查方向才更明确：电池原本画在屏幕上方，错误位置却读到了它的内容，因此继续查不同画面分块之间的数据复用。核对已有 framebuffer fetch 补丁，发现读取旧内容前遗漏了新一代 GPU 的一层缓存失效。遇到画面错误，除了记录颜色和尺寸，还要看能否辨认出错误内容来自哪里；能找到来源，就能继续追踪哪次写入和哪次读取之间缺少处理。

关闭纹理压缩的一轮没有出现闪烁，但那轮也没有出现壁纸。继续看日志，GPU 初始化提前失败，实际回退到了软件绘制；这一轮尚未运行原来出现闪烁的硬件场景。下一次比较类似图形开关，先确认初始化通过、实际 renderer 正确、壁纸已经加载，再观察色块。缺少其中一项，就先处理这项缺失；条件成立后的未复现结果也只覆盖所测时长与场景。具体记录见[桌面验证案例](../analysis/2026-10-26-gpu-validation-lessons.md#1-对照成立前先检查输入与触发场景)。

故障总在某项操作附近出现，先区分经过时间与新增调用的影响。保留前面的配置，暂不执行可疑操作，在覆盖原故障观察窗口的时间内检查状态，再恢复该操作做对照。这样可以减少「此前配置延迟出错」与「新增操作开始处理后出错」之间的不确定性。本次 GPU 完成配置后暂不发布 RAW，十秒内持续可读，调查因此优先转向发布后才发生的处理；依赖 RAW 才会暴露的电源、映射或固件前提仍需检查。结果只覆盖已测时长和资源状态。

关键配置未知但仍有可独立验证的部分，先找出所有候选配置共同支持的条件，限定实验范围和退出方式。候选表来自其他板型，仍需记录适用限制；取得本机运行设备树后，重新核对芯片 revision、SKU 和工作点。本次参考表曾提供 125 MHz，本机各频率档组最低为 160 MHz，旧请求获 ACK 只覆盖该消息应答。共同条件必须有来源；缺少这种条件就先补充资料，依赖继承状态的试验在独立初始化验证前继续保留限制。

最后一条日志只确认该输出已经执行。可疑调用前后的成对标记能进一步划分范围；高频中断中的标记要限制次数。若两条完成标记都出现，后续调查转向其后的执行阶段和共享资源。诊断输出也会改变时序、锁行为和日志量，确认原因后清理临时诊断，或保留明确开关。

异步系统的实际生效时刻要单独确认。发布队列索引后，对方可能已经读取命令，随后暂停无法隔离下一条通知操作。最小实验也需要保留所调查的初始化前提：过早发送 NOP，可能只验证了尚未就绪的入口。精简实验先删除无关条件，再核对剩余输入能否触发目标行为；发布时序与首次命令的实际限制见[A830 案例](../analysis/2026-10-24-a830-command-startup.md#8-cpu-映射越界与-raw-自动复位)。

测试还应覆盖错误后的下一步。协议拒绝非法输入后，继续发送有效请求，确认状态已经恢复。本次空上传修复的有效验收是「预期失败 → 下一条查询成功 → 后续正常上传成功」。

能从真机问题中提取解析、计算或内存操作，就先用实际函数构造最小测试。用独立的格式定义和真实输入确定预期，覆盖单位、边界、重叠及失败后的状态。涉及地址映射或硬件写入，模型还需覆盖非连续物理页、写入未生效等条件。用旧实现或故意注入的错误检查测试能否发现问题。主机测试通过后，再到真机验证模型未覆盖的响应与时序。

测试的配置必须来自生产声明，预期再与独立的协议、设备树或架构定义核对；测试自行提供一个正确常量，会漏掉生产配置的错误。本次 GPU 模型自行映射了较大的寄存器窗口，直至读取生产声明并对照厂商设备树，才覆盖实际越界问题。

测试失败也要检查预期和模型的来源。本次 secure context 的 FSR 含翻译格式字段，要求整个寄存器为零会误拒；核对字段后改查有效故障位，并分别验证格式字段可通过、每个故障位仍会停止。修正页权限后，测试的常量断言与软件页表遍历仍写死旧属性；先按架构规则确认新权限，再同步测试中的相关假设。资源保护测试还应检查真实副作用和调用方能否继续；分别删除保护分支后测试必须发现错误，同时用正常退出用例确认测试没有跳过全部清理。

性能实验先确定正常任务与诊断开关，再固定输入做对照。参数含义检查实际解析，指标核对计时起止点、单位、样本数和阶段。经过时间可能包含调度等待，启动期统计不能直接推广到稳定运行；清理负载后仍有卡顿，继续比较各执行阶段的耗时。

组合进程 CPU 时间、具体调用耗时和线程采样，可以区分繁忙计算、等待及后续提交。本次三种检查共同指向软件绘制。解释前先确认符号与运行产物一致，并检查采样机制：最近保存的用户 PC 受进入内核的时机影响，样本分布不能直接换算成时间占比；不同窗口的耗时也不能相加为完整延迟。

性能指标先对应用户动作和完成条件。用户关心一次手势是否流畅，就分别测首帧等待、动画内帧间隔与长帧，整轮平均值会混入静止期。随后沿同一次操作追踪计算、排队与等待，找到哪段时间推迟了完成；整体忙碌比例较低的部件，仍可能让关键步骤等待。经过时间要与实际执行时间分别解释，具体帧时间的统计边界见[桌面验证案例](../analysis/2026-10-26-gpu-validation-lessons.md#2-沿每帧处理过程寻找耗时并重新评估旧结论)。

一处耗时缩短后，重新测量剩余部分，再决定是否继续优化同一处。本次缩放、分配和提交先后成为调查重点，早先的主要耗时已经变化；增加并行数量或频率的收益也随之改变。收益不足就保留原配置，并记录测试范围。对照输入或诊断开关有差异，就缩小结论范围，必要时重新运行。

## 3. 沿实际使用的数据追踪源码与产物

本项目存在多个独立状态：

| 状态 | 为什么需要单独确认 |
|---|---|
| 顶层仓库与两个 submodule | 父仓只记录子模块 commit，子模块未提交内容需要单独检查 |
| kernel 树与 `.userland.git` overlay | 共用文件目录，分别管理 Git 状态；overlay 使用 `common/ugit` |
| `xnu/files/`、`xnu/patches/` 与展开树 | 仓库来源和实际编译输入可能不同；`xnu/apply.sh` 不会更新已有展开树 |
| 宿主与 `kbuild` 的 `/work/repo` | 容器使用持久卷 checkout，宿主 `/src:ro` 更新后仍需同步对应输入 |
| 编译结果、打包输入与设备 RAM | 文件构建完成后，还要核对选择、打包、上传和本轮实际使用情况 |

复用构建缓存前，可从固定上游基线在独立目录重新应用选定提交的完整补丁，再按文件集合和内容比较实际编译树，处理新增、删除及内容差异。只同步几个已知改动文件会漏掉更早的未同步内容；本次先完成整树比对，再更新差异文件并复用编译缓存。该检查确认源码输入，链接、打包与设备选择继续分别核对。

按「源码 → 展开树 → 编译结果 → payload → 设备日志」追踪实际输入。记录必要的路径、SHA-256、启动参数和版本，避免仅靠可重复使用的文件名。`xl`／QEMU 的本地内核优先级、phone 与默认 loader 的区别、最终 APFS 是否含有所需文件，都属于输入选择问题。

把启动参数也纳入功能输入。此前可用的功能消失，先比较上一份成功配置与本轮最终 cmdline、根盘和驱动启用分支。本次按键及电量缺失直接对应 `buttons=1 battery=1` 遗漏；生成器修正后，还需本轮初始化日志、有效读数与用户按压结果验收。仅核对源码没有变化，覆盖不了打包与启用条件。

生成器的计数与实际输出分别检查。循环变量被复用可能造成覆盖，计数继续增长，文件集合却不完整；本次按需服务生成器因此缺少 PosterBoard 配置。检查输出文件名、内容中的标识、服务属性和最终镜像；最小回归用多个不同服务及配置分支检验这种覆盖。启动任务清理同样追踪源文件、overlay、打包目录和运行镜像，日志缺少字符串不足以单独确认清理完成。

跨模块配置按生产者、格式、消费者逐段核对，明确单位、长度、对齐、字节序和实际执行分支。同名的「页」「长度」「大小」也可能有不同单位：分配页与设备映射页、字节与协议字数应分别定义，只在明确位置转换。测试覆盖不连续内存和跨边界输入，防止单一环境掩盖假设。本次 SMMU 与 HFI 的差异都需要这种检查。

布局或起点变化后，同时重查原来的内存前提：队列开始跨页，原来仅覆盖单页的 CPU 映射就可能不足。按协议需要选择连续分配或完整映射，修订范围限定在需要该前提的缓冲；测试覆盖跨页、环回和不同页大小。

资料冲突先核对适用的芯片、板型、版本和实际执行路径。本机启动日志可确认已加载的固件系列，厂商驱动可说明配套参数；相近型号的编号只能提供待验证线索。修改选型后同步检查派生出的内存大小、寄存器布局、固件协议和打包输入。文件名相同仍需核对二进制版本，已有测试成功也不能自动证明输入选型正确。

芯片 revision、驱动 catalog 和固件文件名分别确认；两个 revision 共用固件，仍可能要求不同的启动标识。本次本机 GMU、SQE、AQE 哈希与实验输入一致，zap 文件不同；仅把前述三个文件的版本差异移出优先检查，zap 的签名接受情况继续单独验证。

公开源码仍无法解释本机行为，先提出一个具体问题，再决定是否检查实际加载的二进制。核对设备与主机文件哈希，利用符号定向查看相关布局、调用顺序和条件分支，可以区分参考版本差异与当前实现遗漏。本次用户补充 idalib 可用后，调查用本机模块核对 HFI 和启动准备，发现了布局与资源准备缺项。反编译结论只覆盖该二进制及已检查路径，动态配置和硬件响应仍需实测；无依据的其他差异继续保留为待验证，逐项照搬会增加实验变量和失败路径。

逆向闭源二进制用宿主机上的 idalib MCP（IDA 无头接口，提供反汇编、反编译、xref、符号查询）。两条使用约束：对大文件建实例不开启自动分析，`idb_open` 传 `run_auto_analysis: false`，必要时加 `build_caches: false`，改用针对具体地址的查询（`disasm`／`decompile`／`xrefs_to`／`get_bytes`）——iOS 26 的 dyld 共享缓存本地有 85 个文件、4.9 GB（最大单文件 235 MB），全量自动分析的内存与时间代价与本机的 256 GiB 内存不成比例，而绝大多数问题只需要几个具体地址；用完 `idb_close` 且 `save` 传 false，传 true 会在被分析文件旁边写 `.i64`，脏掉 `ios26/rootfs` 或共享缓存目录。

哪些问题非走共享缓存不可由一条事实决定：`libsystem_platform.dylib`、`QuartzCore`、`CoreAnimation`、`BackBoardServices`、`FrontBoardServices`、`Metal` 在 `ios26/rootfs` 下都没有磁盘 Mach-O（framework 目录里只有 plist／loctable／png），代码全在共享缓存 `hackios-xnu-kernel/ios26/23G90__iPhone18,3/` 里，任何要看这些库实现的问题都绕不开共享缓存。`tools/symbolize.py` 走的是我们自己 dylib 的符号表，这个场景用不上。

产物哈希的语义是单向的：产物哈希相同可以推出源相同，产物哈希不同推不出源不同。实测记录在 `hackios-xnu-kernel/tools/mk-mesa.sh:32-37`（容器 theos 线，10 月 20 日测）：同一棵源树两次构建，产物字节数完全相同，但库的 14,855,048 字节里有 9,132,774 字节不同、`air_run` 的 9,789,824 字节里有 4,171,752 字节不同，6 个具名 text 符号 5 个换地址，注释结论是「do not compare one of its outputs with another by hash」，布局移动的原因未查明。这条规则只适用于 Mesa 系产物：同一注释记录 userland 程序逐字节可复现（「the userland programs reproduce exactly」），驱动与探针不在此列。userland 程序构建可复现已在容器 clang 18 路径（`build.sh`）上实测——display task-7 的两次容器运行产出的 `obj/input26-service` 逐字节相同（都是 `3bc70a3fa619ff2c`，54,848 字节、`cpusubtype=0x2`、`sdk 26.0`），是支持那句注释的第一个实测；宿主 `package.py` 的 Apple clang 路径未实测（[round C 载荷可行性](../analysis/2026-10-28-roundc-payload-feasibility.md) 记「产物理论上同字节但未验证」）。宿主 meson arm64e 构建未做过这项实测。据此，重编 AIR 后哈希与记录值不同时，第一处置是核 `air-build-record.json` 的 `source_sha256` 与 `tree_sha256`，不是当成污染停下。

内核镜像不指认产出它的源码提交：版本串里的 `aec10a9` 是移植线基提交，roundb 与 round C 两份内核的版本串逐字相同（display 用 `strings -a` 加 `grep -F` 对 `handoff-12377-attr26-roundb.bin` 核过），拿两个内核镜像比版本串永远判不出源码差异，内核来历只能靠外部记录——roundb 那份靠 manifest 的 `build.sources` 逐字记录才定到 `e933479` 加当时未提交的改动。原因是生成的 `version.c` 嵌构建时间、构建者登录名与 `git describe --dirty`（规则在 `makedefs/MakeInc.kernel:285`），增量构建复用它（`version.o` 的 mtime 是 2026-10-26 12:50:44），只有干净重建才会变字节。另一处不确定性来源：镜像里嵌源文件绝对路径（`__FILE__` 带进来的），换检出目录字节就变，这同时是发布前的一道检查项。全树 `__DATE__`／`__TIME__` 零命中。未实测的是同源两次构建，以及那 15 个与改动无关却重编的目标文件是否逐字节稳定（round C 那次构建写了 16 个目标文件，task-1 那次 2 个）。

内核源码的可复现身份只有构建树的工作状态本身（10-28，display 双向不一致普查后 lead 定，取代同日早先的「两组」口径）：一个构建出来的内核，只能由 `out/xnu12377` 的工作状态定——HEAD（`5c9f563`）加它的脏已跟踪文件（当时 `osfmk/conf/files` 是 ` M`、`bsd/conf/files` 干净）加它的未跟踪文件内容（120 个 `??` 条目，含 `BUILD/`、整套移植驱动 `bsd/dev/adreno8*.c`、`iokit/Kernel/MiniIOMobileFramebuffer.cpp`、`osfmk/kern/redwood_threads.c`）。仓库那一侧两个方向都过期：正向，`xnu26/apply.sh` 单向铺出构建树（Apple tag `xnu-12377.121.6`、BASE `ac9718fb…` → 分支 `redwood26` → `BUILD/` 写进 `.git/info/exclude` → 按 `xnu26/patches/series` 73 件逐件 `git apply` → 把 `xnu/files/` 的 157 个文件用 `cp -P -p` 拷进去 → 再覆盖 `xnu26/files/.` 的 2 个文件），开头有守卫（目录已存在即退出），树铺出来之后没有任何脚本再同步它；反向，`xnu26/export.sh` 按 `git diff BASE` 重新生成 `xnu26/patches/` 与 `xnu26/files/`，是唯一写仓库那一侧的脚本，从不写 `xnu/files/`（按脚本注释是手工维护、与 xnu-8796 线共用），且自 10-27 15:18 以后没跑过。所以报 `5c9f563` 不能确定 framebuffer 驱动的内容，报 `5c9f563` 加 `c2ccc7c` 也不能——`redwood_frames_shown` 的定义与 `SYSCTL_INT(_kern_redwood, OID_AUTO, frames, CTLFLAG_RD, &redwood_frames_shown, 0, ...)` 注册只在构建树的 `bsd/dev/redwood_input.c` 与 `bsd/sys/redwood_input.h` 里（比 overlay 分别新 7 行与 13 行），overlay 那两份里这个符号出现 0 次。这条比版本串那条更容易被忽略：它不表现为一个可疑的读数，而表现为一个看起来完整的提交号。演变记录：「两组」口径（`out/xnu12377` 提交加脏已跟踪文件，加外层仓 `xnu/files/` 的提交与拷贝时刻）当天先立后退——它的前提是 `xnu/files/` 为权威副本，双向不一致普查（5 处不一致加 1 个孤儿文件，正反两个方向都有过期）否定这个前提。

比较初始化顺序要追踪资源申请、框架回调和首次启动的完整调用关系。某个启动函数没有配置时钟或地址映射，可能由更早的公共路径完成。先确定差异能解释哪个失败阶段，再选择修改；不能仅因涉及安全固件就提前调用 SCM。本次调用关系核对未支持这种顺序调整，调查继续检查 stream 与 context 分配。

同一驱动保留多种运行模式，先确认本机产品配置实际选择哪个入口。相同消息名在不同模式下可能有不同前置条件；本次普通 HFI 与硬件调度模式的 START 顺序和内存请求处理不同。局部公共消息通过后，仍按选定模式检查完整握手。等待最终应答期间若收到对方的资源请求，必须处理或明确失败，单向发送后等待 ACK 的模型可能不完整。

容器内执行成功后检查预期文件和 diff，再构建。heredoc 通过 stdin 传给容器需要 `docker exec -i`；遗漏该参数曾出现退出 0、文件未修改。`xnu/export.sh` 会重建导出目录，执行前核对来源和修改归属，防止导出过期副本或其他任务的临时诊断。

跨环境复制根目录要保留目标系统的符号链接语义。宿主无法解析目标环境路径，可能只是链接不能在宿主展开；先确认复制策略，再验证镜像中的文件、链接与库版本。本次复制失败后打包和上传仍继续执行，最后一步成功掩盖了输入不完整。复制、替换、打包、上传按依赖检查前一步结果，失败后保留明确的可复用产物，再重做后续步骤。

判断某个接口是否存在、签名是什么，按能执行的事实排顺序：编译或运行的结果在先，代码里的实际用法其次，读文档和头文件的结论最后。三者冲突时按能执行的那个改，并把两侧依据和结论一起留在提交说明或分析文档里。本次一边按头文件记忆得出「没有 `ctl_bind` 回调」，另一边同一份代码里有一整组这类字段并且编译成功，结论按编译结果定，同时请读文档的一方给出所读头文件的路径与版本。

接口结论要连同所属的树一起说。本项目 26 线与 16.5 线各有一棵内核树，同一个字段的可见性与签名可能不同：26 线的 `xnu12377` 里，`<sys/kern_control.h>` 给出的 `struct kern_ctl_reg` 只有公开字段，`ctl_bind`、`ctl_setup`、`ctl_rcvd` 在 `<sys/kern_control_private.h>` 的 `KERNEL_PRIVATE` 段里；16.5 线的 `xnu-8796.121.2` 里这些字段在 `<sys/kern_control.h>` 中直接可见，同一份代码在那棵树上编过，只在少了 `ctl_enable` 时链接失败。只写「这个 API 不存在」会让另一棵树上的工作按错的结论停下，「在这棵树里编过」也会被当成两棵树都编过。

容器不可用时，仍可在一棵树里验证单个文件能不能进核。该树 `BUILD/obj/DEVELOPMENT_ARM64_BCM2837/compile_commands.json` 里取任一同类文件的 `arguments`，把源文件路径和 `-o` 换成 `/tmp` 下的文件后原样执行，得到的结果就是该树的编译结果；再用 `nm -u` 列出目标文件的未定义符号，与同树已链接的 `mach.development.bcm2837.unstripped` 符号表逐个比对，全部能找到就说明链接不会缺符号。本次用这两步在没有容器的情况下确认蓝牙探针在 26 线里 0 warning，13 个未定义符号全部可解。这类检查覆盖编译与符号可见性，运行行为和初始化顺序仍需上机验证。

构建树中的临时诊断与长期修复分别导出。补丁既要能应用到明确基线，也要与实际编译输入一致；局部通过后继续核对完整应用顺序及最终产物，检查漏导出、基线不符和过期副本。

## 4. 把日志和诊断代码纳入被检查对象

日志有自己的执行路径：消息产生函数、console 选择、缓冲写入、loader 读取、主机保存。`kprintf`、`printf`、`IOLog` 和用户态 `/dev/console` 可能走不同分支；实时 USB 日志与内核返回后合并的 message buffer 也有不同覆盖范围。

日志为空先检查输出分支及缓冲状态，补齐观测后再缩小故障范围。本项目曾因实际 console 分支缺少缓冲写入而遗漏启动日志。

用「没有错误」排除原因前，确认对应检查已执行、覆盖本轮失败阶段，并在清除状态或复位前取得结果。诊断开关还需确认能截获哪类故障、记录能否留到主机读取；本次 fault stall 配置读回成功，随后复位仍未留下故障报告，缺少排除其他故障路径的依据。初始化时读过一次故障寄存器，只覆盖此前的访问；超时路径仍需保存现场。本次 GMU 失败日志起初缺少 SMMU 故障检查，补读后发现了故障。计数器递增也只确认它所属的时钟域有活动，其他处理器是否执行还需各自的状态或响应。

PMIC 复位触发记录、pstore、hypervisor 和安全固件日志各有覆盖范围；缓存可能含多次启动，零计数、空日志或加密输出都要保留读取时间与可解释范围。2026-10-25 的 PS_HOLD 记录与空 pstore 未能确定 RAW 复位原因，后续依靠执行位置与路由对照推进，见下段。

GPU 命令不继续执行，故障寄存器又为零，继续围绕「有没有报错」读取相同状态难以确定原因。后续读取各执行单元停留的位置，再对照实际固件，发现两个单元已经执行到同步等待，第三个单元应完成的动作始终没有发生。接下来查第三个单元的启动与取指配置，因为前两个能够运行只验证了各自的配置。最终发现第三个单元使用独立访存标识，驱动遗漏了对应路由，补齐后命令继续执行。遇到没有报错的停滞，先找到具体等待条件，再查负责完成该条件的模块；寄存器为零为何未报告本次故障仍未确认。详细结果见[A830 案例](../analysis/2026-10-24-a830-command-startup.md#lpac-路由与后续验收2026-10-26)。

检查点、异常处理器和日志函数同样受初始化顺序约束。早期阶段可能还没有参数、CPU 数据、锁、分配器或地址映射。检查点未返回，同时检查被测代码和返回代码所依赖的状态。

分阶段诊断要区分准备执行、正在执行和已经完成。访问前标记和停留必须先于目标访问生效，资源归属从首次修改开始记录；步骤中途失败仍可能需要恢复。扩大等待时间前，先确认暂停条件确实在目标访问前成立。

异常报告路径应尽量减少对出错子系统的依赖。若故障发生在持有 console 锁的路径，错误打印再次使用该路径可能触发锁重入，使最初的异常难以读取。优先在复杂调试处理之前保存错误正文、PC、LR、ESR 和 FAR，再检查报告过程中的新错误。本次 panic 锁地址用对应测试二进制的符号表定位到 `_vcputc_lock`，后续保留独立缓冲记录，降低对视频控制台的依赖。

临时提前返回、额外等待和高频日志只能覆盖对应的诊断配置。定位后清理改变执行顺序的临时逻辑，保留必要故障记录，再复测正常输入。否则诊断版的成功无法覆盖最终启动流程。

诊断也会占用时间、改变调度及访问硬件。调查性能前，先确认采样、日志和健康检查会给被测过程增加哪些动作，再用相同负载比较诊断开关。减少检查次数前，写明最多允许多晚发现故障、哪些失败状态必须立即生效；复用成功结果只覆盖限定时间，仍需到期重查及完成轮询中的故障处理。测试同时覆盖立即失败与到期发现故障，防止性能修改削弱停止条件。

周期采样需要配合区间峰值和状态转换计数。较低的间隔读数可能漏掉启动峰值，本次后续日志确认早先固定频率轮已经触发温控，旧的低温结论随之修正。频率请求、协议应答、软件保存的档位和实际时钟读数分别报告；执行耗时缩短可以支持性能比较，实际频率和温控执行仍需对应观察。统计脚本先用已知日志核对字段与单位；空样本、缺少时间标记、重复快照和字符串 `FAILED` 都需解释，零个异常只有在有效样本存在时才有意义。

地址分析必须使用本轮实际运行的二进制，并核对加载地址或偏移。先把寄存器、返回地址和锁地址对应到函数、数据对象或映射范围，再推导可能路径；仅凭数值接近或旧版本符号表容易误判。

短暂故障需要在运行期间保存独立快照，并记录主机单调时间、状态和文件长度。主机请求等待时间与设备故障时间分别说明：一次请求超时只能确定该请求未在限时内完成。调整采集频率需考虑 USB 读取本身对执行时序的影响。

日志快照按时间或数字编号选择，字符排序可能把较早的文件排到最后；同时保留最后一次请求与最后一个非空快照，分别解释传输状态和设备进度。

`sort -u` 之后的唯一行序是文本序，凡带时间语义的序列必须按锚点（`tl:` 微秒行、墙钟行）重建时间轴再读，排序与去重产生的任何顺序同理。2026-10-28 的实例：一次误读把 57→18 的线程收敛读成 18→57 增长（后在 task-19 文档更正）。

协议状态也可能依赖诊断缓冲。状态返回为空但日志仍增长，先检查格式化空间和缓冲生命周期；本次 loader 的状态字符串曾因日志填满而生成失败。修复状态输出后还要检查其他查询是否复用同一路径，并用缓冲接近容量或填满的情形验收。`getvar result` 的修复只覆盖该入口，`getvar screen` 的同类依赖继续单独处理。

日志里的完成标记只覆盖它所描述的动作。一次定时器 IRQ 进入和退出，还需要持续中断验收；一次 framebuffer 初始化，还需要帧提交和面板显示验收。

内核的 `memorystatus_perform_idle_demotion() timed out stuck process N [name]` 不能当成「某进程出问题」的判据。它的含义是「这个进程跨过两个 aging 期限仍未 idle」，服务端空闲时本来就会走到这里。2026-10-28 统计了 58 个证据目录，被判卡的只有五个名字（`AudioConverterService`、`pkd`、`iconservicesagent`、`extensionkitservice`、`installd`），而当时最干净的一轮（11,015 帧、无停帧）这五个里出现了三个。用这一行判断进程是否真卡住，会把正常态误判成故障；要用效果判断，例如记录有没有写出来、容器有没有建立、报错计数有没有归零。判据没坏这件事也由同一份统计支持：若判据随手标卡，`lsd`、`SpringBoard` 这类进程也会出现。

对账产物与构建输入时，判据是给每个镜像条目记「进入通道」（base apfs 自带／staging 树／PROBE 自建／PAYLOAD_PROGRAMS／EXTRA_JOBS），无通道的才算真丢失风险，并且配方本身要落进一个可执行记录。2026-10-28 的实例（round F 第一次跑轮中止）：没有任何文件丢失，丢的是配方记忆——roundb 的完整环境变量没有落进任何可执行记录，device 从 pack 记录逐字段反推配方时漏了两个（`PAYLOAD_PROGRAMS` 与 `JOBS_DROP`）；`framewatch` 历来经 `PAYLOAD_PROGRAMS` 进镜像（`package.py:53-56` 定义、`:452-454` 断言存在并 copy2 进 dest/bin、`:522-526` 计入 added 集合），`lsprobe` 历来经 `PROBE=1` 自建（`:64`／`:402`／`:495`），base 镜像与 staging 的 `/bin` 本来都不含这两个文件（base 镜像 `33ed5fc9` 的 `/bin` 34 条、staging 与 base 集合逐名一致、`package.py:422-425` 的 dest 树每次打包从 `BASE/root` 重新 copytree）。查法：pack 记录 `changes` 里每个 `null→sha` 的 added 条目必须归到一个通道，归不到的就是配方缺口；两层配方对账与全条目 diff 在[运行协议](k90auto-run-protocol.md)。早先的判据「这个文件有没有第二条来路」建立在「`framewatch` 来路只有 staging」的误判上，随根因撤销（device `3278bf9`）。

一行日志输出要先读产生它的那段代码，才轮得到推断它的含义：判的是哪个时刻、读的是哪个量，都在代码里。2026-10-28 的第六个实例（lead 自查）：按 `NOT_RUNNING hung-held` 的字面推断「开始一轮时设备状态是 hung-held、上一轮收尾没做主机冷复位」，作为事实发给 device 与 desktop 让两边按它写归档——display 读了 `run-auto.py` 之后不成立：`state()`（`:94-97`）读的就是 `getvar result` 一个量，`:152-158` 只在它不等于 `running` 时打印，`hung-held` 是 loader 在打印那一刻的字面应答；`:71` 与 `:176` 记着它由内核静默满 50 秒触发，而 `:127` 的开始断言在 21:07:44 通过了，证明那一刻 `result` 是 `idle`、开始一轮时设备状态是干净的。同日的配对正例（display）：改 `staging-entry-channels.md` 的引用之前先自己核了 `package.py` 的行号（`ALLOW_DRIVER_CHANGE` 在 `:213`、`dirty_sources()` 在 `:219`），没有按 lead 的转述改——转述里的行号是错的。规则是既有的那一条：成员报出的结论里带「所以」「说明」的段是推断，转述要标明是推断，不在推断上面建判据或派下游动作；这次的形状是读了一行日志输出就推断它的语义、没有读产生它的代码。配套加一条：**一个判断在发出之后被撤回时，要立刻点名已经按它写下的每一处产物，不能只发更正**——这次更正到达时 desktop 已按旧口径填完了归档骨架的两段，撤回方同时通知了全部下游所以更正送达了，但送达时产物已经写完；点名产物清单让下游能逐处核对改净，而不是各自凭记忆找。

## 5. 用状态和资源归属理解设备行为

Android、LK fastboot、fastbootd、驻留 loader 和 XNU 是不同执行环境。切换后重新枚举并查询身份；Android/LK 的目标序列号通过环境变量 `ANDROID_SERIAL` 提供，loader 使用 `xnuloader`。USB 枚举只说明设备描述可见，协议命令是否可用另行检查。

loader 与 XNU 在其他 CPU 上并行运行，仍共享中断控制器、定时器、内存和固件资源。`cpus=1` 限制 XNU 使用的 CPU 数量，`bootcpu=` 选择启动 CPU；逻辑 CPU 编号与 MPIDR 分别核对。某个初始化动作可能影响仍在处理 USB 的 loader，排查需要检查资源修改范围及调用顺序。单 CPU 交接可作为对照，但运行期间 USB 无响应可能来自控制权已交给内核，须等返回或读取新的启动状态后再判断。

### 硬件身份与寄存器来源分别核对

设备身份、寄存器地址、位域和访问权限分别核实。常量在多个文件中重复出现，可能都来自同一假设；先找到独立来源，再决定是否访问硬件。配置名称相同也要检查定义与消费者，不能按名称推导实际动作。

MMIO 读取需要有效映射、地址、宽度、电源及权限。诊断打印和平台识别也可能访问寄存器，应沿默认调用路径检查开关之前的动作。本项目的旧平台识别曾因此阻断启动，详见[启动案例](../analysis/2026-10-23-boot-debugging-sop.md)。

源码缺少某项设置，先读取接管后的实际状态，因为固件或更早的执行环境可能已经配置过。实验记录包含操作前状态、是否真正发生变化和后续结果；本次新增总线时钟使能前，该位已经置位，实验只确认了继承状态，未检验「关闭后开启」的效果。Android 框架引用计数、当前硬件寄存器和冷启动初始化分别检查，它们描述的环境与状态不同。

不同设备树与驱动可能使用不同资源起点。写出基址、子窗口偏移和单元步长的完整计算，检查遗漏或重复偏移。调试文件读取也可能触发硬件访问，优先核对已保存的描述，再选择定点检查；仅有操作后重启的现象，原因仍需保留不确定性。

字段位宽与总线访问宽度分别检查：按设备支持的宽度读取后，再提取有效字段。取得数值后继续核对其含义、单位和映射关系；本次速度分档与 SKU 来自不同来源，旧比较方式无效。结构布局、频率表和默认值都需要独立来源支持。

权限问题按访问主体、特权级、读写或取指及页属性组合判断。允许数据读写仍可能触发执行限制；本次允许非特权写入的页禁止特权取指，清除对应 AP 位后 GMU 启动。复用映射函数前按资源用途分别确定权限，固件、命令缓冲与写回数据不能仅因共用分配方式就沿用同一属性。

回读不一致先分类：必要控制位、可选提示、固定读值和保留位的验收方式不同。命令寄存器可能写入后自清，写一清除操作应检查目标故障状态；普通配置寄存器则继续检查有效位是否保持。传输完成但配置未变化，先核对操作码、地址格式与所有者，再考虑放宽读回检查。本次震动故障清除和手电写入分别对应这两类问题，见[桌面验证案例](../analysis/2026-10-26-gpu-validation-lessons.md#3-外设验证要检查实际状态和中途退出)。同时测试允许的差异可以通过、真正的写入失败仍会停止。SMMU 的相关边界见[桌面交互案例](../analysis/2026-10-24-interactive-runtime.md#9-后续初始化提供的判断经验)。

映射越界先按实际通道计算完整地址，再选择所需窗口。扩大到整个硬件区域会增加启动早期的地址空间和映射开销；本次 SPMI 从窗口不足改为整段映射后又分配失败，最终按已发现的通道分别映射。边界检查与最小必要映射一起保留，缩小范围后继续覆盖全部实际访问。

只读查询也要检查软件共享状态。多线程 panic 出现在设备树遍历中，本次源码确认查询使用共享游标；启动时缓存平台身份减少了运行期查询，遍历改用每次调用自己的游标才处理了其他调用方的并发问题。两项修改分别记录作用范围，短期未复现只覆盖该轮负载和时长。

软件页表检查从实际 TTBR 根遍历每个映射页，核对中间表、输出物理页、权限及完整缓冲范围；首个叶子正确仍可能遗漏其他页、根索引或跨边界映射。CPU 映射长度与设备 IOVA 范围也分别核对，CPU MMIO data abort 先按故障 PC、FAR 和映射边界检查。

配置回读、启用状态转换和设备实际访问分别验收。启用前还要核对资源保留规则、占用情况与字段之间的约束；数值可写只能确认对应访问完成。本次 context 回读通过后，stream 翻译启用仍触发异常。用故障指令和执行阶段定位后，先检查分配及匹配规则，后续固件执行检查暂缓。

使用已有硬件描述，需要同时核对生产者与消费者；当前 GIC 地址组合只覆盖项目支持的平台集合。未知身份应有明确处理，尤其不能因识别失败而继续执行机型专属写入。修正公共平台判断后，重新列出所有调用方及变得可达的默认分支；GPU 的识别修复也可能改变旧调频驱动的启用条件，寄存器访问仍需按本机核对。扩大平台支持时重新验证身份来源及未知分支，详见[独立评审 F02](../analysis/2026-10-23-independent-review.md)。

CPU 数量、逻辑编号、MPIDR、拓扑标记和在线时间分别核对。早期少一颗 CPU 可能来自延迟启动策略；本次完整日志确认第二颗在延迟后在线。拓扑字段还要沿生成器、loader、内核 CPU 查找、secondary 入口和跨核心中断逐处检查，任何一处掩码都可能截断身份。本次改为完整 MPIDR 表并保留 Aff2 后，两颗高性能核心在线；主机测试覆盖转换与编码，真机再验证启动、停止与返回。新增字段涉及多个消费者的修复需配套选择产物，启动失败的旧试验不产生性能结论。

主机端检查退出码、stdout、stderr、协议失败文本和预期字段。fastboot 曾以退出码 0 输出 `FAILED`；命令成功后也要确认 `product`、检查点编号或实际传输长度。依赖步骤只在这些条件满足后继续。macOS 使用 Python `subprocess.run(..., timeout=...)` 控制等待，不调用本机缺少的 `timeout` 命令。

### 缓冲和镜像都有生命周期

`oem log` 与 `oem screenshot` 准备数据，`get_staged` 读取最近一次准备的内容。它们共用暂存状态，应成对、串行执行。内核正常返回后先取 `result`，再直接读取已合并日志；额外调用 `oem log` 会重新生成内容，有限长度的 loader 缓冲可能缺少原始内核输出。

RAM 系统盘可以在同一驻留 loader 生命周期中复用。整机重启后重新上传；USB 断开、控制器复位和整机重启分别确认。每轮从日志核对镜像地址、大小和磁盘编号，不能沿用上轮「已经上传」的记录。

完整双盘模式中，`system.apfs` 作为 `md0`，小 `root.apfs` 作为 `md1` 并挂到 `/redwood`。仅有小镜像的检查点测试覆盖早期内核。重启后日志缺少 resident image，就先恢复完整输入，再验证根盘挂载，详见[根文件系统说明](../analysis/rootfs-strategy.md)。

主机超时或关闭进程后，设备端 USB DMA 请求仍可能未结束。abort 返回只确认调用结束，只有匹配且有效的终止通知才能解除缓冲归属；等待 IN 完成期间收到的 OUT 命令也需保留并只交付一次。空闲命令接收超时后仍要允许下一条完整命令，已经放弃的数据传输迟到后则只结束原请求。恢复测试覆盖事件交错、中止传输后的查询、重启及无法确认终止的资源保留；[USB 案例](../analysis/2026-10-25-loader-usb-after-panic.md)记录 v7 的实测边界。

为调查电源或共享资源而读取票值，先明确返回的是本方请求、其他参与方聚合后的状态，还是实际供给。本次 ARC 读数只描述 DRV2 的请求，实际电源由多个 DRV 的需求聚合；某一方返回零，仍需保留其他参与方的需求。修改前按实际等级解释读数，再确定本轮需要增加的请求，防止降低已经继承的需求。

获取读数也可能需要写命令、触发请求和处理 IRQ，应按实际副作用安排检查。先用纯寄存器读取确认版本、空闲状态与共享使用者，再决定是否允许协议请求；本次 ARC 诊断要求关闭共用 DRV2 的触摸路径。完成后只清理本轮占用和新增的控制位，保留其他位的当前状态；直接写回旧快照可能覆盖期间发生的其他修改。完成或取消无法确认，就保留状态并使用已约定的恢复方式；成功取得一个读数后还要检查资源回收。

### 恢复能力也是完成条件

用户已要求减少手动介入。实验前准备下一版产物、日志接收和恢复入口；每次失败先保存可用信息，再决定恢复方式。正常返回、协议错误后的有效请求、异常后的状态查询，都应成为调试工具的验收项。

初始化验收包含资源归属和退出顺序。先记录固件遗留的配置，只恢复本轮修改的部分；局部写入失败也需要撤销已生效的动作。释放或重用设备可访问的内存前，必须确认设备访问已阻止、映射已关闭、必要同步已完成。无法确认停止就保留内存并转入明确的恢复流程。测试既覆盖正常退出，也覆盖分配、回读与关闭失败。

提交失败且未返回 fence，仍需保留「设备可能已访问」的状态；解除映射失败或 TLB 同步未完成，IOVA、页表和内存 descriptor 也继续保留。通知消息、提交 ACK 和实际完成分别检查，绘制完成标记要依赖 fence 或设备写回。

异步完成信号按各自含义验收。GPU 写完 EOP、核心空闲与 GMU 更新队列读指针可能先后可见；本次阶段 22 在前两项通过后，单次读指针检查仍失败。针对尚未完成的队列消费增加有界等待，继续保留超时停止和资源保留；测试分别覆盖延迟更新与永久停滞。缺少这些区分就增加整轮等待，会掩盖首个未满足的条件。

有副作用的固件请求可能先执行、后应答。发送前记录「请求可能已生效」，ACK 超时或失败也保留该状态；已完成步骤计数无法覆盖这种不确定性。清理动作同样有状态前提：休眠消息需要完整参数，关闭辅助单元也可能保留电源投票或其他设备访问。本次 DCVS 之后的完整退出尚未验证，因此同时检查普通退出、失败退出和 panic 返回，保留映射及内存直到全系统复位；该限制只在完整停止流程通过后解除。

自动返回依赖它所在的执行阶段。`loader_return_after` 需要相应初始化和定时回调，早期停滞可能无法处理 `oem stop`。固件具有重启函数，还需确认板级实现及重启目标；冷重启与进入 FASTBOOT 分别验收。重启命令的成功应答只确认处理已进入相应分支，还要等待重新枚举并查询新状态。空闲状态下恢复成功后，异常状态及重复恢复仍需分别验证。

实验重启意外进入 Android，先查询 LK 的槽位成功、可启动和重试计数。连续未标记成功的实验启动可能耗尽重试次数并回退到受保护槽；已有 loader 镜像仍在，可经 ADB／LK 恢复入口，具体步骤见操作手册。不能仅凭进入 Android 推断实验分区已被改写。

软件恢复不可用再请求用户按键。一次说明完整动作、预期画面和后续操作。保留用户已尝试的动作及结果，并关联当时环境：本次重插 USB 未恢复旧 loader 停滞，后来 Android 桌面出现但主机未枚举设备，重插后 ADB 恢复。先前恢复动作的结果适用于对应状态；用户报告新画面后，重新检查枚举、协议和身份，再选择恢复动作。

设备轮中途失联时，先抢拉日志环，再发 stop（lead 2026-10-28 定的常设规程，修复轮开始前生效）：判据是环随时可能被新输出覆盖、也可能随 stop 丢失，抢拉动作排在任何 stop 命令之前。round F 的第二次异常是它的验证：harness 作业无声死亡、采样止于 238 s，device 先手动抢拉了 manual-s012-deepstatic.log 再做 teardown，环跨度因此覆盖了近全轮。

跑轮开始后每 60 s 核一次 `commands.jsonl` 的 mtime 推进（lead 2026-10-28 定的常设规程，修复轮开始前生效）：mtime 停滞即视为失联，走上一条的恢复规程（先抢拉环、再 stop、teardown 到 fresh idle 三项验证）。round F 的 harness 作业无声死亡时没有这个核查，死亡要到收尾才会被发现。

自己设的检查不能挡住一轮真机测试（lead 2026-10-28 定的常设规程）：自己加的检查——闸、断言、核验脚本——挡住一轮真机测试时，直接用该检查的放行开关或删掉检查，在那一轮的归档说明里记一行（挡住了什么、用什么放行、检查的原意是什么），不停下来等，也不升级到 lead。当天实例：`package.py` 的工作树检查把修复轮挡在一个文档任务后面，放行开关 `ALLOW_DIRTY=1` 一直存在，处置却是把关键路径排到文档任务后面；随后按用户要求把该检查删除——未提交改动只打印一行提示并写进 pack 记录的 `worktree_status`、打包照常进行，保留的是产物哈希基线检查（`library-baseline.json` 的 `driver_sha256` 与 `air_sha256`，本轮用 `UPDATE_BASELINE=1` 更新）。设备时间比这类检查的价值高，检查要说明的事情转为事后记录（这一轮由什么构成读 `worktree_status` 那份清单）。

一轮失败且失败签名对这一代载荷是新的时候，先报失败与重试计划，再决定要不要消耗下一次启动（lead 2026-10-28 定的常设规程）：判「签名是不是新的」用在历史轮次里搜同一签名的方法——搜到先例就是既有类、按先例类重试有依据，搜不到就是新的、必须先报再动。当天实例（device 自报的过程错误，按它的原文记、不作时序辩解）：第一次 `QUEUE stop` 在 21:09:4x，它 21:10 到 21:12 认出 panic 签名与先例类（在历史轮次里搜到 bbmetal11-panic 与 bbmetal12 两轮先例），21:13 前后重打，21:14:41 开始第二次，lead 的停止消息在它开始之后到达——按先例类重试有依据，缺的是报出来这一步。

## 6. 存储安全取决于所有权和时间

`boot_a` 用于实验，B 槽保留 Android；两槽共用 userdata。原始块写入绕过文件系统分配，剩余容量、尾部全零或 Android 能开机，都不足以确认某段空间可写。写入前核对区段所有权、逻辑块大小、起始偏移、长度和结束位置。

备份只覆盖采集时刻和指定范围。既有分区备份未包含 `super`、`userdata`；后补的 userdata 尾部备份晚于首次暂存写入。恢复旧备份前还要考虑之后的文件分配和写入。问题先后发生只能用于提出假设；确认某次原始写入损坏特定文件，需要物理区段映射等进一步检查。

当前系统盘通过 USB 传入 RAM。日志读取同样要核对副作用：`oem logwrite` 在缺少日志分区时会覆盖 `boot_a` 开头。命令名称无法说明写入范围，诊断入口与常规读操作分别审阅。备份与 NAS 清单见 `docs/backup/`。

## 7. 各子系统复用同一套判断方法

| 方向 | 优先区分的层次 | 验收边界 |
|---|---|---|
| Android 界面 | 进程 → 新崩溃栈 → 实际加载的包或插件 → 编译产物 → 窗口 | 定向处理后检查持续运行、新崩溃和用户操作；新栈指向另一个包就继续定位 |
| 显示与触摸 | framebuffer 地址、宽高、stride、格式 → 内存内容 → 面板扫描；驱动启用条件 → 原始触摸 → 坐标变换 → iOS 注入 | 主机截图确认内存内容；物理画面和触摸手势分别验收 |
| GPU | 镜像内固件 → 电源与时钟 → 地址映射 → GMU/HFI → 离屏提交和 fence → GLES／Metal／UI | 主机翻译、软件 renderer 和真实 GPU 执行分别验证 |
| Wi-Fi | PCIe ID/link/BAR → DMA/MSI → MHI → 固件/QMI → 数据传输 | 区分热启动继承状态与冷启动初始化 |
| 相机与音频 | 身份、时钟、电源、路由 → 缓冲与传输 → 帧或录放结果 | 检查格式、stride、长度及实际内容；播放与录音分别确认 |
| 按键、电池、振动、手电 | 原始读数与有效位 → 单项行为 → 退出状态 | 保留 fault、时长、限流及资源恢复条件 |

源码里存在驱动或固件，只确认实现和输入存在。构建、最终镜像内容、设备初始化和用户可用行为分别验收。各项当前进度见[开发指导](2026-10-23-development-guidance.md)及总账，已解决的 Android 案例见[系统界面修复记录](../analysis/2026-10-23-android-systemui-recovery.md)。

总线通信成功后，继续检查固件工作模式。身份与校验稳定、事件内容却全零，优先核对报告开关、地址和格式；本次 Goodix 需要关闭 THP 原始帧并开启坐标上报。参考同芯片的其他机型驱动可以提出具体检查，但必须注明分支来源，再以本机应答、有效事件和用户操作验证。类似地，电量、净电流、外部电源连接和充电状态需要各自的数据来源，本次 BQ 读数有效仍未完成充电标志验收。

原有功能再次失败，先查看本轮进程与最新错误。壁纸第一次因服务配置缺失而失败，修复后的一轮则记录扩展启动超时。相同画面允许多个解释；沿用旧修复前先确认它对应的前提是否再次发生。涉及共享总线的替代传输，还需检查引脚配置、占用和退出恢复，功能成功只覆盖已经测过的输入与资源状态。

QEMU 适合验证通用内核、镜像装配和用户态。日志可能重复输出同一事件，按时间、PID 和实际动作辨认；字符串出现次数不能直接用于统计启动成功次数。手机的显示、中断及外设仍需对应配置的真机结果。

借鉴其他项目先拆分 API、编译器、内核接口、缓冲同步和最终设备行为。记录源码版本、验证硬件、样本范围及未完成项；编译通过、提交成功、fence 完成和结果内容正确分别统计。本次 UniXNU 的 A740 Metal 路径为 K90 提供参考；本机已有 A830 GLES 桌面，Metal 路径与其他系统构建仍需各自实测。图形路径选择还要比较首次编译和缓存后运行，保留已经可恢复的对照配置，不能仅从 API 名称推定性能。

升级调查按具体设备与构建检查架构、动态库依赖和实际入口。相同系统大版本可能分别提供 arm64 与 arm64e；库中保留 GLES 字符串只支持继续调查该路径。先用最小程序验证加载、设备枚举，再做提交和读回，可逐层找到缺项。能力探测也检查服务端语义：未知请求返回成功会让客户端选择尚未实现的功能；成功返回零个设备仍需继续检查枚举分支。对应结果见[桌面验证案例](../analysis/2026-10-26-gpu-validation-lessons.md#4-兼容性判断逐层验证实际入口)。

## 8. 与用户和其他会话协作

- 目标有缺口，先问一个会改变架构、数据模型或用户体验的问题；可独立开展的只读调查继续进行。视觉或交互需要用户选择，先给低成本原型。
- 搜索从已知项目目录、脚本路径或本地运行目录开始，先列候选再定向读取。用户已明确反对无目的的全盘扫描；搜索范围扩大前，应能说明已知位置缺少什么，以及扩大范围要回答的问题。
- 沿用已有明确授权，保护数据和操作范围。新增影响先说明；不要因重复接手再次索取已有授权。
- 工作更新说明新发现、剩余未知和下一步检查的作用。用户的画面、声音、触感和按键反馈是独立观察，保留关键细节。
- 用户授权持续推进，后续在约定范围内继续工作，并按最新要求安排成果汇报。本次用户进一步要求硬件加速实际运行后再汇报；GMU 启动或 HFI 应答只作为内部阶段记录，任务完成条件仍对应实际加速。需要用户操作设备或作决定，再说明原因及所需输入。
- 用户修正观察后更新同一条结论，并保留影响判断的等待过程；解释错误要明确修正，不让旧说明继续成为检查前提。尊重用户确定的先后顺序，本次先处理交互与卡顿，其他外设留待可操作后调查。
- 用户质疑某个改动能否解决问题，先测量它对应的执行阶段，再解释收益范围。本次用户担心换核心仍然卡顿，后续通过 CPU 时间、慢调用和符号采样确认软件绘制耗时，随后才将 GPU 加速列为重点。
- 安全要求直接约束已排队实验。用户明确要求不触发九十多度后，撤下尚未启动的高温轮次，核对后续载荷也已修改。用主机注入覆盖异常温度、读数失效与恢复分支；自然触发的低阈值温控单独记录。未实测的分支保留为待验证，验收完整性不能成为继续升温的理由。
- 用户指定由操作系统决定调频策略，就把这项要求纳入实现约束。先区分硬件档位控制、系统提供的负载信号与最终策略，再核对现有接口及消费者。某条路径缺少闭源组件，就记录该依赖，其他接口是否可适配继续分别核对。采用自建策略前，说明已经检查的路径、采用原因与剩余复用可能，实施后保留替换条件及兼容性限制。借用已有算法只支持该实现选择，完整系统的功耗与温控仍需验收。
- 来源会话仍在执行，先固定本次读取的阶段与输入；后续计划只作背景，未结束的构建或诊断保留为待确认。旁路文档任务核对已有输出和本地文件，设备、服务、构建与代码操作由实现会话继续负责。
- 同一设备只由一个任务发送命令。共享构建树、overlay、导出目录和文档分别确认修改归属；旁路文档任务通过读取会话和本地材料整理经验。
- 用户暂时无法操作设备，实验选择也随恢复条件调整：优先运行能够自行结束、保存结果并返回已知状态的一轮，软件恢复尚未覆盖的故障继续保留限制。无人值守减少操作步骤中的人工参与，光亮、震感和真实按压等验收仍需对应观察；无人反馈期间只报告已经采集到的结果。
- 长队列还需固定运行脚本及分析器版本。执行期间修改脚本，可能使同一任务读取前后两版内容；本次队列结束处出现过语法错误，后续读取的文件已正常。先保存运行日志与版本并检查是否有重复设备任务，再决定重跑范围；语法错误的具体形成过程仍需核对。新脚本可以准备在独立副本，当前轮继续使用已选定版本。
- 获准并行后，按当前失败阶段分配能够独立回答的问题，说明实际输入、最后通过的步骤、首个失败动作、允许修改的文件和交付要求，明确共享接口与资源所有者。区分只读调查与实现任务；前置阶段失败后，暂停依赖它的设备测试，后续模块的调查可转向当前缺失的前提。
- 子任务交付应包含源码位置与适用版本、实际修改、验证范围、未确认项和下一项区分性检查。报告缺少依据的假设也有用，可以阻止未经验证的初始化顺序调整。多个报告采用同一来源，只增加核对次数；结论仍按该来源的适用范围判断。
- 整合者选定本轮文件版本，核对共享格式及实际构建输入，再统一构建和真机验证。各子任务的局部测试成功后，仍要检查跨模块的单位、布局、生命周期和失败处理；新故障出现后，把相关日志和阶段变化反馈给对应子任务，更新共同结论。
- 可以让独立子任务检查实现者容易遗漏的退出路径，并用删除保护条件的对照验证其必要性。本次资源生命周期审查保留了「请求可能已生效」状态，复杂度审查再移除无消费者的定义；精简范围由调用关系和状态语义决定。
- 后台任务被接收后，还要检查结束状态、退出结果及产物。完成报告说明实际变化、选择理由、验证范围和偏离。
- 历史总账与当前脚本冲突，先核对时间和实际行为。过期操作指令要修正或移到历史说明，尤其是写入目标与恢复命令。

dsh 数据位于用户主目录下的 `.dsh/sessions/`，项目缓存位于 `.dsh/storages/session_projcache/sessions/`；通过 `turnOutline` 定位，再读取对应 `session.v4.jsonl.zstd`。Codex 长任务可能只有一个很长的 turn，应提取近期消息和相关工具输出。Claude Code 的用户追加要求还可能保存在队列事件或附件，读取时一并还原；压缩摘要用于导航，再核对后续修正。用户要求完整阅读，就按固定范围分段覆盖全文、工具活动与图片，并在本地记录已读位置，重复的请求元数据单独识别。旧指令用于理解背景，本轮执行范围由当前用户要求决定。

## 9. 怎样维护这份知识

优先保留可复用的因果解释、判断顺序、数据边界和协作要求。已经由代码解决的单次缺陷，用短案例说明它验证了哪条方法；命令细节集中在当前操作手册，原始流水保留在本地日志和会话。

新条目至少回答一个问题：它会改变下一轮的检查顺序、操作边界或验收标准吗？保留一项具体观察，写清原来怎样判断、哪条输出改变了方向、为什么接下来选择那项检查。例如「缓冲新建慢」继续拆到分配、等锁与映射，读者才能知道下一次应在哪里计时。再说明这段方法适用于什么问题，以及哪些情况仍需另查。完整参数、地址和逐轮输出集中在专题与操作记录，同一方法的新案例优先补充原条目。会话中的过早归因和无效对照也要说明修正理由，成功结果覆盖的因果范围继续按实际试验判断。
