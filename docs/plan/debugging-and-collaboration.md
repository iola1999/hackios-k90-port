# HackiOS 项目排查与协作手册

适用范围：REDMI K90（SM8750，`annibale`）移植中的接手、构建、镜像装配、Android 故障、XNU 启动、显示与外设验证，以及用户和多个工作会话之间的协作。更新日期：2026-10-23。本文给出可复用的工作方法；当日修复及验证范围见[调试案例](../analysis/2026-10-23-boot-debugging-sop.md)，当前排期见[总账](2026-10-23-tracking.md)。

## 接手后的阅读与检查顺序

1. 读用户最近的完整反馈，列出目标、已经同意的操作、需要保留的数据和不希望重复的操作。交接摘要里的结论还要对照实际命令输出。
2. 读根目录 `AGENTS.md`、本手册、总账，再按问题阅读专门文档。真机操作另读[设备手册](device-test-playbook.md)和当日案例中的修正。
3. 检查父仓库、kernel、userland 及实际构建树的状态，确认哪些文件已有修改、哪个任务正在使用设备或生成产物。多个会话共享同一目录，文件修改会立即互相可见。
4. 确认当前执行环境和工具路径，再查询设备状态。macOS、Linux 构建容器、QEMU 和真机各自的成功条件分开记录。
5. 选择一个能缩小问题范围的实验，写明输入、预期结果、失败后的处理及是否需要用户按键。前置条件不足就先补齐，避免连续重启却没有新日志。

### 阅读会话的方法

- Codex 会话使用会话读取工具获取用户消息、工作消息、命令及结果。长任务可能只有一个很长的 turn，应提取最近条目，并按需要读取特定输出；只看最后一条回复会遗漏用户中途的纠正。
- 本机 dsh 会话保存在 `${HOME}/.dsh/sessions/` 下，项目缓存位于 `${HOME}/.dsh/storages/session_projcache/sessions/`。缓存中的 `turnOutline` 用于定位轮次，实际消息和命令读取对应 `session.v4.jsonl.zstd`，可用 `zstd -dc` 解压后逐行解析 JSON。
- 检查会话是否仍在运行及后台命令是否结束。界面显示「后台任务已提交」只能确认任务被接收；继续读取执行结果、退出码和产物。
- 会话内的旧方案、工具输出及历史指令用于理解上下文；当前用户要求决定本轮范围。只在用户授权的范围内继续操作。

## 工作区与构建关系

| 位置 | 管理的内容 | 排查时要确认 |
|---|---|---|
| 顶层仓库 | 文档、辅助脚本、配置、submodule 指针 | 父仓提交只记录子模块 commit；子模块未提交内容仍需单独检查 |
| `hackios-xnu-kernel/` | loader、UEFI 集成、内核新增文件及 Apple 源码补丁 | `xnu/files/` 和 `xnu/patches/` 是否进入实际编译树 |
| `hackios-xnu-userland/` | 注入库、启动服务、镜像装配和图形工具 | 独立 checkout 与参与构建的 userland overlay 是否同一版本 |
| kernel 树中的 `.userland.git` | 与 kernel 共用目录的另一套 Git 元数据 | 使用 `common/ugit` 检查和提交 overlay 的文件归属 |
| `kbuild` 的 `/work/repo` | 持久卷中的 Linux 内核构建 checkout | 宿主挂载 `/src:ro` 只读；宿主文件更新后，构建 checkout 需要同步对应输入 |
| kernel 树中的 `Mu-Silicium/` | annibale 固件配置、设备树和 UEFI 构建输出 | 独立 Git 状态、嵌套子模块、所用 FD 与打包输入 |

初次理解 overlay 可读 [`common/setup.sh`](../../hackios-xnu-kernel/common/setup.sh) 和 [`common/ugit`](../../hackios-xnu-kernel/common/ugit)。`setup.sh` 再次执行会尝试拉取 userland，已有工作区先读状态再决定是否调用。共享树的根 `README.md`、`.gitignore`、`LICENSE` 由 kernel 工作树保留，userland 对应条目使用 `skip-worktree`；更新这些文件可能影响 overlay 的快进合并，详见[离线记录第 33 条](../progress/2026-10-23-offline-prep.md)。

### 源码修改如何进入最终镜像

1. 改新增内核文件，更新 `xnu/files/` 中的来源，并将对应文件同步到本轮实际使用的 `xnu-src/xnu-8796.121.2/`。改 Apple 既有文件，保留到 `xnu/patches/`，检查 `patches/series`。
2. 运行实际构建并检查退出结果。当前可用命令与工具链限制见[内核构建文档](../analysis/kernel-build-linux.md)。`xnu/apply.sh` 用于创建新展开树，已有目录会被拒绝，不能依靠重跑它更新现有构建树。
3. `xnu/export.sh` 会重建导出目录。并发工作期间先确认输入树及输出归属，核对生成的完整 diff，防止把另一任务的修改或过期副本导回仓库。
4. 将产出的 Mach-O 复制到明确的测试位置，记录 SHA-256，再打包 payload。测试阶段可以使用 `out/` 中的候选产物，确认后再按项目约定更新 `prebuilt/` 及清单。
5. 检查实际消费路径。`xl`、QEMU 脚本会优先选择本地展开树中的内核，缺失后才使用 `prebuilt/`；只替换 `prebuilt/` 可能未改变测试输入。显式传给 `mkpayload.py` 的路径更容易核对。
6. 保存 kernel、loader、FD、DTB、两个 APFS 镜像、payload 和 boot image 的路径、长度、哈希、参数及构建时的 Git 状态。文件名可被反复使用，哈希需要与具体试验同时记录。

`userland/system.apfs` 是完整系统盘，`userland/root.apfs` 是小镜像。完整双盘启动中，system 作为根盘 `md0`，小镜像作为 `md1` 并挂到 `/redwood`。只有小镜像的检查点测试覆盖早期内核；完整用户态还依赖 system 镜像中的文件。磁盘编号以该轮 loader 和内核日志确认，详见[根文件系统说明](../analysis/rootfs-strategy.md)。

### 环境和工具的常见问题

- 本机新命令使用 Python `subprocess.run(..., timeout=...)` 限制等待，不调用 macOS 缺少的 `timeout` 命令。既有脚本如依赖 GNU 工具，先审阅依赖和执行环境；本机可用工具与容器内工具分别检查。
- Python 包按实际解释器确认。系统 `python3` 曾缺少 Pillow，脚本应先检查依赖；读取 framebuffer 可按已确认的格式转换，失败原因要保留。
- Shell 通配符可能在调用程序前就由 zsh 报错。文件搜索使用 `rg --files` 和 `rg --glob`；路径及参数用结构化数组传给子进程。
- 查询命令保留 stdout、stderr、退出码和实际耗时。fastboot 的有效结果常写在 stderr；丢弃 stderr 会遗漏设备应答。
- 同时检查退出码、协议状态和预期字段。本次 `getvar result` 曾以退出码 0 返回 `FAILED (Write to device failed (No such process))`，仅使用 `check=True` 会漏掉失败。脚本需要检查 `FAILED`，成功后再核对预期的 `product`、检查点编号或字节数。
- 管道末端成功可能掩盖前面失败；启用 `pipefail` 后，提前退出的 `grep -q` 或 `head` 又可能使生产者收到 SIGPIPE。涉及状态判定时先完整采集结果，再在主机内存中筛选。
- 一个步骤失败后停止依赖它的后续步骤。构建失败后的旧产物仍可能存在，必须核对本次退出结果与输入输出关系。

## 从现象到结论的排查顺序

先写用户或设备实际显示的现象，再选择能区分候选原因的检查。例如「没有通知栏」可先检查 SystemUI 进程与崩溃日志；「USB 无应答」先区分设备枚举、序列号选择、协议应答和内核是否占用 loader 所在 CPU。

每个实验记录以下内容，其他会话只看这一条也应能继续：

```text
问题：本轮要区分哪些原因
前提：设备模式、槽位、工具、权限、已验证的恢复方式
输入：源码状态、产物哈希、启动参数、上轮是否已经复位
操作：实际执行的命令与顺序
观察：退出码、耗时、日志位置、用户看到的现象
判断：本轮确认了什么，仍缺什么
下一步：成功和失败分别怎样继续
```

### 调试代码也需要验证

检查点、异常处理器、日志输出和返回 loader 的函数都可能依赖尚未初始化的状态。检查早期失败，先看这段诊断代码是否调用了平台参数解析、CPU 编号、锁、分配器或其他晚于当前阶段初始化的功能。

此次 `loader_jump()` 在检查点 10 返回途中调用 `PE_parse_boot_argn()`，相关 `PE_state.bootArgs` 尚未设置。主会话增加空指针前提检查后，用 `cpus=1 bootcpu=1` 取得 `checkpoint 10 0`，再得到后续内核错误。详细过程见[调试案例](../analysis/2026-10-23-boot-debugging-sop.md)。检查点失败的候选原因应同时包含业务初始化和诊断返回路径。

最后一条日志只确认此前执行过该输出。实际故障指令可能位于之后，也可能发生在异常或日志处理路径。继续定位时结合检查点、异常寄存器、符号地址与对应二进制，避免只按最后一条字符串修改模块。

### 检查生产者、格式和消费方

跨模块参数需要沿实际调用关系核对。GIC 例子是设备树的范围和 stride，经 loader 写入 Apple 设备树，再由 XNU 读取；显示例子是板级配置经 GOP 传给 `SCREEN` 和 `BootArgs.video`。只改某个未被执行的 fallback 分支，不会影响当前路径。

核对数据的单位、长度、对齐、字节序、范围和生命周期。数组里存在某个地址，仍需确认本轮内存映射覆盖它；寄存器窗口长度正确，还要确认逐帧步长。未知地址与读数应保留未验证状态，其他 SoC 的常量需要先核对 K90 的实际定义。

## 设备状态、USB 与运行恢复

| 已观察到的状态 | 下一项检查 | 可以据此确认的范围 |
|---|---|---|
| ADB 列出 `${ANDROID_SERIAL}` | 槽位、系统版本、`sys.boot_completed`、需要的 root 命令 | Android 调试通道可用；界面是否正常另行检查 |
| fastboot 枚举设备 | 按当前序列号查询 `product`、`is-userspace` | 区分 LK、fastbootd 和 loader |
| `product: xnuloader` 且能取日志 | 查询 `result`，读取本轮启动标记 | loader 命令循环可用 |
| USB 枚举存在但命令超时 | 确认序列号和内核运行方式，检查日志与实际复位现象 | 当前请求没有完成；执行位置继续调查 |
| 内核检查点返回 | 比对编号和本轮 payload，保存返回日志 | 该检查点及返回路径执行成功 |
| 根盘挂载或 SpringBoard 日志 | 确认环境、进程事件和屏幕 | 对应软件阶段已执行；真机画面与操作单独验收 |

ADB/LK 与 loader 的序列号不同，本次分别为 `${ANDROID_SERIAL}` 和 `xnuloader`。进入新模式后重新枚举。多台设备连接时按本轮确认的序列号操作；同一设备同时只允许一个操作任务发送命令。

### 驻留流程与日志顺序

1. 在已确认的实验启动槽启动带 `--usb` 的 loader，建立日志、截图和内存图基线。
2. 后续内核测试使用 `stage` 上传 payload，先运行 `selftest` 和所需检查点。修改 loader 或 UEFI 才重新构建其启动镜像。
3. 内核返回后先读取 `result`，直接 `get_staged` 保存已合并的日志，再准备其他日志或截图。当前状态的日志使用 `oem log → get_staged`，截图使用 `oem screenshot → get_staged`。
4. `get_staged` 与最近一次准备命令配对。截图和日志共用暂存指针，中途准备另一份内容会改变读取目标。主机 fastboot 的命令为 `get_staged`；loader 协议中的 `upload` 由该命令发起。
5. 需要运行期间读取日志，验证 `bootcpu=` 选定的 CPU 可启动、返回，且 loader 所在 CPU 继续处理 USB。`cpus=1` 只限制 XNU 使用的 CPU 数量。不同 MPIDR 的可用情况分别验证，`bootcpu=1` 的成功范围只覆盖此次测试。
6. 请求超时后先判断状态，不直接重复运行、刷写或切槽。早期内核停滞可能无法处理 `oem stop`；`loader_return_after` 依赖内核定时回调，也需要进入相应初始化阶段。

大镜像上传、日志准备、日志读取和后续内核运行分别检查结果。本次 2,492,227,584 字节系统盘上传返回 `OKAY`，耗时约 62 秒；随后读取空日志失败，后续命令超时。上传成功仍需继续检查镜像内容和挂载结果；读取日志失败应先调查缓冲长度与协议状态。主会话已为零长度上传增加 `FAIL no staged data` 响应，构建通过，真机复测尚未完成。

设备复位后重新确认 RAM 中的系统盘和 payload，不能沿用复位前的上传状态。USB 断开、USB 控制器复位和整机重启分别记录；恢复后查询身份、启动日志及镜像状态，再决定是否重新传输。大文件请求的主机等待时间按实际大小和测得耗时设置，状态查询与镜像上传分别设限。

`oem logwrite` 是存储写入操作，本版缺少 `logdump` 时会回退写 `boot_a`，标志仅在当前调用期间有效。正常诊断使用 USB 导出，保持启动镜像可用。自动读取模式和显式写探针的副作用分别核对，诊断命令的名字无法说明它是否写盘。

### 请求用户按键

确认软件命令无响应、确实需要人工恢复后，再请用户操作。一次给出一个完整动作，说明按哪些键、看到什么再松手、USB 是否保持连接、随后计划进入哪个环境。本项目已使用「长按电源键＋音量下直到出现 FASTBOOT，然后松开并保持 USB 连接」。

用户回复已到 FASTBOOT 后，实际查询设备身份再继续。实验前先准备下一版产物与接收命令，减少用户重复操作。若需要暂时回 Android 处理故障，说明具体原因和返回调试环境的顺序，保留用户希望减少 Android 重启及重复写入的要求。

## 存储与备份

- `boot_a` 是已约定的实验分区，B 槽保留 Android。两槽共用 userdata，保留 B 槽启动分区无法隔离 userdata 的修改。
- 备份按设备、分区名、大小、时间和哈希核对。`annibale-backup/20261022-2355/` 包含 123 个具名分区及六个 LUN 的 GPT 头尾；既有说明记录其中未包含 `super` 和 `userdata`。尾部备份另有范围和建立时间。
- userdata 尾部地址属于文件系统范围；原始块写入绕过文件系统分配。可用容量、尾部全零和已备份都不能确认目标区段当前未被使用。
- 备份覆盖的是采集时刻和指定字节范围。恢复旧尾部之前，核对备份后是否有新分配或写入。已有 Android 异常应先保存日志，再判断是否与该区域相关。
- 需要加载完整 iOS 系统盘，优先验证现有 USB 到 RAM 路径。其他分区暂存方案必须先确认区段归属、容量、写入影响和已有授权。
- 以块设备为单位核对逻辑块大小、起始偏移、写入长度和结束位置，执行前完成边界计算。loader 内存窗口的范围检查同样应在清零、复制和读盘之前完成。
- NAS 备份有独立清单，压缩文件与解压内容的哈希分别比较。既有 NAS 挂载曾不支持原子 rename，写入方法参考[补充备份记录](../backup/supplement-nas-20261022.md)。

## Android 异常的排查

先将用户的界面反馈对应到实际进程、窗口和日志。本次通知栏、手势条、动画消失，伴随 SystemUI 反复崩溃。`sys.boot_completed=1` 只确认系统发出开机完成状态，SystemUI 仍可能异常。

1. 读取 `logcat -b crash` 的时间、进程名、信号、错误消息和调用栈，同时检查包路径、编译产物和相关模块。记录修复前的状态。
2. 确定涉及的文件后保存副本和哈希。针对包的编译产物，优先查看设备当前 `pm help` 提供的操作；编译产物重建与清除应用数据的影响分别说明。
3. 每次修改后先记录工具返回结果，再重新取进程和窗口状态，并比较修复后的新崩溃记录。旧日志仍可能保留在缓冲区，按时间区分。
4. 持续观察进程 PID 与新日志，再请用户确认通知栏、手势和动画。一次窗口出现只能确认该时刻已创建，持续重启中的进程也可能短暂显示界面。
5. 错误变化后按新栈继续定位，避免重复处理已重建的缓存或直接扩大到整机清理。

2026-10-23 先保存 SystemUI 编译文件，执行 `pm delete-dexopt com.android.systemui`、`pm compile -m verify -f com.android.systemui` 并重启该进程。命令返回成功、窗口短暂出现，随后 PID 再次变化并记录 `SIGSEGV`。继续读取新栈，发现 `PluginInstance.loadPlugin` 和 `MIUIAod.apk`，再备份并重建 `com.miui.aod` 的编译产物。第二轮处理后进程保持运行，用户于 22:10 左右确认系统界面恢复。包路径、备份、命令和验收方法见[系统界面修复记录](../analysis/2026-10-23-android-systemui-recovery.md)。

本次验收覆盖系统界面，另有 `com.xiaomi.aicr:cognitionService` 的崩溃尚未调查。编译缓存异常的来源仍未确认，userdata 尾部写入与具体文件的物理区段关系也未取得。定向修复成功后保留这些未确认项，后续按实际影响分别处理。

## QEMU、显示和外设

### QEMU 的验证范围

QEMU 用于验证通用内核、镜像装配、用户态与默认配置。手机 loader 使用 `loader-phone.efi`，QEMU 使用默认构建的 `loader.efi`。旧试验中手机版 loader 用于 QEMU 曾在早期停滞，构建脚本现已分开输出；打包输入仍需核对。

检查 APFS 挂载、`launchd` 和 SpringBoard 运行日志，再检查实际画面。QEMU 日志可能重放同一段输出，统计事件应结合时间和 PID；`grep -c SpringBoard` 会把路径、配置、失败查找和重放都计算进去。关闭硬件开关的回归只覆盖该配置，K90 外设仍需对应的真机验收。

### 显示与触摸

显示依次确认实际使用的缓冲地址、宽高、stride、像素格式、写入内容和面板扫描结果。按 GOP 参数解码的主机截图可确认内存内容，物理显示还需用户观察。GOP 数值可能来自固件固定配置；Android DRM、面板 XML、LK 当前扫描模式分别核对。

触摸先检查原始按下、移动、抬起事件、坐标范围、旋转和中断，再检查 iOS 输入注入，最后用明确手势验收。画面错位与触摸坐标错误分开验证，避免同时改动两个路径。

### 板级驱动与图形、无线

| 方向 | 最小验证顺序 | 需要保留的边界 |
|---|---|---|
| 按键、电池、振动、手电 | 身份与寄存器范围 → 原始状态 → 单项输入或有限时长动作 → 退出状态 | 数据有效位、fault、限流或时长，以及资源是否已恢复 |
| GPU | 镜像内固件 → 电源与时钟 → GMU/HFI → 最小离屏提交和 fence → GLES → UI/Metal | 软件 renderer、shader 翻译和真实硬件执行分别验收 |
| Wi-Fi | PCIe 设备 ID/link/BAR → DMA/MSI → MHI → 固件/QMI → 数据传输与 iOS 接口 | 热启动继承的状态与冷启动初始化分别记录 |
| 相机 | 传感器身份和初始化资料 → 时钟/电源/SMMU → TPG → RAW 帧 | 尺寸、stride、格式、缓冲长度与帧内容逐项核对 |
| 音频 | 时钟和路由 → 缓冲与传输 → 录放结果 | 仅播放与实际录音的权限、输入来源和验收分别确认 |

上述表是后续排查顺序；各项已实现、已编译和已真机验证的范围以[开发指导](2026-10-23-development-guidance.md)及总账中的专门记录为准。启用一个新驱动前，先验证它需要的固件确实进入最终 APFS，并从镜像读回；源码目录存在文件只确认源文件可用。

Mesa/AIR 改动需同时检查实际 renderer、导出符号、动态库路径与构建戳。共享戳逻辑位于 `tools/mesa-stamp.sh`，文件排序使用 `LC_ALL=C`。缺少某个工具而跳过的检查要保留跳过状态；主机翻译、软件执行和 a830 硬件结果分开说明。涉及 `eagl.c` 拆分，还要检查 `mkeagl.py` 的扫描输入，参见[用户态审计](../analysis/linecount-audit-userland-2026-10.md)。

## 与用户及其他会话协作

- 目标优先。当前目标为 RAM 模式启动 iOS，问题定位期间先处理阻止下一步验证的具体故障。支线规划、代码整理和新增外设按依赖安排。
- 需求有缺口，先问一个会改变架构、数据模型或用户体验的问题；可独立开展的只读调查继续进行。视觉或交互需要用户选择，先给低成本原型。
- 用户的硬件观察逐字保留关键细节。解释应附当前能确认的范围，例如画面逐行偏移需要查几何参数，缺少通知栏需要查 SystemUI；未经验证的原因保持推断。
- 已有明确授权继续执行，新增不可恢复写入或超出范围的影响先说明。保护项、备份范围、需要人工恢复的前提写入交接，后续会话沿用这些边界。
- 工作更新说明新发现、仍未知的事项和下一步能回答的问题。后台作业实际启动、结束和产物分别核对，再报告对应状态。
- 设备操作、构建输出、共享 overlay 和导出脚本分配明确的操作归属。同一时刻一个任务控制设备；旁路文档任务通过读取会话和本地日志更新知识，保持主任务可继续执行。
- 不同会话产生的未提交修改分别保留。提交前检查逐文件 diff 与所属仓库，只纳入本轮负责的内容。
- 完成较大变更后说明做了什么、关键选择及偏离、与原要求的差异。测试描述明确环境、输入、结果和未覆盖部分。

## 复杂度、记录与本地产物

修改前追踪真实调用方和动态入口。已有接口能回答问题，就复用现有接口；新增参数、抽象或状态必须有明确消费方。跨模块修改使用 `reclaim-code-entropy` 审查：列出删除该设计会损失的行为，选择能验证该行为的最小检查。保留数据边界、权限和恢复需要的校验。

新文件与大改后净增长越线的代码文件按 `AGENTS.md` 的 800 行规则处理。拆文件还要同步编译列表、生成器扫描、私有声明及消费者；诊断关键阶段的行为修复与大规模整理分别验收。

记录放置约定：

- `docs/plan/` 保存可复用 SOP、规划和依赖；总账每项一行，链接详细记录。
- `docs/analysis/` 保存分析结论、必要数值、关键日志摘录及来源；结论要能在没有本地原始文件的 checkout 中读懂。
- `docs/progress/` 保存按日期的过程与验证范围。新实测修正旧结论，说明适用版本与输入，避免让历史快照继续指示当前操作。
- `docs/analysis/local/` 保存本地原始日志、转储、缓存备份和 manifest；新调试截图也可放在已忽略的 `docs/progress/evidence/`。既有 `*-debug.txt` 摘录由忽略规则覆盖。
- 忽略规则只影响未跟踪文件。已经跟踪的资料仍受版本管理；需要改变其归属，单独审阅用途和引用。子模块的忽略规则在其所属仓库内生效。
- 用 `git check-ignore -v <路径>` 确认具体规则，再看 `git status --short`。不得用全仓 `*.txt` 等规则隐藏本来应交付的配置或数据来源。
- 文件清理前区分可再生构建缓存、当前试验输入、备份和唯一日志。按实际磁盘占用检查，保留正在使用的构建环境与输入，避免重复下载和重编译。

交接至少写清当前目标、最后成功阶段、首个失败阶段、用户最新反馈、具体产物及参数、未提交文件归属、后台任务状态、恢复入口和下一项实验。自动化超时、一次成功返回和一次画面出现各有自己的含义，进度按实际验证范围更新。
